# Working loop and ownership

## Repeatable cycle

1. Discover a hypothesis from observed stalls, a paper, source or a prior failure. Record applicability and a falsifiable prediction.
2. Select the cheapest discriminating check. Distinguish placement/scheduling, arithmetic, routing and weight changes; freeze the appropriate correctness policy before results.
3. Bind branch, hypothesis, decision, graph revision and existing cycle budget. Use one durable execution system, not a second scheduler.
4. Build only for a source change. Preserve source/dependency/toolchain/artifact identity and compatible incremental objects; reuse a qualified image for runtime-only changes.
5. Check the actual binary and effective configuration. A successful build or tool help does not show that the treatment was used.
6. Quiet owned factory/agent/build processes before exclusive lab execution. Keep only necessary queue/recorder/recovery services. Check unrelated contention; never kill unrelated work.
7. Collect raw output, workload identities, resource observations, failures and cleanup. Resume/reconcile the same request after disconnect instead of duplicating it.
8. Evaluate engagement, correctness, completeness and equal-work performance separately. Record supported/refuted/inconclusive/blocked; update the next hypothesis without rewriting the previous contract.

## Responsibilities

| Owner | Responsibility |
|---|---|
| Operator | Objective, permitted effects, source/model roots, fresh deadline and resource/experiment/build budgets, numerical/quality policy |
| Agent | Evidence intake, hypothesis choice, justified branch decisions, package selection, interpretation and continuation proposal |
| CC runtime | Package/material identity, grants, invocation receipts and scoped verification |
| Factory Store/taskgraph/loop | Durable evidence, decision lineage, revisions, reservations and cycle-to-attempt linkage |
| Manager/supervisor | Admission, quieting/recovery, owned-job reconciliation, result ingestion |
| Lab/queue/recorder | Hardware-facing bounded execution, raw telemetry/output, actual termination and cleanup facts |
| RSI | Improve selected CC jobs against their own contracts, failures and costs; do not weaken checks to improve scores |

## Measurement rules worth retaining

- Spark CPU/GPU share DRAM; cgroup peaks, host availability, model residency and GPU-driver allocation are different observations. Do not add them into an invented total.
- An8GiB cap on a12.1GB model is over allocated budget, not necessarily over physical RAM. The later large DeepSeek work has a separate model/source/image binding.
- Shared page cache can fake an SSD-streaming story. Use justified owned-file control and measured reads; never clear the global host cache.
- Preserve all demanded experts for scheduling tests. Prediction may move data earlier, not silently omit work.
- Use fresh-process balanced comparisons and held-out confirmation; distinguish prefill, decode, first request and combined latency.
- Instrumented traces explain mechanism; observer-off measurements establish performance. Measure observer overhead.
- Failed correctness remains failed under its original contract. A new approximation policy needs a new experiment, not a post-hoc relaxed threshold.
- Native/Docker access here is trusted-local, not hostile-code isolation. No blanket cleanup, driver changes or global dependency installation follows from this handoff.
