## Model and benchmark decision

1. **Admit the model.** Begin with the retained DeepSeek asset inventory. The historical oversized Strata run used six assets totaling 256.8 GB, and its execution does not establish stock llama.cpp compatibility. Check complete shard and tokenizer identity, source-supported tensor layouts, placement/headroom and an actual deterministic `llama-server` completion. The local atlas pins `9048bad8d6e3a0f9f1726e238e451181c7e02613` as a starting revision. If the oversized pack fails admission or the timebox, use an approved, pinned DeepSeek-V2-Lite-Chat GGUF as the fallback model. Choose one checkpoint for both benchmark arms and the live demo. [Retained Spark implementation evidence](<../../reference/factory-source/docs/architecture/factory/SPARK-IMPLEMENTATION-NOTES-2026-11-13.md>) · [DeepSeek-V2-Lite-Chat model card](https://huggingface.co/deepseek-ai/DeepSeek-V2-Lite-Chat) · [Pinned llama.cpp server documentation](https://github.com/ggml-org/llama.cpp/blob/9048bad8d6e3a0f9f1726e238e451181c7e02613/tools/server/README.md)
2. **Qualify decode or switch once.** Use a reasonable stock configuration within the same memory ceiling. Check baseline A/A token agreement and run-to-run noise. Measure non-overlapped demand-read time on the decode critical path. A 1.30× speedup from eliminating that wait alone requires it to account for at least 23.1% of baseline time, with practical headroom above that bound for partial savings and overhead. If the smaller model is fully resident, prefer the prefill branch over an artificially starved stock baseline. A separately labeled memory-budget workload is valid if that budget is an actual requirement and applies to both arms.
3. **Alternate for resident weights or weak I/O leverage.** Try **Long-prompt prefill scheduler builder** plus **Memory-budget planner builder**, using the existing batch and microbatch paths to choose a larger safe prompt chunk and fall back near the workspace limit. The source change must add useful behavior such as adapting chunk size to a request/memory profile. Screen the best safe stock chunk settings and use the strongest as baseline. Score client time to first token (TTFT) on a fixed long-input, short-output workload, with native prompt time as the explanation. A retained Strata run on 4,096 input / 16 output tokens measured 37.22% lower native prefill-plus-decode latency when changing chunk size. This is a workload lead for a llama.cpp experiment. Confirm within the target source and model. [Retained Spark results](../../CURRENT-STATE.md)

### Freeze before scoring

- **Workload.** One client, one pinned checkpoint/quantization/tokenizer, fixed prompt set and output cap, identical generation/sampling and context. Start screening at 512 prompt / 128 generated tokens for decode or 4,096 prompt / up to 16 generated for prefill. Freeze prompt hashes, termination policy, cache condition and engine/resource settings. Disable prompt-prefix reuse for these phase comparisons and verify actual prompt tokens processed. Predeclare whether the main workload is first-after-initialization or steady repeat. Time and label both. A fresh server does not imply cold storage.
- **Comparison.** Run A/A first, screen on development prompts, then use held-out prompts and counterbalanced ABBA/BAAB blocks across independent server starts. Target four or more adjacent A/B pairs, with at least four process starts per arm. Keep all trials, report paired results and uncertainty, and extend if noise obscures the gain. Keep build jobs and AI4R activity off the Spark during timed runs. Use separate diagnostic captures for heavy tracing.
- **Headline.** Decode uses generated tokens after the first token divided by client elapsed time from first to last token. Verify the client’s streamed event-to-token mapping or use an exact engine token count and documented stream timestamps. Prefill uses client request-to-first-token elapsed time. The proposed bar is at least 1.30× throughput or 1.30× inverse TTFT (23.1% lower latency), with reproducible positive paired effects. Report TTFT, full completion time, tail token gaps, native phase times and memory/headroom alongside the headline. Freeze guardrails before scoring. A faster native phase with worse client completion time cannot support a claim of faster completion.
- **Correctness and mechanism.** Require matching greedy token IDs, stop reasons and completion counts on the frozen checks for these behavior-preserving changes. Investigate A/A or candidate divergence before attributing speed. Verify the path engaged and no requests failed or fell back unnoticed. For expert readiness, count demanded expert bytes ready at first use divided by total demanded expert bytes. Report demand wait/token, actual reads and speculative waste if applicable. A readiness-only result can be shown under its own scope if it beats a frozen threshold and explains actual waiting behavior.
- **One evidence chain.** Emit one run summary keyed by workload, baseline/candidate source and executable/image digests, model manifest, effective settings, CC receipts, native and client measurements, output checks, and the decision. Use it to generate the chart, the stage handoff and the recorded fallback.
