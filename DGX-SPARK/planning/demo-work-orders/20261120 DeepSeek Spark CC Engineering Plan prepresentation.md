# 20261120 DeepSeek Spark CC Engineering Plan prepresentation

**Target DeepSeek V4.1 Flash 1017 on a single 128 GB DGX Spark, with a modified `llama-server` streaming a real completion.** Build three reusable CCs around the routed-expert path. The first two should deliver a measurable decode candidate on their own. The third gives us a second large opportunity when long-prompt expert execution is the bottleneck.

| Priority | CC to build | Owns a complete engineering responsibility | Release order |
|---|---|---|---|
| 1 | **Expert Weight Residency Builder** | Weight residency. Accounts for the shared budget, selects a static warm set, manages admission and eviction, and keeps slots valid until consumers finish. | First decode candidate with CC 2 |
| 2 | **Expert Weight Streaming Builder** | Weight residency and its loader/backend interface. Maps selected expert IDs to source byte ranges, coalesces actual demand reads and exposes a weight-ready handle. | First decode candidate with CC 1 |
| 3 | **Routed Expert Execution Builder** | Model execution and Tensor execution backend. Groups prompt rows by selected expert, executes groups on the appropriate backend, and restores the original row/weight ordering. | Add only when a routed-prefill profile supports it |

The two Weight residency CCs have a useful seam. The residency builder owns **which bytes may occupy memory and when their slot can be reused**. The streaming builder owns **how bytes get there and when they are safe to consume**. Sequence state supplies its reservation. The router supplies authoritative expert IDs and mixture weights. Existing factory build and lab CCs take the source through to an independently checked executable and result.

The no-draft file set totals **231.74 GiB on disk**. File size describes the storage footprint. The working set depends on placement, actual row and expert access, page cache and live state. ## Targets and criteria for proceeding

| Opportunity | Primary target | Select it when | Pause or change direction when |
|---|---|---|---|
| **A. Expert-streamed decode** | **1.5×** client decode tok/s preferred. **2.0×** stretch. **1.30×** minimum for a speedup headline. | Stock completes repeatably. Uncovered routed-expert wait is substantial. Held-out, byte-weighted residency replay indicates enough avoidable misses under the real budget. | Stock wait is mostly Engram, model execution or synchronized copies outside the chosen seam. Workload-critical I/O waits cannot plausibly yield 1.30× after overhead. |
| **B. Grouped long-prompt prefill** | **2×** inverse TTFT preferred (50% lower TTFT), **1.30×** minimum (23.1% lower TTFT). | Long prompts deliver enough rows per expert, and stock spends material time in routed CPU compute or repeated expert transfers. A small group-kernel screen shows a meaningful win, including staging and reduction. | The best stock batch profile is close to the ceiling, or the gain comes only from repeated-prefix reuse or altered outputs. |
| **C. Functional integration** | A live completion, two CCs engaged, exact output under the fixture contract, and a documented bound on memory and demand readiness. | Model and components pass correctness, with insufficient evidence for a speedup headline. | Treat an output divergence, OOM, unbounded allocation or silent fallback as a failed qualification. |

For decode, estimate `speedup = 1 / (1 − f × r + h)`, where `f` is the baseline fraction spent on **uncovered routed-expert wait**, `r` is the fraction of that wait the change can remove, and `h` is new overhead as a fraction of baseline time. Count only critical-path stalls. Four sample budgets illustrate the decision:

| Baseline uncovered expert wait | Wait removed | New overhead | Estimated decode multiplier |
|---:|---:|---:|---:|
| 40% | 60% | 5% | 1.23× |
| 50% | 75% | 5% | 1.48× |
| 60% | 70% | 4% | 1.61× |
| 70% | 80% | 5% | 2.04× |

With 5% overhead, **1.50× requires removing at least 38.3% of baseline token time** and **2× requires 55%**. A high ready-byte hit rate can still yield a small gain if hits already come from the OS page cache, if the expensive misses remain, or if a synchronization barrier moves to another part of the graph. Track useful reads, physical reads and uncovered wait independently. For prefill, use the same calculation with affected routed compute and transfer time, including any overlap in the baseline. Measure client TTFT and include initialization-independent request work.

## Work orders for the three builders

### 1. Expert Weight Residency Builder

- **Inputs and output.** Take the pinned model inventory, a physical-memory ceiling, fixed tensor and runtime reservations, the observed KV/state and workspace envelopes at admitted contexts, I/O buffers, and a training trace. Produce a deterministic placement manifest, a bounded slot manager and an effective-config receipt. Report infeasible plans explicitly. Use the atlas’s 96 GiB example for the presentation. Derive actual caps from host observations.
- **First version.** Use a frozen hot set derived by layer and physical bytes with a simple bounded fallback policy. Compare against a same-size ordinary cache and tune only on training traces. Deduplicate shared allocations and include double-buffered staging, resident copies and page-cache effects. Allocate for the longer admitted context at startup. Avoid dynamic resizing during decode for this release.
- **Acceptance.** Replay both context budgets and prove that increases in sequence reservation reduce admitted slots within the same cap. Exercise oversize bypass, simultaneous lookups, eviction pressure and retirement after the final backend reader. On Spark record host headroom, peak process/device accounting, and cache fallbacks and admissions by phase. Use host-wide measurements as well as process counters on unified memory.
- **Reuse.** `engine.expert_cache_lab` for policy fixtures and offline selection. The local placement lab for budget and scheduling examples. Reuse stock `--fit`, tensor overrides and `--n-cpu-moe` in the baseline sweep so the new planner earns its result.

### 2. Expert Weight Streaming Builder

- **Inputs and output.** Take model identity, validated shard/offset/stride/quant metadata, a retirement-aware slot interface and the authoritative routed set for a layer and token batch. Return ready weight views plus completion/release events. Keep I/O and completion logic reusable across model-specific layouts. Reject an unsupported layout during admission.
- **First version.** Start with one supported CPU/mapped expert path and demand-only reads. Compare controlled page warming with explicit buffers on the real path. Choose one. The lowest-integration-risk path may be page warming, but it only succeeds if page-cache residency can be observed and bounded adequately. If it cannot, use owned compact slots with explicit reader lifetime. Queue at most one fill per expert identity, bound outstanding bytes, handle short reads, and favor demand. Do not add speculative prefetch in the first benchmark.
- **Source seam.** DeepSeek 4.1 feeds routing logits into `build_moe_ffn` in `src/models/deepseek41.cpp`. The CPU backend consumes selected IDs in its `MUL_MAT_ID` path. The ggml scheduler already has a `callback_copy`/host-weight path and an input-prefetch path. Trace which branch actually runs before choosing the hook. Verify that IDs are available before dereferencing weights and that no CPU/CUDA user can outlive a slot. Preserve existing complete-tensor semantics when that path is selected. A compact-slot implementation may need a dedicated consumer/view. A global scheduler synchronization after every routing op can erase the gain.
- **Acceptance.** Compare packed weight ranges against the original GGUF bytes. Stress simultaneous same-key requests, short reads, failed fills and cancellation with pending reads. Show source counters for cache engagement and wait; verify exact selected IDs, mixture weights and greedy generation on A/B checks. Count Engram, MoE reads and scheduler/backend copies separately. [V4.1 routing](https://github.com/ggml-org/llama.cpp/blob/9048bad8d6e3a0f9f1726e238e451181c7e02613/src/models/deepseek41.cpp#L877) · [CPU consumer](https://github.com/ggml-org/llama.cpp/blob/9048bad8d6e3a0f9f1726e238e451181c7e02613/ggml/src/ggml-cpu/ggml-cpu.c#L1566) · [Existing scheduler data movement](https://github.com/ggml-org/llama.cpp/blob/9048bad8d6e3a0f9f1726e238e451181c7e02613/ggml/src/ggml-backend.cpp#L2100)
- **Reuse.** Jetson `expert_fill`, `inflight_join` and `expert_readiness` as integration design material. `engine.ssd_streaming_lab` supplies bounded-read, failure and cancellation fixtures. Keep existing mmap and lazy paths available as the reference and fallback.

### 3. Routed Expert Execution Builder

- **Inputs and output.** Take authoritative expert IDs and mixture weights, token-to-row mapping, ready packed tensors, shape/quant capabilities and a workspace bound. Return the same weighted rows to the model, with path counts and an effective workspace receipt.
- **First version.** Group ready experts over prompt rows, dispatch the existing grouped/quantized CUDA expert path for one supported weight format when there are enough rows to amortize staging, and restore row ordering. Compare against the stock CPU/GPU split and best safe batch/microbatch settings. Leave short or unsupported groups on their proven path. The pinned CUDA backend already has `MUL_MAT_ID` kernel selection and fusion. Prove from profiling that the proposed dispatch changes which work reaches those kernels. Reuse them before attempting a new kernel.
- **Acceptance.** Use tagged row fixtures with repeated expert IDs and uneven group size. Compare all rows to the existing implementation with explicit numeric tolerances, then require exact frozen greedy tokens and stop reasons for the Friday headline. Check untouched decode performance and peak memory. If source admission or GPU numerics consume the allotted time, ship the qualified decode pair and keep this CC as a separate follow-up.
- **Boundary.** Generation runtime owns prompt chunk admission. If the profile shows pure prompt-chunk overhead after optimizing stock flags, the alternate third assignment can be a **Prompt Batch Scheduler Builder** under Generation runtime. Only switch if the same fixed workload demonstrates a remaining scheduling bottleneck. Avoid turning ordinary flag tuning into evidence of a new source component. [Existing CUDA expert path](https://github.com/ggml-org/llama.cpp/blob/9048bad8d6e3a0f9f1726e238e451181c7e02613/ggml/src/ggml-cuda/ggml-cuda.cu#L2224) · [Server prompt batching](https://github.com/ggml-org/llama.cpp/blob/9048bad8d6e3a0f9f1726e238e451181c7e02613/tools/server/server-context.cpp#L3914)

**Further opportunities.** The Expert Demand Predictor follows the measured floor. It starts only if the demand-only path shows actionable residual wait and a held-out, byte-bounded simulation predicts timely bytes net of waste. Measure proposed lookahead against the available overlap window. Keep the existing router authoritative. Quantization, speculative decoding and KV compression are separate experiments with their own quality or cache-state obligations. Their gains cannot be attributed to the first three CCs.
