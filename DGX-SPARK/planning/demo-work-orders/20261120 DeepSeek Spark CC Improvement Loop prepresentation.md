## 2. Make one methodology CC that can direct several builders

Prototype one **Lab-Guided Improvement Methodology CC** behind the existing CC host. Inspect and extend the existing `factory.methodology_diagnosis`, `factory.methodology_hypothesis`, `factory.methodology_ablation`, and `factory.methodology_followup` materials and contracts before adding a new capability. A cohesive extension is enough if it supplies the required output and real invocation receipt. Keep the existing evidence CC and the November 13 planner. This methodology can choose measurement, placement, scheduling, prefetch or execution assignments and can improve a factory CC when its use fails. It owns the method and the evidence-backed proposal. Builder CCs own changes to software components.

**Input.** One immutable evidence bundle with build/model/contract identities, effective settings, comparable A/A or A/B data, trace schema and quality status, bounded resource grants, source/atlas mapping, and earlier decisions if applicable.

**Output.** A structured recommendation (`collect_more`, `propose`, or `stop`) with evidence IDs, bottleneck and alternative explanation, estimated benefit and cost ranges, required observations, source owner and CC candidates. A `propose` result includes a **versioned ontology delta** (entities, relations, inferred state and how each is observed) and a **draft child contract** referencing the base and delta, mapping the observed requirement to one treatment, one falsifier, guardrails and an acceptance test. Unknown telemetry remains unknown. The method proposes; task admission, source changes and scoring remain in the existing planner, controller, builder and lab.

Example. If a real timeline shows several consumers waiting on one in-flight expert, extend the ontology with `ExpertDemand`, `InFlightFill`, `ReadySlot` and `BackendReader`, and relations `joins`, `becomes_ready` and `retained_until`. Bind those to measured queue/join/ready/release events and actual code ownership. The draft child contract may then test one bounded change to fill scheduling while holding memory and outputs fixed. A high missing-byte counter alone is insufficient evidence of wait, and an ontology change alone does not change runtime behavior. Ontology → contract → builder CC → changed code → measured evidence makes the hypothesis testable.

## 3. Close one loop before expanding it

1. Use existing method CCs first for A/A, matched comparison, and diagnosis. Exercise the new methodology on retained fixtures for at least a missing-signal case, noisy A/A, and a supported one-change hypothesis. Then have the actual JiuwenSwarm session call it on the live lab evidence. Preserve the CC receipt, ontology diff, new contract revision and the agent's decision in the Friday task plan.
2. Execute at most one evidence-backed successor in the first live loop. Choose from expert residency/queue policy, expert-demand prediction with measurable lead time and limited waste, or grouped prefill if profile data favors routed compute. Require an implementation seam and estimate net benefit from uncovered wait and new overhead. Prefer the change with the largest credible client-visible gain under the deadline. Keep the shipped run reproducible. Score the successor against its qualified parent and compare the best full stack directly with qualified stock at matched settings. Use fresh evaluation prompts for scoring after trace-based tuning, and keep exact output and host bounds.
3. If readiness or telemetry is missing, use the next iteration to repair the observation contract. If the CC as used produced poor code or needed recurring manual intervention, revise it and show the before/after use receipts. If a valid experiment is null, record it and protect the stronger engine. Fixing the method and improving the engine may both be valuable, but each needs its own evidence.
