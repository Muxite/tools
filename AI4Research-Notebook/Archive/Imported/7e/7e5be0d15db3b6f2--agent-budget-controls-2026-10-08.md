# Agent Budget Controls in OpenJiuwen and Current Harnesses

**Research date:** 8 October 2026  
**Scope:** runtime-level token and monetary controls plus budget-aware execution; model selection and routing are outside the recommended implementation.

## Executive summary

The industry has three distinct patterns: hard execution caps, usage/cost accounting, and budget signals that let an agent adapt before a hard cap. Most open harnesses expose the first two more clearly than the third. Anthropic’s task-budget API and recent budget-aware-agent research make the remaining-budget signal an explicit part of the agent loop. Tool-call budgets also matter because agents spend resources on both model reasoning and acting.

OpenJiuwen already has meaningful runtime enforcement. Generic Harness stop conditions and goal budgets cover outer task loops; Agent Teams SwarmFlow uses shared and per-workflow token ledgers, model-call rails, and terminal budget events. JiuwenSwarm configures and surfaces the shared SwarmFlow cap. However, these mechanisms are not yet one uniform budget contract: generic Harness budgets are token-only, monetary cost handling is isolated in an application-specific Auto Harness, and the normalized harness protocol’s cost field is only populated by some provider integrations. SwarmFlow accounts actual reported usage after a model call, so a call can cross the ceiling; concurrent in-flight calls can add further overshoot.

**Recommendation:** extend the existing runtime control pattern rather than adding a model router. Normalize usage and estimated cost at model-call boundaries, introduce a shared run/team budget context with token and currency caps, reserve capacity before calls or parallel work, reconcile actual usage afterward, and expose a remaining-budget signal to workflow planning. Begin with opt-in SwarmFlow support, then generalize it to the generic Harness task loop after provider coverage and graceful termination behavior are proven.

## Research findings

### Budget-aware agent research

- [Budget-Aware Tool-Use Enables Effective Agent Scaling (BATS)](https://arxiv.org/abs/2511.17006) studies explicit tool-use budgets in search agents. Its lightweight Budget Tracker gives agents continuous resource awareness; BATS adapts planning and verification, including when to continue a promising line or pivot. It evaluates a combined token and tool-use cost. The findings are promising but task-domain-specific; the paper does not establish that the same policies improve every agent workload.
- [Token-Budget-Aware LLM Reasoning](https://aclanthology.org/2025.findings-acl.1274/) dynamically adjusts reasoning-token budgets to task complexity and reports lower token use with a modest performance trade-off. This concerns reasoning generation more than whole multi-agent execution.
- [BudgetMLAgent](https://arxiv.org/abs/2411.07464) reports lower cost and higher average task success for an ML engineering benchmark using a multi-agent design. Its mechanism includes model cascades and expert calls, so it is useful evidence for cost-quality trade-offs but falls outside the no-routing runtime-control recommendation.
- [AgentBalance](https://arxiv.org/abs/2512.11426) evaluates multi-agent designs under matched token-cost and latency budgets. Its backbone selection and topology optimization are relevant to the broader field, but model/backbone choice is explicitly outside this scope.

### What the research suggests for runtime design

Budget awareness and enforcement solve different problems. A hard limit prevents continued execution after exhaustion; a remaining-budget signal can help the model or workflow choose shorter plans, reduce fan-out, skip low-value retries, or reserve time/tokens for verification. BATS provides evidence for adapting tool use, while Anthropic’s [task-budget API](https://platform.claude.com/docs/en/build-with-claude/task-budgets) injects a server-maintained token countdown into the model’s context so it can finish more gracefully. Anthropic describes this as advisory: the client still needs its own accounting, and server and client token counts can differ.

Cost and token limits should remain distinct. Tokens are useful for provider-neutral ceilings, while dollars account for model-specific input/output and cache pricing. Dollar amounts produced from local price tables are estimates, not billing truth; Anthropic’s [Agent SDK cost documentation](https://code.claude.com/docs/en/agent-sdk/cost-tracking) explicitly warns that SDK-computed cost can diverge from billed cost when pricing, model recognition, or billing rules differ.

Across these systems, step/iteration limits are common and inexpensive to enforce, but they are only proxies for spend. Usage summaries are also common, but they do not stop work by themselves. ## Gap analysis and recommended design

### Gaps to address

1. **No single budget contract.** Generic Harness token stops, goal token limits, Agent Teams ledgers, and Auto Harness cost controls are distinct APIs and lifecycles.
2. **Monetary data is partial and estimated.** The provider-neutral result type supports cost, but accounting coverage varies. Existing Auto Harness pricing constants are fixed estimates; they should not be silently treated as billing truth.
3. **Enforcement is post-call for actual usage.** A hard cap can be exceeded by the call that crosses it. Parallel agents create additional in-flight exposure unless spend is reserved before dispatch.
4. **Budget signals do not consistently drive execution policy.** SwarmFlow scripts can inspect remaining tokens, and goal prompts show token status, but generic execution does not expose a standard remaining-resource context for deciding whether to fan out, retry, verify, or finish.
5. **Tool and non-model resource usage is not included in SwarmFlow token spend.** BATS treats tool use as a separate constrained resource. For OpenJiuwen, tool-call count and tool-specific monetary cost should be optional budget dimensions rather than implicitly conflated with model tokens.

### Runtime design

- **One shared `BudgetContext` per execution tree.** Track independent token and monetary caps, spend, reservations, currency, and accounting provenance. Support nested scopes such as call, workflow/run, and team/session; child work shares the parent ledger while optional child limits reserve from it. Keep it in runtime/harness code, not the model router.
- **Normalize call accounting.** At the provider boundary, emit token usage and optional monetary cost with model/provider identity, cache breakdowns, and whether cost is provider-reported or estimated. Preserve unknown separately from zero. Use a configurable price source to estimate only when no authoritative cost is available; do not use these rates to choose a model.
- **Reserve before costly work; reconcile after.** Before dispatching a model call or fan-out, reserve the maximum known output allowance plus an input estimate. Deny or reduce the request when the reservation cannot fit. When the response returns, replace the reservation with reported usage/cost and release the unused portion. This limits concurrent overshoot; provider-side fees or unreported usage still prevent a universal guarantee of exact final billing.
- **Expose remaining capacity as an advisory signal.** Add a provider-neutral runtime view for remaining tokens/cost and near-limit state. Inject it into planning/goal context and expose it to workflow scripts. The orchestrator can use deterministic policies for expensive retries, subagent fan-out, tool loops, and verification, while allowing a graceful summary/final response when work must stop.
- **Keep hard enforcement independent from model compliance.** Model-visible awareness is an optimization. The ledger admission checks remain authoritative. Emit explicit `budget_warning`, `budget_exhausted`, and `budget_overrun` outcomes with scope, cap, spend, remaining amount, and accounting confidence; preserve completed work/checkpoints where possible.

### Staged implementation target

1. **Unify measurement:** use the SwarmFlow rail and normalized harness protocol as the first integration seam; map usage from all in-scope model providers, expose cost provenance, and measure missing-usage rates.
2. **Add dual token/USD reservations to SwarmFlow:** preserve `swarmflow_budget` compatibility, add opt-in monetary configuration, use atomic ledger reservations before parallel worker/model dispatch, and report overrun separately from normal failure.
3. **Add adaptive execution guidance:** surface remaining budget to SwarmFlow planning and script primitives; establish default thresholds for reducing parallel branches, retries, and optional verification while preserving a final-answer reserve.
4. **Generalize after validation:** adapt the shared contract to generic Harness `StopCondition`/goal execution and Java counterparts; keep existing token-only fields as compatibility aliases during migration.

### Acceptance checks for a later implementation

- Usage parsing distinguishes omitted values from zero, handles cumulative versus delta streams, cache/reasoning counters, failed calls, provider-reported cost, and estimated cost.
- Exact-fit requests are admitted; over-budget reservations are denied; unused reservations are released; concurrent requests cannot jointly reserve more than the shared cap.
- Actual usage exceeding its reservation emits an explicit overrun and prevents further admission. Missing usage follows a documented strict-cap policy rather than silently charging zero.
- Nested workflows, child agents, retries, resume/checkpoint replay, and parallel fan-out account each call once and do not reset shared-session spend.
- Near-limit guidance reduces optional work while allowing completion; exhaustion has stable UI/API status, preserves usable partial output, and does not masquerade as success.
- Python/Java API behavior, SwarmFlow configuration, and progress events remain compatible when budgets are unset; existing token-only configurations keep their current meaning.
- Offline evaluations compare task success/quality, token usage, monetary estimates, tool-call volume, latency, and overrun rate at several budget levels. No model-routing policy is needed for this evaluation.
