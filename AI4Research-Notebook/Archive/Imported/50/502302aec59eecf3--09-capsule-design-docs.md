- `docs/CAPSULE_ECOSYSTEM_DESIGN.md` — 1139 lines / ~79 KB, dated inline "2026-02-03"

## Summary (5 bullets)

1. **CAPSULE_ARCHITECTURE.md is a from-scratch protocol spec**, not an as-built description: it defines a `capsule/v1` YAML schema (6 contract sections: interface/permission/guarantee/risk/verification/evolution), a 4-layer protocol stack (identity/verification/execution/composition), a `capsule://namespace/name@version` URI scheme, algebraic composition-spec-derivation rules, a SQL data model (`sys_capsules` etc.), and ends with a literal "Next steps" TODO list — none of whose five items ("implement Capsule Runtime", "implement Verification Engine", "migrate existing Skills", "build Capsule Registry", "implement composition engine") matches the actual registry/schema architecture that now exists in the repo.
2. **CAPSULE_ECOSYSTEM_DESIGN.md is almost entirely aspirational multi-agent/marketplace speculation**: a 5-layer protocol stack (Discovery/Trust/Composition/Execution/Specification) with Ed25519 signing, a SCARE 0–100 numeric score, a federated cross-agent JSON-RPC invocation protocol between "Claude / GPT-5 / Gemini" agents, a 4-tier namespace governance model (Core/Verified/Community/Experimental), plus a large section on LLM-context token-budget optimization (lazy spec loading, index compression, caching tiers, spec "dehydration") and a composition DSL (`>>`, `[]`, `?`, `while`, `||`). None of this — URIs, JSON-RPC invoke, SCARE scores, federation, governance tiers — has any corresponding code in `harness/` or `core/` (verified by grep, all zero hits except unrelated files).
3. **The actual implemented system (registry + schema + admission, per established facts) bears only a loose family resemblance to either doc.** The real `capability_capsule_id` naming (`cap.foo`, `adapter.foo-to-bar`, `guard.secret-leak-guard`) is dot-namespaced, not the `capsule://ns/name@semver` URI the docs mandate throughout. The real schema's 11 required top-level sections (`capability_capsule_id, capsule_kind, metadata, applicability, contract, composition, effects, bindings, verification, operator_compatibility, provenance`) share only "verification" and roughly "contract"/"effects"≈"permissions+guarantees+risks" as conceptual overlap with the docs' 6-section YAML; the doc's `permissions/guarantees/risks/evolution` sections and the SQL tables do not exist as such.
4. **SCARE in the two docs is inconsistent with itself and with the code.** ARCHITECTURE.md defines SCARE as Safety/Completeness/Accountability/Risk/Evolution — five *qualitative properties*, not a metric. ECOSYSTEM_DESIGN.md then treats "SCARE score" as a single 0–100 *number* used for trust ranking, governance tier eligibility (≥90 for Core, ≥70 for Verified), and cross-agent routing decisions — a scoring formalism never given a formula and absent from code. This is a documentation-internal drift, worth flagging in the report as evidence the docs are unreviewed brainstorm artifacts rather than a maintained spec.
5. **Neither document argues for or demonstrates any actual formal verification.** "Verification" in both docs means declared preconditions/postconditions/invariants as *expression strings* checked by an unspecified "Verification Engine" (static/symbolic/runtime/post-execution phases are named but no logic, prover, SMT solver, or type-theoretic formalism is described anywhere in ~2100 lines). "Symbolic verification" phase names ("precondition_satisfiability", "termination_analysis") are listed as bullet items with zero elaboration — no algorithm, no tool, no worked proof. This directly contradicts any reading of "formally verifiable" as meaning machine-checked proof; it is a labeling aspiration, not a verification theory.

### Q2 — Formal verification story

The document repeatedly uses "可形式化验证" (formally verifiable) and "verification protocol," but:
- **No formalism is named.** No temporal logic, Hoare logic, SMT/Z3, dependent types, model checking, or any named verification technique appears anywhere in either document.
- **"Verification" = expression-string contracts, not proofs.** Preconditions/postconditions/invariants are given as free-form boolean expression strings (e.g. `"input.location.length > 0"`, `"no_filesystem_access()"`) evaluated presumably by some interpreter — this is closer to a design-by-contract / assertion-checking scheme (a la Eiffel contracts) than to formal verification in the sense of static proof.
- **The "symbolic" verification phase is a bullet list with no method**: "precondition_satisfiability," "postcondition_reachability," "invariant_preservation," "termination_analysis" are named as line items under Phase 2 (§3.3) with zero elaboration on how any of them would actually be computed (no SAT/SMT encoding, no abstract interpretation, nothing). Termination analysis in particular is a famously undecidable-in-general problem for arbitrary code, and the doc gives no restriction (e.g., to a DSL without unbounded loops) that would make it tractable — this is a claim with no supporting theory.
- **What is actually claimed to be checked**: schema validation, type checking, permission-declaration completeness, dependency resolvability (static); precondition/postcondition/invariant expressions and side-effect declarations vs. actual side effects (runtime + post-execution, essentially runtime assertion checking and audit logging, not proof).
- **No claim of completeness or termination guarantees is substantiated** — "completeness" in SCARE means something like "the capsule's contract fully describes its behavior," an authoring-discipline claim, not a decidability or completeness-theorem claim.
- **Conclusion**: the docs *claim* the word "provable"/"可验证" liberally but the actual mechanism described is contract-based runtime/static assertion checking plus manual/automated code review (per the ecosystem doc's governance tiers, "强制代码审查 + 形式化验证" for the Core tier — formal verification is *named* as a gate requirement for the highest trust tier but never defined). There is no worked proof, no soundness argument, and no verification tool referenced by name anywhere in ~2100 lines.

### Q3 — Capsule lifecycle: authoring, registration, versioning, deprecation, evolution

- **Authoring**: write a `capsule.yaml` conforming to the 6-section spec (§2 of ARCHITECTURE.md); optionally migrate from an existing Skill/Script/MCP by "adding a spec" (§5.2 worked example, tagging `migrated_from: skill:weather-fetch`).
- **Registration**: implied by the `sys_capsules` SQL table (§7) — a capsule row is created with `verification_status: pending/verified/failed`; the ecosystem doc's Discovery layer (§1.1) additionally proposes `capsule://registry.solar.ai/discover` and DNS-SD/mDNS for local discovery, and a `FederationRegistry.register()` call (§1.3.1) for federated registration — all speculative, no implementation referenced.
- **Versioning**: strict SemVer with narrowing rules on evolution (§6.1): permissions can only shrink except on MAJOR bump; timing guarantees can only tighten except on MAJOR; output schema can only add fields except on MAJOR; new version must pass all old version's test cases. Version *constraint* operators (`^`, `~`, exact) are defined for dependency resolution.
- **Deprecation**: the `evolution.deprecation` contract block (§2.1) has fields `deprecated_features`, `sunset_date`, `migration_guide` — all null in the worked example, i.e. the schema has placeholders but no deprecation *process* (who declares it, how consumers are notified, what happens at sunset) is described.
- **Evolution / growth**: the 3-tier atomic→composite→meta model (§6.2) is the closest thing to a lifecycle-of-the-ecosystem narrative — a generative flow where unmet needs first look for a matching capsule, else generate an atomic one, verify, register, and if composable, generate a composite capsule, and if a "meta-pattern" is detected, generate a meta-capsule (a capsule-generating capsule). This is entirely aspirational; no `capsule-generator`/`capsule-migrator` meta-capsule exists in the registry (checked: registry has 80 capsules, all "capability/guard/resource" kind, none matching this "meta" concept).

### Q4 — What is the ECOSYSTEM design? What does "ecosystem" mean here?

"Ecosystem" in this document means, concretely, a **federated multi-agent-vendor marketplace and trust network** — not primarily a single-user or single-org capability catalog. Its components:
- **Discovery/marketplace**: a registry protocol (`capsule://registry.solar.ai/discover`) plus local mDNS/DNS-SD discovery, envisioned as something like an open directory of publishable capsules across namespaces (`solar.core.*`, `verified.*`, `community.*`, `experimental.*`).
- **Cross-vendor interoperability**: the multi-agent diagram explicitly names Claude, GPT-5, and Gemini as peer agents that could each run a Capsule Runtime and interoperate via a shared Federation Layer — i.e., this is pitched as a *cross-LLM-vendor* open protocol, not an OpenSolar-internal-only mechanism.
- **Trust/reputation**: Ed25519 signing of capsule authorship, SHA-256 content hashing, a composite trust_score formula blending static (spec quality), dynamic (execution track record), and community (usage/reviews/incidents) signals — this is explicitly a reputation/marketplace-trust system, akin to a package-registry trust model (think npm/PyPI trust scores) crossed with agent-to-agent routing.
- **Community contribution**: the 4-tier governance model (Core/Verified/Community/Experimental) is explicitly a **contribution funnel** — "任何人" (anyone) can publish to `community.*` with only automated static checks, while `solar.core.*` requires the core team plus mandatory review and "formal verification."
- **Dependency/composition resolution**: DAG dependency graphs and static type-compatibility checking for composing capsules from possibly different providers/namespaces are part of the same "ecosystem" layer stack.
- **Economic/cost framing**: budgets (`context.budget.max_cost`), per-capsule cost accounting, and SCARE-based agent selection all suggest an implicit micro-economy of capsule invocation, though no actual payment/billing mechanism is specified (cost fields are informational/quota-like, not transactional).

In short: "ecosystem" = an open, cross-vendor, signed, reputation-ranked, tiered-governance **capsule marketplace with federated discovery and routing** — a much larger ambition than the current single-process, single-repo, YAML-registry-based implementation described in the established facts.

### Q5 — Composition model in theory: typed composition, effect algebra, compatibility rules

- **Typed composition / compatibility rule**: `A >> B` requires `A.output_schema ⊇ B.input_schema` — described as "structural subtyping" with covariant outputs (can be more specific) and contravariant inputs (can be more general), i.e., a fairly standard structural/duck-typed subtyping discipline lifted from JSON Schema field presence, not a nominal or algebraic type system. Field mismatches are resolved by an explicit user-supplied "mapping" transform, statically checked for validity at composition time (per the doc's claim; no checker is shown).
- **"Effect algebra" / effect union**: the docs do not use the term "effect algebra" verbatim, but the composition-spec-derivation rules (ARCHITECTURE.md §3.6 and ECOSYSTEM_DESIGN.md §3.4) constitute an ad hoc effect-composition calculus:
  - **Permissions/resources** (the closest analogue to "declared effects" in the established-facts vocabulary) compose by **union** (`permissions(A→B) = permissions(A) ∪ permissions(B)`) under every composition type (sequence, parallel, conditional, loop, fallback) — this is the "effect union" referred to in the task prompt: whatever a composite capsule's children can touch, the composite is declared able to touch the union of all of it, regardless of whether all branches actually execute at runtime (e.g., conditional composition unions *both* branches' permissions even though only one branch runs — a deliberately conservative/sound over-approximation).
  - **`denies`** (explicit negative permission declarations) compose by **intersection**, not union (`deriveSpec` §3.4 of ECOSYSTEM_DESIGN.md: `denies: intersection(subSpecs, s => s.permissions.denies)`) — i.e., a composite only denies what *all* children agree to deny; if any child doesn't deny filesystem access, the composite doesn't either. This is a subtle and important asymmetry: permissions are unioned optimistically (assume worst case = anything any part could touch) while denials are intersected conservatively (only guarantee what everyone guarantees) — together they bias the derived contract toward *broader* stated capability and *narrower* stated restriction, which is the safety-conservative direction for a permission system (better to over-declare risk than under-declare it) but under-documented as a deliberate design choice; the docs state the arithmetic but never argue why union/intersection is the correct or safe combinator.
  - **Timing**: sum (sequence), max (parallel/conditional), ×N (loop), sum-worst/first-typical (fallback).
  - **Cost**: sum (sequence/parallel/fallback-worst), max (conditional), ×N (loop).
  - **Idempotency**: logical AND across all children for sequence/parallel/conditional/fallback, but **hardcoded to `false` for loop** regardless of the child's own idempotency — an explicit, uncommented policy choice ("循环通常非幂等" / "loops are usually non-idempotent") that overrides the general AND rule without justifying why a loop of provably-idempotent atomic steps couldn't itself be idempotent.
  - **Preconditions/postconditions** (ARCHITECTURE.md §3.6 only, for sequence): `precond(A→B) = precond(A)`, `postcond(A→B) = postcond(B) ∧ (postcond(A) → precond(B))` — this is the one place the docs write something resembling a genuine Hoare-logic-style composition rule (sequential composition's postcondition entails the successor's precondition is implied by the predecessor's postcondition). It is not extended to parallel/conditional/loop/fallback in either document, and it is never connected to an actual prover.
- **No true "effect algebra" (in the PL-theory sense of an algebraic effect system with handlers, or a resource-typed effect monoid)** appears; what exists is a fixed table of ad hoc combinators (union/intersection/sum/max/AND) hand-picked per composition type, presented via a switch statement rather than derived from general algebraic laws.

### Q6 — Capsule KINDS/categories vs. implemented capability/guard/resource split

### Q7 — Relationship to Skills / MCP / Agents / Operators / "State Capsule" / "ECapsule"

- **Skills**: ARCHITECTURE.md explicitly positions Skill as a lower-priority, lower-trust mechanism than Capsule in the REE integration ladder (§5.1: P0 Capsule > ... > P3 Skill > P4 MCP > P5 Agent), and gives a full migration recipe "Skill → add spec → Capsule" with a worked before/after example converting a `skill: weather-fetch` command into a Capsule (§5.2). The framing is that Skills are a *predecessor/legacy* form that Capsules are meant to formalize and supersede for anything requiring verifiable guarantees — but there's no claim that all Skills must migrate, and Skill remains in the priority ladder as a still-valid (lower-trust) execution path.
- **MCP**: also placed below Capsule in the priority ladder (P4) and given its own migration path "MCP → wrap spec → Capsule" (i.e., an MCP tool gets wrapped with a Capsule contract rather than reimplemented). ECOSYSTEM_DESIGN.md's `FederationRegistry.consumes` example (§1.3.1) explicitly lists `capsule://solar.mcp/filesystem@1.0.0` and `capsule://solar.mcp/network@1.0.0` as consumed capsules — implying MCP capabilities are themselves expected to be exposed *as* capsules in a `solar.mcp` namespace, i.e., MCP becomes a capsule-namespace/provider rather than a separate system.
- **Agents**: positioned at P5, below Capsule/Shortcut/Script/Skill/MCP — i.e., ad hoc multi-step agentic orchestration is treated as the *least* trusted/most expensive fallback in ARCHITECTURE.md's ladder, to be used only when no verified capsule exists. In ECOSYSTEM_DESIGN.md, "Agent" instead means a *peer LLM system* (Claude/GPT-5/Gemini) that hosts its own Capsule Runtime and federates with others — a completely different sense of "Agent" from the REE-priority sense in the other document. **This is an internal terminology collision worth flagging**: "Agent" means "orchestration fallback mechanism" in one doc and "peer LLM vendor/runtime" in the other.
- **Operators**: the word "operator" in the physical-operator-selection sense (from the established facts, e.g. `NO_SELECTABLE_PHYSICAL_OPERATOR`) **does not appear in either document.** Neither doc discusses "which operators may execute" a capsule as a declared field or concept — `ExecutionContext.caller` (a string identity) is the closest analogue, but there is no operator-compatibility contract, no operator registry, and no notion of "physical operator" binding at all. This is a genuine gap: a core piece of the implemented schema (`operator_compatibility` as one of the 11 required sections) has **no precursor or discussion in either design doc.**
- **"State Capsule" / "Execution Capsule (ECapsule)"**: **neither term appears anywhere in either document** (checked via full read, not just grep — both documents use only the single unqualified term "Capsule"/"胶囊" throughout, with `Capsule`, `ComposedCapsule`, and `CapsuleProvider` as the only `kind:` values ever used). There is no deprecated-alias table, no migration note referencing older "State Capsule" or "ECapsule" naming, and no indication either doc is aware such naming ever existed. If "State Capsule"/"ECapsule" are real prior-generation names used elsewhere in the repo (e.g., in `kernel/` or older docs), these two documents give **zero migration guidance** connecting them to the current Capsule concept — this should be flagged as an open question / documentation gap rather than assumed resolved.
