# 2606.11926 · Toward Generalist Autonomous Research via Hypothesis-Tree Refinement (Arbor)

arXiv 2606.11926 · 36 pp (16 body, references at p17)
Read: p2-3 (intro, related work), p5-13 (formalism, framework, all experiments,
ablations, cost). Discussion p13+ and appendices skimmed only.

## Summary
Arbor formalises **Autonomous Optimization (AO)**: given an initial artifact M₀, a
natural-language objective, a **development evaluator E_dev** and a **held-out test
evaluator E_test**, improve the artifact without step-level human supervision. Its
mechanism is **Hypothesis Tree Refinement (HTR)**: a long-lived coordinator owns a
persistent hypothesis tree; short-lived executors test one hypothesis each in an
isolated git worktree. A **held-out merge gate** admits a candidate into the best
artifact only if it improves E_test (p5, p8). This is the closest thing in this sweep to
a mechanically enforced verification tier inside an end-to-end research system.

## How it works (p5-8)
- Node n = ⟨hypothesis hₙ, insight ιₙ, metadata µₙ⟩. Metadata holds status, dev score,
  factual result record and a **git branch/commit reference**; the artifact itself is
  never duplicated into the tree (p6)
- Coordinator loop is six steps: **Observe → Ideate → Select → Dispatch →
  Backpropagate → Decide** (p7, Alg. 1). Observe re-grounds from the tree, not from
  conversational history, so context compression cannot corrupt state
- Executors are **hypothesis-bound**: they may repair the implementation Δ but may not
  change hₙ, "otherwise the returned score would no longer be evidence about the
  assigned node" (p8). They cannot write to the shared tree
- **Decide / merge gate** (Alg. 1 line 11, p7): `if O(E_test(b_n†)) > O(E_test(M_best))
  then M_best ← merge(b_n†)`. Dev-only wins are recorded as evidence of overfitting, not
  as progress
- Insights are propagated upward so a leaf-level observation becomes a direction-level
  constraint and then a global prior

## Results
- **Six self-built AO tasks, 48 h wall clock each, Claude Opus 4.6 backbone** (p9-10,
  Table 2). Best held-out result on all six vs Codex (GPT-5.5) and Claude Code
  (Opus 4.6):
  - BrowseComp held-out accuracy 45.33 → **67.67** (Codex 50.00, Claude Code 53.33)
  - Math-reasoning data synthesis held-out pass-gap +19.79 pts (Codex +5.21, CC +7.29)
  - Optimizer design: 3325 → 3237.5 steps (+2.63% held-out)
- ⭐ **The dev/test gap is measured, not assumed**: on Terminal-Bench 2.0 Claude Code has
  the best dev score (75.00) but drops to 71.70 on test, while Arbor has a lower dev
  (72.22) and the best test (77.36) (p10, Table 2)
- MLE-Bench Lite (p11, Table 3): Arbor + Gemini-3-Flash 81.82% any medal (ties
  AI-Scientist on the same backbone); Arbor + GPT-5.5 **86.36% any medal, 77.27% gold,
  95.45% above median**
- Ablations on MLE-Bench Lite, Opus 4.6 (p12, Table 4): full 81.82% any medal, w/o tree
  63.64%, **w/o insight feedback 54.54%** — removing insight propagation while keeping
  the tree hurts more than removing the tree
- Transfer (p12, Fig. 3b): a BrowseComp-evolved harness, frozen, lifts HLE 25.50 → 31.50
  and DeepSearchQA 61.00 → 69.00 without further tuning
- Node statistics (p12, Table 5): e.g. Architecture Design 150 nodes, 15 dev-positive,
  **9 merged** — most dev gains never pass the gate
- Cost: 20.12M-43.19M tokens, "comparable scale to the single-trajectory baselines" (p13)

## Limitations
- ⚠ **E_test is used as a selection oracle in spite of the stated constraint.** p5 says
  decisions are made "without using E_test as an exploration oracle", but Alg. 1 line 11
  calls E_test on the best candidate of *every* cycle (default 20 cycles) and merges on
  improvement. Repeated held-out selection over 20 rounds is exactly the leakage the
  gate is meant to prevent; the reported "held-out" score is the max over ~20 test
  evaluations, not a single clean measurement
- ⚠ **Table 2 reports no variance** although §5.2 (p9) says "we run each stochastic
  method three times and report Avg@3 with standard deviation unless otherwise
  specified". The model-training test evaluators average only **two** seeds (p8)
- ⚠ MLE-Bench baselines are "adopted from the official MLE-Bench leaderboard" (p9), not
  rerun, and use different backbones (DeepSeek-R1, Gemini-3-Pro, o3, Claude-Opus-4.6).
  The headline 86.36% uses GPT-5.5 while no baseline in Table 3 does, so it is **not a
  controlled comparison**; only the Gemini-3-Flash row (81.82%, tied) is matched
- Five of the six AO tasks and their dev/test splits are constructed by the authors
  (Terminal-Bench's 36/53 split is theirs, not official, p8), so absolute numbers are
  not comparable to anything published
- Tree depth is capped at 2 with 20 coordinator cycles (p9); this is a shallow search

## Relevance
- ⭐ **REPORT.md §4 SoTA table**: the strongest verification tier of any system in this
  sweep. Planning is an explicit persistent DAG-like tree grown by a coordinator;
  checking is a **non-LLM, executable held-out evaluator** that gates artifact
  promotion. Closest counterexample to "strong at generating, weak at checking"
- Does **not** contradict the integrity-hash claim: the gate is enforced by the
  controller at runtime, criteria are supplied by the task author, nothing is hashed or
  sealed, and the same controller both explores and calls the gate
- §3.3: the hypothesis tree is a *grown* research-state tree, like InternAgent's flow
  graph, not a compiled-and-frozen plan
- The Terminal-Bench dev-vs-test inversion (p10) is a clean, citable demonstration that
  self-reported dev scores from autonomous agents systematically overstate transfer
