## What each thing is for

### `docs` repo
States its own purpose plainly: "The docs repository hosts the openJiuwen product overview documentation; the technical documentation for each SIG is stored under the `docs` directory of the corresponding repository." It holds exactly one substantive document (in two languages): "What is openJiuwen?" / "什么是openJiuwen". Everything else in the repo is a contribution-process page.

**openJiuwen's own positioning statement**, quoted from `en/Product Overview.md`:
> "As an open-source agent platform, openJiuwen is dedicated to providing flexible, powerful, and easy-to-use capabilities for AI Agent development and execution... openJiuwen also helps enterprises and individuals quickly build AI Agent systems or platforms, accelerating the adoption and large-scale deployment of commercial-grade Agentic AI technologies."

Chinese original: "openJiuwen作为开源Agent平台，致力于提供灵活、强大且易用的AI Agent开发与运行能力...并助力企业与个人快速搭建AI Agent系统或平台，推动商用级Agentic AI技术广泛应用与落地。" The two are a close, faithful mirror translation — no meaningful divergence found between EN and ZH product-overview text itself.

### `community` repo
Governance and process hub. Its own words (both README language versions, identical in substance): "Welcome to the openJiuwen community! As an open-source Agent platform, openJiuwen is dedicated to providing flexible, powerful, and easy-to-use AI Agent development and runtime capabilities." The repo is the place where CLA, code of conduct, SIG charter, licensing rules, security/vulnerability process, and (as of 2026/07) a documentation-quality governance standard live.

### Website (`openjiuwen.com`)
Tagline, identical in both languages (load-bearing, quoted verbatim):
> ZH: **"精准 · 易用 · 高效，打造生产级AI Agent"**
> EN: **"Precise · Easy-to-use · Efficient, Building Production-Grade AI Agents"**

## Goals and direction

- **Layered architecture (stated, both `docs` repo language versions, near-identical):** DeepAgents → Agent Studio → Agent Framework → Agent Distributed Runtime → Agent System Service. `Agent Framework` is explicitly said to cover "complex task planning, iterative execution, tool and skill invocation, context management, memory subsystems, multi-agent collaboration, **agent self-evolution**, and affinity-aware scheduling" (ZH: "...Agent 自演进、算力亲和调度..."). Self-evolution is stated as a *framework-level* design goal, not just a jiuwenswarm feature.
- **Repository table (`docs`/`community` READMEs) states SkillHub's *intended* function** — this is a claim about the repo, not something I verified in SkillHub's own code: "A Skill hosting and distribution platform that supports Skill publishing, version management, search and download, sharing and reuse, and private deployment." (ZH: "Skill 托管与分发平台，支持 Skill 发布、版本管理、检索下载、共享复用及私有化部署。") This is the most direct statement in this scope of an intended admission/versioning/reuse system for capabilities — but it is a one-line repo description, not a spec.
- **`agent-gateway` is explicitly not yet released**: both language versions mark it "Currently opening soon" / "当前 Opening Soon" — a stated near-term roadmap item (unified access gateway: channel management, message processing, scheduled tasks, heartbeat).
- **Documentation governance is an active, dated initiative**, not settled policy. `各仓资料体系治理规范.md` (repo documentation governance standard) has a revision log showing **first publication 2026/07** and a revision the same month. It states an explicit "current state vs. target state" distinction:
  > "有（现状）：各仓均有 README、多数仓有 docs 内容。" ("Have (current state): every repo has a README, most repos have some docs content.")
  > "齐（目标）：每仓文档标准化达标——README 结构规范完整、docs 具备高检索性..." ("Complete (target): every repo's docs meet the standard — README fully structured, docs highly searchable...")
  This is exactly the "final design vs. current implementation" distinction the brief asks to capture, applied to *documentation* rather than to code or capabilities. It names `agent-studio`'s `studio-2.0` docs as the reference template repo, and `skillhub`'s `SECURITY.md` as the reference security-policy template — both by external link, not verified by me.
- **Website introduces vocabulary not present in the local `docs`/`community` repos**: "WorkSwarm" (unified workbench), "Coordination Engineering" (see below), and a **quantified claim of "250 个 Swarm Skills" (250 Swarm Skills)** driving it. The `docs` repo's Product Overview (as of its 2026-08-04 HEAD) never mentions WorkSwarm, Coordination Engineering, or any skill count — it only describes `jiuwenswarm` generically as "A multi-agent collaboration framework and official flagship application that supports complex task collaboration and autonomous Skill evolution" (ZH: "多智能体协同框架与官方旗舰应用，支持复杂任务协作与 Skill 自演进。"). Taken together this looks like **the website is ahead of the local docs repo** — newer product/marketing framing (WorkSwarm, Coordination Engineering, a specific skill count) that the docs repo has not yet absorbed, or that lives in product marketing rather than technical documentation. Flag this as a direction-of-travel signal: whatever "WorkSwarm" and "Coordination Engineering" mean concretely, they are being pushed harder on the public site than in the engineering docs.
- **Self-evolution mechanism, as stated on the jiuwenswarm product page (web, both languages consistent)**:
  > ZH: "自动识别智能体轨迹中的异常错误，实现 Skills 自主演进"
  > EN: "Automatically identify abnormal errors in agent trajectories and enable autonomous evolution of Skills."
  Homepage (ZH) adds: "双层协同演进" (dual-layer collaborative evolution) based on "Agent执行轨迹与用户反馈信号" (agent execution trajectories and user feedback signals). **Ambiguous**: I could not determine what the two layers of "双层协同演进" are (agent-level vs. skill-level? individual vs. team-level?) — the fetched page summary did not carry enough detail, and I did not have budget to dig further. Flag as unresolved rather than guessed.
- **License/special-license review names an "incubation graduation" gate.** This is the clearest hint of a formal *module-level* maturity/admission concept found anywhere in this scope, but it appears in a licensing document, not the (empty) lifecycle document:
  > "Passing the special license review is a mandatory condition for a software module that adopts a special license to pass the code compliance check within the openJiuwen project... The special license review conclusion for that software module must serve as a mandatory condition for its **openJiuwen QA SIG exit review / incubation graduation review**."
  This implies a QA SIG "exit review" and an "incubation graduation review" exist as governance concepts for modules — but nowhere in the 43 community-repo files is either process itself defined. This is a real gap: the *gate* is referenced as a precondition-consumer, but its own criteria are not documented in this scope.

## Findings relevant to the capsule

**Capability reuse (skills, tools, plugins):**
- SkillHub is *described* (repo-table one-liner only, both `docs` and `community`) as supporting "publishing, version management, search and download, sharing and reuse, and private deployment" of Skills. No contract format, schema, or admission criteria are given anywhere in this scope.
- Website: "Swarm Skills" are framed as "团队协作流程沉淀为标准化技能包" (team collaboration workflows consolidated into standardized skill packages), with a claimed count of 250. No description of what "standardized" means structurally.
- `jiuwensymbiosis` (embodied-intelligence framework) is described, docs-repo only, as supporting "构型无关的能力复用" (configuration/embodiment-agnostic capability reuse) — a second, differently-scoped reuse concept (cross-embodiment rather than cross-agent) that the capsule design should be aware of as a *sibling* concept, not the same one.

**Contracts (declared inputs/outputs/preconditions/effects/permissions/cost):**
- No document in this scope defines a Skill/capability contract schema. The closest analog is the `openJiuwen安全设计规范` (security design guide), which sets *implementation-level* security requirements rather than a capability contract format: default-deny/least-privilege on new accounts ("系统新建账号默认不授予任何权限，或者默认只指派最小权限"), mandatory authentication on all management interfaces, no hardcoded keys, cryptographically secure randomness required, and a minimum-necessary principle for personal-data logging. Useful as "what a capability must not violate," not as "what a capability declares about itself."

**Admission and validation:**
- Code-level admission is well documented and concrete: minimum reviewer count, self-merge prohibited ("禁止合入自己创建的 Pull Request"), CI gate required before merge, PR-bot label mechanics (`/lgtm`, `/approve`, `/check-pr`, `/check-cla`) drive merge eligibility.
- Documentation-level admission is well documented (the 2026/07 governance standard + self-check checklist: README 7-section rule, Diátaxis 4-category docs rule, directory-structure rules), with an explicit rule/suggestion distinction (【规则】mandatory vs 【建议】advisory).
- Special-license admission is well documented (Compliance SIG review, PMC + legal + Compliance SIG representative required).
- **Capability/Skill admission is not documented anywhere in this scope.** The only trace is the "QA SIG exit review / incubation graduation review" phrase noted above, referenced but not defined. The jiuwenswarm self-evolution description explicitly frames Skill evolution as automatic ("自动识别...异常错误，实现 Skills 自主演进") with no stated human review step before an evolved Skill is kept. This is a genuine, load-bearing absence for the capsule design to note: openJiuwen's own public materials describe capability admission for *code* and *docs* but not, in this scope, for *skills/capabilities themselves*.

**Versioning, lineage, deprecation:**
- Repo-level: CHANGELOG.md or GitCode Release recommended (advisory, not mandatory) by the docs governance standard; no repo-wide semver policy stated.
- Capability-level: SkillHub's one-line description claims "version management" (版本管理) for Skills, but no mechanism, scheme, or deprecation policy is documented in this scope.
- **The community/release lifecycle document that would presumably state version-lifecycle policy is empty** — see Contradictions section below; this is the single most direct gap for "what does production-ready/maturity mean to openJiuwen."

**Evidence and provenance:**
- Security vulnerability handling (`社区安全漏洞治理及披露.md`) is the most evidence/provenance-like process found: it follows ISO/IEC 30111 and ISO/IEC 29147, uses CVSS 3.1 scoring into four severity tiers (Critical/High/Medium/Low), and distinguishes "LTS版本&Release版本" as the only package type with a defined vulnerability-response SLA (full fix during "active maintenance," CVSS≥7.0 fix during "passive maintenance," with SA/CVE disclosure). This is a real maturity-tier concept — but it depends on a lifecycle document (see below) that does not exist in this scope, so the terms "active/passive maintenance period" are used without being defined anywhere I could read.
- No trace of execution-trace, claim-to-evidence, or reproducibility documentation for AI-generated outputs (research-agent outputs, reports, etc.) anywhere in this scope.

**Composition (systems, not just functions):**
- The architecture description explicitly separates a "framework" layer (Agent Framework: build/orchestrate/invoke agents) from a "runtime" layer (Agent Distributed Runtime: multi-tenant isolation, elastic scaling, service discovery, cross-cluster communication) from an "OS" layer (Agent System Service: sandboxing, persistent memory, CLI, filesystem, message bus). This is a genuine claim of composing whole systems, not just functions — but again, this scope offers no schema for how a composed system's parts declare compatibility with each other.
- `agent-protocol` is named as providing "MCP SDK, A2A SDK, and A2X Registry" (both languages) — interoperability protocols for cross-agent composition — but not described further in this scope.

**Research-agent workflows (literature, hypotheses, experiments, reports):**
- `deepsearch` is the only research-agent-shaped module named in this scope: "A knowledge-augmented deep retrieval and research Agent designed for search, reasoning, and report generation scenarios" (ZH: "知识增强型深度检索与研究 Agent，面向搜索、推理和报告生成场景。"). No further detail — this scope is documentation/governance/website only, not the deepsearch repo itself.

**Stated non-goals and boundaries:**
- The single clearest non-goal statement in this entire scope, appearing verbatim and identically at the bottom of both `community/README.md` and `community/README_CN.md` (i.e., consistent across languages):
  > EN: "This product serves only as a workflow orchestration tool and does not include AI model capabilities. When connecting an AI model for a specific business scenario, users must independently bear the relevant compliance obligations, such as those under the EU AI Act."
  > ZH: "本产品仅作为流程编排工具，不包含 AI 模型能力；用户在连接 AI 模型用于特定业务场景时，需自行承担欧盟 AI 法案等相关合规义务。"
  This is a legal-positioning boundary: openJiuwen defines itself as orchestration, explicitly disclaiming that it *is* a model or provides model capability, and pushes AI-Act-style compliance liability onto the integrator. Worth keeping in mind for the capsule's own compliance/liability story.
- License-and-Copyright-Guidelines.md states its own scope boundary: "These guidelines apply only to the openJiuwen community. They do not apply to scenarios in which the openJiuwen project is used by individuals or enterprises to develop other products" — i.e., openJiuwen explicitly does not attempt to govern downstream forks/products (directly relevant to the capsule project, which is itself a downstream build on openJiuwen).
- `docs.openjiuwen.com`'s home fetch reported (web, paraphrased) "no documented capability contracts, admission processes, or validation frameworks" at that level — consistent with everything else found: openJiuwen's public materials do not claim to have a capability-contract system yet.

## Contradictions and ambiguities

1. **The lifecycle/release document is empty, and its only cross-reference points somewhere we don't have.** `community/release/openJiuwen生命周期发布公告.md` is confirmed empty except for its title (`# openJiuwen生命周期发布公告`, 36 bytes, 1 line — verified with both `wc` and a full read). But `community/contribute/社区安全漏洞治理及披露.md` links to what should be this same document at a **different repo**:
   > "版本生命周期请参考：[openJiuwen生命周期发布公告](https://gitcode.com/openJiuwen/release-management/blob/main/openJiuwen%E7%94%9F%E5%91%BD%E5%91%A8%E6%9C%9F%E5%8F%91%E5%B8%83%E5%85%AC%E5%91%8A.md)"
   That link points into a `release-management` repo, not into `community/release/`. I did not have that repo checked out locally and did not fetch it (out of the web-fetch scope given in the brief, which named the marketing site and doc/skill subdomains, not arbitrary GitCode repos). **This means the brief's flagged empty file is confirmed empty, but I cannot confirm whether the real lifecycle policy exists in `release-management` and is simply not mirrored here, or whether it too is unwritten.** This is exactly the kind of "missing lifecycle policy" the brief said would matter — recommend someone with access check `openJiuwen/release-management` directly before concluding no lifecycle policy exists at all.
2. **Governance detail lives in the Chinese-first `community` repo but the public English governance web page is an explicit stub.** `https://www.openjiuwen.com/en/about/governance` returned (web) essentially only "Content is being prepared..." while `community/coreteam/openJiuwen社区章程.md` (Chinese only, no English version exists in this repo) is a full, detailed governance charter (Board/理事会, Technical Committee/TC, SIG creation and role-promotion criteria with vote thresholds, meeting cadence, quorum rules). So: full governance content exists, but only in Chinese, in a code repo rather than the public website; an English reader following the public site's own "Governance" link finds nothing.
3. **README hyperlink inconsistency (Code of Conduct), same language, same repo.** `community/README.md` (English) links the phrase "openJiuwen Community Code of Conduct" to `./openJiuwen社区行为准则.md` — i.e., the *Chinese-titled* file — even though an English-titled twin, `openJiuwen-Community-Code-of-Conduct.md`, also exists in the same directory with equivalent (translated) content. Not a broken link, but an odd routing choice worth flagging as a minor documentation inconsistency.
4. **Dual code-hosting split by language, applied consistently.** `docs/README.md` (English) and every English-facing repo table (`docs` repo and `community/README.md`) point to `github.com/openJiuwen-ai/...` URLs. `docs/README_zh.md` and `community/README_CN.md` point to the same repos on `gitcode.com/openJiuwen/...` instead. This is systematic, not a one-off typo — English audience is routed to GitHub, Chinese audience to GitCode, for identical repos. Worth knowing if the capsule project needs to reference openJiuwen repos: the two mirrors may drift.
5. **Code-of-Conduct template placeholders left unfilled, identically in both languages.** Both `openJiuwen-Community-Code-of-Conduct.md` (EN) and `openJiuwen社区行为准则.md` (ZH) — which are Contributor Covenant v3.0 derivatives — contain a literal unfilled template instruction:
   > EN: "To report a possible violation, **[Note: Please fill in the reporting method here]**."
   > ZH: "要报告可能的违规行为，**[注意：请在此填入举报方式]**。"
   and further down:
   > EN: "**[Note: The handling measures and remedies listed below are suggestions... If your community already has established enforcement procedures, please ensure that you modify this section to describe your own policies.]**"
   Both documents *do* give a general contact email earlier ("发送邮件至[社区委员会](contact@openjiuwen.com)处理"), so this isn't a total absence of a reporting channel — but the Covenant template's own instruction to the document's author has not been executed. This is a real signal about document maturity/rigor in the governance repo, consistent across both languages (so not an EN/ZH divergence, but a genuine unfinished-template finding).
6. **Privacy policy has two different "last updated" dates in the same document.** `community/privacy/openJiuwen隐私申明.md` states near the top "更新时间：2026年2月28日" (update time: 2026-02-28) and at the very bottom "最近更新时间：2025年11月25日" (most recent update: 2025-11-25) alongside "隐私政策版本：v20260228". The header date is later than the footer date, which is internally inconsistent — most plausibly a template/versioning bug (the version string encodes the header date but the footer wasn't updated to match), but I can't rule out that these mean two different things (e.g., "update time" of this text vs. "last reviewed" date). Flagged as ambiguous rather than resolved.
7. **Two English/Chinese-authority conventions coexist and point opposite directions.** The docs-governance standard mandates Chinese as the authoritative source for documentation content ("中文为权威源，英文跟随" — Chinese is the authoritative source, English follows), but the contribution guide mandates commit messages be written in English ("提交信息采用英文格式"). Not a contradiction exactly, but worth noting: process artifacts (commits) are English-first while content artifacts (docs) are Chinese-first.
8. **"Governance" content quality gap between repo and web is the opposite of the "SkillHub" content quality gap.** The community repo has rich governance text but the sigs/README.md is a bare stub (`# sigs`, one line) despite the charter describing a full SIG creation and lifecycle process — i.e., the *process for creating SIGs* is documented, but the *actual current roster of SIGs* is not published anywhere I could read (not in `sigs/README.md`, not confirmed on the website — the `contribute` pages mention a "SIG Center" but content there wasn't retrievable). Cannot determine how many SIGs currently exist or what they are.
