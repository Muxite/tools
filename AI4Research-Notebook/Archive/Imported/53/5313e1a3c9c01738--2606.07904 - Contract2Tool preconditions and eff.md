# 2606.07904 · Contract2Tool: Learning Preconditions and Effects for Reliable Tool-Augmented LLM Agents

Suresh Babu, Ganesh Iyer (independent) · arXiv Jun 2026 · 10 pp (9 body)
Read: p1-9 fully (method, benchmark design, setup, all result tables)

## Summary
The missing half of every "typed agent contract" proposal: contracts have to come from
somewhere. A tool schema says *how* to call a tool, never *when* it is causally appropriate
or *what task state it produces*. Contract2Tool infers a symbolic contract
c_i = (R_i requires, E_i produces, ρ_i risk, k_i cost) per tool from whatever evidence
exists — name, description, schema, docs, execution traces — normalises it into a canonical
state-variable vocabulary, and feeds it to causal multi-step tool filtering (CMTF).

## How it works (p3-5)
- Six evidence conditions of increasing richness: Name → Metadata → Schema → Documentation →
  Traces → **Hybrid** (docs + traces) (p4)
- A trace is (s_before, tool, args, status, obs, s_after); **successful traces reveal
  produced state variables through before/after state diffs**, failed traces would suggest
  missing preconditions (p4, Fig. 2 p5)
- Normalisation/validation layer maps surface forms ("event identifier") to canonical state
  variables, drops duplicates, rejects malformed output — necessary because downstream
  causal filtering matches on exact symbolic variables (p4)
- Three evaluation layers, deliberately separated: intrinsic (vs gold contracts),
  **filter-oracle** (does the learned contract expose the gold next tool at each gold
  decision step?), and downstream agent performance (p4-5)
- The key mechanism claim: docs describe a *human-facing* output ("a list of search
  results") while the next tool needs a *specific state variable* (an event identifier) —
  only traces expose that (p7)

## Results (p7-8)
- Intrinsic by evidence (Table III, p7): Requires-F1 0.77 (name) → 0.99 (schema) → **1.00**
  (documentation); Produces-F1 goes the *other* way, 0.86 → 0.80 → 0.77; exact contract
  match never exceeds 0.54
- Hybrid evidence, best generator (Claude Opus 4.8): **1.00 Requires-F1, 0.98 Produces-F1,
  0.77 exact match**; Sonnet 4.6 1.00 / 0.99 / 0.74 (p7)
- Filter-oracle over **283 gold decision steps** (Table IV, p8): docs- and schema-derived
  contracts expose the gold next tool **84.1%** of the time and leave no visible tool 7.8%
  of the time; trace and hybrid contracts reach **1.000 gold exposure, 0.000 no-visible,
  1.000 visible tools, 0.000 extra** — identical to gold contracts. Llama 3.3 docs: 0.604
- Downstream over 102 multi-step tasks, aggregated over four models (Table V, p8):

| Method | Success | Wrong tools | Premature | Tools/step | Tokens |
|---|---|---|---|---|---|
| All tools | 0.775 | 1.461 | 0.027 | 100.0 | 26,172 |
| Keyword top-5 | 0.620 | 2.265 | 0.032 | 5.0 | 4,482 |
| State-aware | 0.620 | 2.196 | 0.000 | 5.733 | 4,648 |
| Gold CMTF | 0.990 | 0.010 | 0.000 | 1.000 | 2,532 |
| **Learned CMTF** | **0.980** | 0.020 | 0.000 | 1.000 | **2,528** |

- So learned contracts retain 0.980 of gold's 0.990 while cutting visible tools 100 → 1 and
  tokens 26,172 → 2,528 (**10.4×**) against all-tools exposure (p1, p8)

## Limitations
- ⚠ **The registry is 100 synthetic tools with author-written gold contracts** and 102
  author-written tasks (Table I, p6). Every number is measured inside a world whose causal
  structure the authors defined, against contracts they defined
- ⚠ CMTF exposes **exactly one tool per step** at 1.000 gold exposure. At that point the
  contract graph is doing the planning and the LLM is executing a forced move. "0.980 vs
  0.775" is therefore mostly a measurement of how much damage 99 distractor tools do, not of
  contract quality. The distractors were designed to be confusable (p5)
- ⚠ Traces are drawn from **gold successful trajectories** in the same benchmark (p4, p6),
  so the trace evidence is a partial leak of the gold contract. This is exactly why trace and
  hybrid hit 1.000 on the filter oracle while docs stall at 0.841
- Failed traces — the only evidence source for *preconditions* — are described but not used
  (p4, p6)
- Llama 3.3 70B is excluded from the main aggregate for tool-call compatibility failures
  (p8); the aggregate is over four models
- Exact contract match is at best 0.77 even with hybrid evidence, i.e. roughly one in four
  learned contracts is wrong somewhere and the pipeline survives anyway

## Relevance
- REPORT.md §3.1-3.2: this is the **acquisition story** for the typed contract layer.
  AI4Research's frozen contract assumes preconditions and postconditions exist; this is the
  only paper in the sweep that measures how well they can be inferred, and the answer is
  "well enough to filter, not well enough to trust" (0.77 exact match)
- Its strongest transferable finding is negative and mechanism-level: richer *documentation*
  monotonically improves precondition recovery but **degrades effect recovery**
  (Produces-F1 0.86 → 0.77, Table III p7). Documentation describes outputs for humans;
  only execution traces name the state variable the next step consumes
- Cross-reference SkillWeaver (2504.07079) and SkillDAG (2606.03056): same
  precondition/effect vocabulary, but this paper measures contract accuracy against a gold
  set rather than assuming it
