## What Capability Capsule is (settled by the supervisor; do not change)

- It is a **schema layer**, "a scheme, not a tool": a shared contract every capability declares, applied by a
  capsule layer's code. "CC and verifier are in different layers. CC is more of a scheme, and verifier is a tool. CC can
  use tools, but CC is not a tool." (supervisor, 2026-09-21)
- It sits in **AI4Research**, a research pipeline being rebuilt on **openJiuwen**: the agent runtime **agent-core**, with
  **Symphony** (capability discovery and planning) inside it. The old AI4Research code is being discarded, but its
  pipeline theory is kept: intake, intent, requirement compilation, planning, **freeze**, scheduling, dispatch,
  operators with in-run gates, delivery of claims. One pass is a run, called a sprint.
- Neighbouring teams: **RSI** (recursive self-improvement; builds and improves capabilities; Saurav), **verification**
  (capability- and system-level checks at each sprint; Ramika), **routing** (picks models only, never capsules;
  Xiaoyang). Capsules change code, prompts and manifests, never model weights. AI4Research itself is not a capsule.
  agent-core may be changed only where necessary.
- The supervisor's own slides and answers are transcribed in `tundle/ai4research/notes/45-*.md` and `46-*.md`. Read both.
- The supervisor said: don't worry about time or pages; quality, logic and flow decide length.

## What Muk wants this report to do

1. **Lead with the schema**: what it is, on one screen, before anything else. Then define every term before it is
   used. A reader going top to bottom must never meet an undefined name.
2. **Explain why the schema looks the way it does, paper by paper.** Each paper motivates a *tool* the new system
   needs (an admission gate, an executability filter, a verifier audit, a librarian, a composition screener, a
   gap-driven builder...). Each tool needs certain facts about a capability, and those facts are the fields. Muk wants
   to talk at length about each paper, because this shows why each field exists and, in doing so, the dependencies and
   impacts the schema has on every team. Decide where this belongs in the report and say why.
3. **Argue for a declarative design over an observational one**, and make every section support that argument:
   declaring what a capability needs, guarantees and changes, and checking it before use, rather than judging
   capabilities by watching outcomes afterwards. Be honest about the limits of declaration.
4. **Compare and contrast with what exists**, especially:
   - **Symphony's fingerprint versus a manifest.** Symphony derives a fingerprint for each capability from its
     inventory (descriptor, content hash, typed inputs and outputs, semantic profile, quality and failures gathered
     from use). Read it in source and contrast derived-from-observation with declared-and-tested.
   - **Skills** (`SKILL.md` folders in jiuwenswarm and skillhub; skillhub's per-version review), **MCP** tool listings
     and **A2A** agent cards, agent-core's **ToolCard**, and ScienceDiscovery's versioned skill library.
   - Say plainly whether a capsule is a skill, contains one, or overlaps with one.
5. **Show integration**: how the design fits agent-core and Symphony, how **RSI** fits with it (what it gives RSI, what
   it asks of RSI), what it **demands of verification**, and what routing gets. The message: the schema helps every
   team do better. Show it, don't assert it.
6. **Cover the requirements a to g** (the assignment): a) function: what it does and why; b) architecture: how it is
   built; c) position: where it sits in the AI4Research workflow and in openJiuwen; d) dependencies; e) similar
   designs; f) advantages; g) feasibility. For (g), keep it short: the parts exist somewhere, and ownership is for the
   teams to decide together, because the capsule touches every team.
7. **Include:**
   - one **worked example end to end** for one realistic AI4Research capability (its manifest, how it is admitted,
     how it is offered and bound in a run, what the run records, what happens when it is revised or revoked);
   - **the ownership picture**: the loops (building, admitting, using) and who owns each;
   - **composites and their ceiling**; which **pipeline stages** could become capsules later and which must not;
   - **what CC deliberately does not do** for RSI, verification and routing;
   - **spatiotemporal composability** (Cordis, 2608.25512): capsules must be addable, replaceable, revertible and
     removable without breaking dependents; state how the schema supports this and where it cannot;
   - **composition screening**: capsules are not certified as safe together; show how the schema supplies what a
     screener such as SkillFuzz (2607.02345) reads, and how its findings are recorded and used;
   - **what the schema does not claim**.
8. **Diagrams lead where a mechanism can be drawn.** You cannot draw images; instead, for each diagram write a precise
   figure specification in a fenced block marked `figure-spec` (boxes, arrows, labels, which are code and which are
   model calls), so it can be drawn afterwards. Every box and arrow must be supported by the text.
9. **End with a topic register**: a table of every topic the report covers, where it is, and any topic you considered
   and left out, with why.

**Facts already verified in source** (use them, and re-check any you rely on):
- AI4Research's planner selects capsules in three steps: a code filter on types, effects and proof classes
  (`elastic_planner.py:4553-4648`), a model that binds each plan step (`:4678-4724`), and a separate fit review
  (`:5685`), with one repair at most (`:4934`, `:4949`). The filter never reads preconditions; dispatch checks four
  fixed precondition kinds against the task envelope (`capability_capsules.py:1220-1242`). The binding prompt carries
  every eligible capsule's full catalog row; excluded capsules appear as short exclusion rows (`:4600-4650`). The
  freeze admits only `stable` capsules (`execution_authority.py:55-56`) and rejects capsules changed during planning
  (`:81-94`).
- Symphony: `CapabilityProvider` (`symphony/interfaces/capability.py:13`) feeds its fingerprint service and graph;
  batch graph mutation needs `AtomicCapabilityProvider` (`orchestration/mutations.py:167`) and a model for ontology
  matching (`orchestration/mutation_service.py:129`). The graph accepts only skill, subagent and agent capabilities
  (`orchestration/graph/build.py:161`) and proposes `can_feed` edges at confidence 0.7 (`:122`). The fast planner reads
  each candidate's id, name and description and leaves I/O compatibility until after the plan
  (`orchestration/planning/fast.py:32-44`). `SkillGraphUpdater` adds, updates and deletes skills
  (`interfaces/graph.py:14`).
- agent-core: the binder loads tools, MCP servers, skills and subagents by name, raises if a name is already bound, and
  checks no hash (`harness/extension_binder.py:27-60`); hot apply and unapply undo registrations in reverse order.
  `before_tool_call` observes tool calls (`harness/observability/rail.py:888`), not what code does inside. Load records
  live in memory (`harness/deep_agent.py:314`); `TrajectoryStore` is written by the trajectory rail. `ToolCard` has
  four flags: exposure, parallel_safe, stateless, idempotent (`core/foundation/tool/base.py:83-118`).
