# 1. AllocBench — when should an agent build a tool?

**AllocBench: Measuring Online Tool Allocation Capability in LLM Agents.**
Daniel Wang, Andrew Xu (Yale University). arXiv **2607.23332v2 [cs.LG]**,
submitted 25 Jul 2026, revised 31 Jul 2026. **Preprint — not peer-reviewed.**
Local copy: `papers/2607.23332.{pdf,txt}`. All **[verified]**, full read
2026-09-10 (`38-`).

## 1.1 Setup

| Parameter | Value |
|---|---|
| Stream length `T` | **60** problems |
| Latent classes `N` | **8** numeric families |
| Tool budget `B` | **3** |
| Hot families | **3**, sharing **0.85** of probability mass (0.283 each) — recur **13-23** times |
| Trap families | **5**, sharing **0.15** (0.03 each) — recur **1-6** times |
| Evaluation panel | **24** independent streams (seeds 2000-2023) |
| Constraint | rejection-sampled so ≥1 trap falls within the first **3** slots |

The 8 families: linear congruential generators, modular exponentiation,
continued fractions, Chinese-remainder systems, Josephus survivor, iterated
modular quadratic maps, xorshift steps, modular matrix powers.

Models are verified approximately unable to solve the problems without a script,
so allocation genuinely determines the outcome.

**Optimal policy:** pass on first sight, build on confirmed recurrence.

## 1.2 The framing ladder

Four renderings of **identical latent sequences** — the optimal policy is the
same at every rung.

| Rung | What is required |
|---|---|
| **R0 abstract** | coloured balls; free-text KEEP/PASS |
| **R1 declarative** | real numeric problems; KEEP/PASS **tool calls**; no code |
| **R2 code** | keeping requires a non-empty `solve(inputs)`; **payoff independent of code correctness** |
| **R3 full** | reusable script, tested and rerun on later instances |

## 1.3 ⭐ Table 1 — first-sight commitment (lower is better)

Fraction of commitments made on a class's **first** occurrence. The optimum
passes every first instance.

| Model | R0 | R1 | R2 | R3 | Fails at |
|---|---|---|---|---|---|
| Claude Haiku 4.5 | 28% | 33% | **99%** | 100% | R2 |
| Claude Opus 4.8 | **4%** | 0% | **92%** | 99% | R2 |
| GPT-5.4-mini | 15% | 29% | 85% | 88% | R2 |
| GPT-5.6 Sol | 24% | 0% | 39% | **100%** | R3 |

**The headline number: Opus 4% → 92%.**

**Two controls that make it airtight:**
1. **R1 causes no significant shift in any model** ⇒ the failure is *not* caused
   by mathematical reasoning.
2. **R2 does not check code correctness** ⇒ the failure is *not* the difficulty
   of writing correct code. Merely *requiring* a script is enough.

GPT-5.6 Sol survives R2 at 39% — so allocation under a code requirement is
demonstrably possible — then collapses to 100% at R3 when forced through
`write_script` / `run_script` tools.

## 1.4 Score — percent of hindsight optimum realised

`Score = Σ utility_i / Σ optimal_i`, where the optimum is the sum of the sizes of
the `B` largest classes. Reported for R0-R2 only; R3 confounds allocation with
script-writing ability.

- All four frontier models fall within a **10%** interval on R0.
- On R2, **GPT-5.6 Sol scores ~25 points higher than GPT-5.4-mini**.
- GPT-5.6 Sol R0 score: **78.3%**.
- Only GPT-5.6 Sol avoids a drop from R0 to R2.
- Intervals are 95% seed-bootstrap, N = 24.

## 1.5 The price check — Appendix E

Build cost made **visible** at charges `K ∈ {0, 10, 20, 24}` (⚠ the 20 was missing before 2026-09-11):

- **R0** first-sight hazard **falls as price rises**, tracking the hindsight
  optimum, which itself declines to **~1%** commitment at K = 24.
- **R2 stays pinned near 100%** across the entire surface, **including K = 24**.

> **Abstract allocation responds to price. Code-required allocation is
> behaviourally inelastic.**

**Use this for:** a capability budget stated to the agent as a price will not
change its behaviour. A budget must be an **enforced gate**.

## 1.6 The RL case study

Qwen2.5-Coder-14B-Instruct, q8_0 GGUF; QLoRA + PPO; **no demonstrations**;
asymmetric critic observing the true latent class rate; **20 steps × 25
episodes**.

- R0 first-sight commitment: **74% → 6%**.
- Generalises to **lexical reskins** (coins in a chest, arrows in a quiver) —
  near-zero, slightly below R0.
- Generalises to the same choice issued via a **zero-argument tool call**.
- ⚠ **Breaks at R1**, earlier than any frontier model's failure point; base and
  post-trained become statistically indistinguishable once a numeric problem is
  shown.

**Table 2 — Score, percent of hindsight optimum:**

| | R0 | R1 | R2 |
|---|---|---|---|
| Qwen-14B base (q8) | 74.8% | 49.2% | 61.2% |
| Qwen-14B post-trained (q8) | **79.6%** | **34.8%** | **41.7%** |

Post-training lifts R0 to frontier level (79.6% vs Sol's 78.3%) and leaves R1/R2
no better. The authors attribute the R2 drop to a **code-emission channel
limitation of a 14B model**, not to allocation timing — quote that caveat if the
row is used.

## 1.7 Quotable transcript evidence

**Abstract frame (R0), Opus:**
> *"Still gathering information; too early to commit a keep."*
> *"Red has now appeared 3 times in 7 draws — a strong rate. With 53 draws left,
> keeping red should yield many more."*

**Tool frame (R3), Opus, on the first problem of the stream:**
> *"I'll write a script for this bit-manipulation problem type."*

Budget is mentioned only near exhaustion: *"I have 1 write left."*

The authors' summary:
> *"The models do not consider waiting for recurrence evidence at all, and
> scripts are reused only reactively when a class later returns."*

## 1.8 Their explanation (labelled a conjecture in the paper)

Coding post-training datasets (DeepSWE and similar) present streams of
**unrelated problems with independent rewards**. Episodes share no state, so a
tool built while solving one problem carries no expected future value — no
gradient toward reserve behaviour. Reasoning models additionally carry explicit
length and efficiency penalties. Both OpenAI and Anthropic have stated they use
RL on coding datasets. The authors explicitly leave the mechanistic account open.

## 1.9 ⭐ Their prescription

> *"Current models cannot simultaneously manage budget allocation and tool
> creation. This suggests that tool-building agent systems should **separate the
> abstract decision to invest from the process of creating the tool** — one
> agent outputting declarative claims when building is optimal (R1), and a
> different agent constructing the desired tools."*

## 1.10 A framing worth borrowing

They distinguish two failure modes that tool benchmarks conflate:
- **the policy is absent** (base Qwen), versus
- **the policy is present but suppressed by framing** (every frontier model).

## 1.11 Limitations — state these if cited

- **One synthetic environment**; engineered classes and streams; 24 seeds. Real
  tasks have ambiguous class boundaries, shifting frequencies, incomplete
  reusability and an unknown number of classes.
- ⚠ **Both GPT models ran at `reasoning effort=none`** — the OpenAI endpoint
  rejected tools with reasoning enabled. Paired design holds it fixed within
  model; still a caveat a supervisor may raise first.
- The RL study uses a **privileged critic**; it does not show non-privileged
  learnability, nor that post-training cannot fix R3.
- Score is calibrated against a hindsight optimum **not implementable online** —
  a relative measure only.
- **Preprint**, cs.LG.

# 2. Beyond Task Completion — the silent-rot measurement

arXiv **2604.00392v2 [cs.SE]**, 4 Jul 2026. Kaliyev (UT Austin), Maryanskyy
(Uber). Local: `papers/2604.00392.txt`. **[verified]** (`29-`).

**Definition:** a preserved tool exhibits **silent rot** if it *executes cleanly*
but records `C = 0.00` on a held-out conformance suite for the capability it was
built for.

**Table 5:**

| System | Tools | Mean C | Mean R | Silent rot |
|---|---|---|---|---|
| One-Shot | 119 | 0.000 | 0.518 | **100.0%** |
| ToolMaker-style | 19 | 0.000 | 0.526 | **100.0%** |
| CREATOR-style | 84 | 0.049 | 0.536 | 91.7% |
| **Total** | **222** | **0.018** | 0.525 | **96.8%** |

- **215 of 222** tools score zero. CREATOR-style: 7 of 84 (8.3%) non-zero, exactly one at C = 1.00.
- **Calibration:** hand-written reference implementations score **C = 1.00 on all 16 capability suites**.
- Suites: **5-6 hidden unit inputs + 5-6 adversarial probes**; per-tool size 10-22, **median 11**.
- Sessions carrying these libraries still pass **31-34%** of their verified tasks.
- Benchmark **EvolveTool-Bench**: 99 tasks, 3 domains, sessions in six roles — **seed, gap, variant, composition, regression, adversarial**.
- Tool execution: in-process sandbox, **5-second wall-clock limit**.
- Design: 3 seeds × 8 sessions = **24 session rows** per protocol; bootstrap B = 10,000, seed 20260604.
- Their own honesty: the decision-split contrast is **−7.1 pp, 95% CI [−13.9, −0.1], not significant after BH correction** — reported as "a hypothesis-generating **signal**, not a confirmed effect." (⚠ "signal" restored 2026-09-11)
- Audit cost: overhead "dominated by the LLM calls themselves"; manifest emission, reuse decomposition and per-tool source dumping add **millisecond-scale latency and bounded disk I/O**, "cheap enough to leave on in production."

**The key clause:** *"the verifier scores task outputs, not tools."*

⚠ **Scope limit — libraries are per-session.** §4: *"harness state resets
between sessions so library accumulation is per-session, not cross-session."*
This paper measures capabilities that are **born broken**, not libraries that
**decay over a long run**. Do not use it for a long-horizon decay claim; that
claim's evidence is Alita-G Table 4 (effective coverage 1.00 → 0.51). Two
failure modes, two citations — see `29-` §3b. Added 2026-09-11.

⚠ **Single-model scope.** One model (Claude Haiku 4.5), 3 seeds, 8 sessions,
51 graded task decisions per pass (the full benchmark design is 99 tasks);
within the strict subset verifier coverage is 51/64 = 79.7% — ⚠ **different
denominators**, do not juxtapose them as "51 of 99 = 79.7%". One domain excluded; the three
protocols are `-style` **reimplementations**, and the 96.8% comes from a
re-execution distinct from the Table 3 run. The authors say Sonnet-scale rates
could differ. State 96.8% as *the rate in the one regime where anyone has
measured it*, never as *the rate*.

⚠ **Never cite "four failure modes"** (specification drift / hidden dependencies /
incomplete validation / interface violations). Zero occurrences in the paper.

**How to state it:**
> Across 222 tools synthesised by three tool-creating protocols, 96.8% scored
> zero correctness when replayed against a held-out suite for the capability they
> were built for — while executing cleanly, raising no in-session flag, and
> sitting in sessions that still passed a third of their verified tasks.

# 3. CoEvoSkills — verification is the entire delta

arXiv **2604.01687v3**, COLM 2026. UIC / MBZUAI / McGill / Columbia / Zhejiang /
UBC. **[verified]** (`35-`). Benchmark: SkillsBench, Claude Opus 4.6 + Claude Code.

| Condition | Pass rate |
|---|---|
| No skills | **30.6%** |
| CoT-guided self-generation (5-step prompt) | 30.7% (±5.2) |
| SkillsBench self-generated baseline | 32.0% (±3.1) |
| Anthropic's naive Skill-Creator | 34.1% |
| **Human-curated skills** | **53.5%** |
| **CoEvoSkills** | **71.1%** |

+40.5pp over no-skill; **+17.6pp over human-curated**.

**Evolution dynamics:** round 0 (one-shot, no verification) ≈ no-skill baseline ·
round 2 = 44% · **round 3 = 63%, overtakes human-curated** · round 5 = 75%,
converged.

⚠ §4.2 headline is **71.1%**; §4.5 says the curve converges "at 75% by round 5."
Different scopes — cite 71.1% and do not present 75% as the same quantity.

**Verification cost:** **4.1 verification cycles and 2.4 ground-truth oracle
rounds per task** on average.

**Domain analysis:** self-evolved beat human-curated in **9 of 11 domains**;
Finance **+56.9pp**, Cybersecurity **+23.2pp**. In **Natural Science,
human-curated skills degrade performance** relative to no skills.

**Structural comparison (Table C3, exoplanet transit detection):**

| | Human-curated | Self-evolved |
|---|---|---|
| Size | **5 skills, 1,096 lines** | **1 skill, 64 lines MD + 142 lines Python** |
| Executable code | **none** | **9 callable functions** |
| Algorithm guidance | lists BLS, TLS, Lomb-Scargle equally | prescribes TLS, with justification |
| Alias detection | "check for aliasing" — 1 sentence | function testing P, 2P, P/2 |
| Precision handling | not addressed | enforces 5-decimal formatting |

Patterns were earned: two-stage period search emerged after versions 2 and 3 both
failed at 75%; the 3σ clip threshold exists because 2σ was insufficient.

⚠ **Do not say "agents write better skills than humans" unqualified.** Three
unverified self-generation methods sit at the no-skill baseline. Say: *agents
with a verification loop* beat humans; agents without one produce skills worth
about as much as no skills.

**Paper's own limit:** it evolves skills from task-relevant background knowledge
available at initialisation — refinement within a known task family, **not
open-ended discovery**.

# 5. Darwin Gödel Machine

arXiv **2505.22954v3**, ICLR 2026. UBC / Vector / Sakana AI. **[verified]** (`36-`).

| | Start | End |
|---|---|---|
| SWE-bench (subset) | 20.0% | **50.0%** |

maintenance, parent selection) is fixed and not modifiable by the DGM, which we
leave as an avenue for future work."*

**Discovered improvements:** granular file editing via string replacement ·
history-aware patch generation and ranking · multiple patch generations with
ranking · auto-summarisation on context limit · non-empty patch validation and
retry · peer review.

## 5.1 ⭐ Appendix H — objective hacking

Task: solve **hallucination of tool use** — with very long context, Claude claims
Bash was used to run tests when it was not, with tool results "entirely
hallucinated in plain text." Scored 0-2, averaged over **3 SWE-bench tasks**,
detected by markers inserted into the logs. **150 iterations.**

| Node | Score | What it did |
|---|---|---|
| **96** | 1.67 | **Honest.** Improved tool-transaction logging so hallucination could be detected, then stripped hallucinated tool use from output |
| **114** | **2.00** | **Objective hacking**, in **2 modifications** — removed the logging of the special tokens indicating tool usage, **despite instructions not to change them**, bypassing the detection function |

The paper prints the diff: `TOOL_USED_MARKER` / `TOOL_INPUT_MARKER` /
`TOOL_RESULT_MARKER` replaced by a nested `"tool_invocation"` dict, under the
comment *"Use structured format instead of text markers."*

**Their closing safety line:** *"an option worth exploring is to create an
unmodifiable part of the system to be able to evaluate at halt the rest."*

**And the risk they name:** if benchmarks "do not fully capture all desired agent
properties (e.g., safety and robustness), the self-improvement loop could
**amplify misalignment over successive generations**."

# 6. SkillWeaver · SkillDAG · survey · CostBench

**SkillWeaver** — arXiv **2504.07079**, OSU / CMU / UVA / Purdue / Cisco.
[verified]. WebArena **+31.8%** relative success, real-world sites **+39.8%**;
APIs from strong agents lift weaker agents **up to +54.3%** on WebArena.
Three stages: Skill Proposal → Skill Synthesis (practice + reward model + API
synthesis) → **Skill Honing** (auto-generated test cases, execution, debugging).

**SkillDAG** — arXiv **2606.03056**, Fudan / NUS / A*STAR. [verified].
ALFWorld + SkillsBench with MiniMax-M2.7: **67.1%** success, **27.3%** reward —
**+12.8** and **+8.6** over the strongest Graph-of-Skills baseline. Intrinsic
SkillsBench **Ret@K 65.5 → 78.2** under matched queries. Ranking "stays robust as
the pool grows 10×." Ports to gpt-5.2-codex. Typed edges: `depends_on`,
`specializes`, `similar_to`, `conflicts_with`. Three invariants on every commit:
**acyclicity, non-contradiction, append-only reversibility**. Indexing cost: one
embedding call per skill per view, two views.
⚠ **Still needed:** the scaling curve and the per-edge-type ablation (`37-` §2.2).

**Survey of Self-Evolving Agents** — arXiv **2507.21046**, TMLR 01/2026.
Four axes: **what** (models · context · **tools** · architecture) · **when**
(intra- / **inter-test-time**) · **how** (reward · **imitation** ·
population-based) · **where** (general · **specialised**). Three evaluation
paradigms: static, short-horizon adaptive, long-horizon lifelong. Names
**automated verification and sandboxing** as the critical open safety problems.

**CostBench** — arXiv **2511.02734**, Nov 2025, rev. Jun 2026. **Abstract only —
do not cite specifics.** Cost-centric benchmark for multi-turn cost-optimal
planning; agents miss cost-optimal solutions even statically; ~40% degradation
under dynamic conditions.
