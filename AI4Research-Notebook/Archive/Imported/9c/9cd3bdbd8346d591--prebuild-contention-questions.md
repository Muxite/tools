# Pre-build GPU contention questions and minimal experiments

AI4Research is not yet built. These are proposed experiments to choose its first useful resource model, not completed measurements or requirements. Keep the first pass to one fully identified target machine and a few representative tasks. Preserve task inputs, software/backend versions, engine path, power/clock state, and cold/warm condition. Repeat paired conditions in alternating order; report distributions, not only averages.

## Recommended minimum contrasts

| Contrast | Decision it resolves | Keep it controlled / caveat |
|---|---|---|
| **Same model and request mix: one process with batching vs multiple independent processes.** First compare processes without MPS, then with MPS if supported. Measure throughput, per-request latency/tail, memory, GPU overlap/context activity, and total work. | Is the gain from batching/shared model state, from MPS enabling overlap and reducing context switching, or from both? Does the planner need to recommend one process, concurrent processes, or a specific execution mode? | Batching changes kernel shape and amortizes launch/weight costs; MPS changes scheduling/context sharing. This is not a pure concurrency comparison, so keep total requests, model, precision, and target latency fixed, and report the two mechanisms as separate factors. NVIDIA documents MPS overlap and reduced context-switching, but this is device/software-specific. [MPS guide](https://docs.nvidia.com/deploy/mps/latest/index.html), [MPS overview](https://docs.nvidia.com/deploy/pdf/CUDA_Multi_Process_Service_Overview.pdf). |
| **For each representative task: solo baseline, then one deliberately contrasting co-runner.** Use compute-heavy vs memory-traffic-heavy GPU work; add one CPU-heavy task while GPU work runs. Record both tasks’ slowdown/latency and resource signals, not aggregate utilization alone. | Does task history predict resource *demand* when alone, and does it predict *sensitivity* and *impact* under contention? Is interference asymmetric? Which shared resource is a candidate cause? | Start with one pair and both solo baselines. A stressor establishes a controlled perturbation, not proof of a unique bottleneck. Orion shows per-kernel compute/memory profiles can reveal complementary phases; SoCC’25 shows SM partitioning still leaves shared cache and memory paths. [Orion](https://anakli.inf.ethz.ch/papers/orion_eurosys24.pdf), [SoCC’25 interference study](https://anakli.inf.ethz.ch/papers/gpu_interference_socc25.pdf). |
| **One task with a small input/batch-size change and distinct phases preserved.** For LLM inference, separate prompt/prefill from token decode. For speech/video, split CPU preprocessing, accelerator work, and postprocessing where observable. | Are profiles stable enough to key on task identity, or must input size, phase, and backend be features? Can short history predict the next phase’s pressure? | Avoid one whole-run average: Orion measures bursty compute and memory phases, and its DNN results do not establish transfer to all tasks or GPUs. Record phase boundaries with low-overhead tracing first. |
| **Cold launch/model load vs warm process/model; separately measure first-result latency and steady-state service.** If useful, separate disk-cold, OS-cache-warm, host-RAM-resident, and device-resident states. | Is apparent “GPU pressure” actually startup, compilation, model loading, or steady-state GPU execution? Should the future planner model readiness/cache state separately from resource contention? | Do not combine this with the concurrency experiment initially. Keep backend and request identical; distinguish model/context creation from first inference and steady-state requests. |
| **CPU-heavy speech or video with explicit backend contrast: CPU fallback vs GPU path; for video, decode-only, encode-only, then one end-to-end transcode.** Observe CPU, GPU compute, copy/data movement, and codec-engine activity if exposed. | Does the process consume CUDA SMs, fixed-function media hardware, shared memory/bandwidth, or mostly CPU? Does the selected backend change the resource vector enough to change placement/simulation? | Verify the actual runtime path: “GPU accelerated” does not imply CUDA kernels, and unsupported codec/format can silently select a CPU path. NVENC/NVDEC can be distinct engines while frame buffers and transfers still share system resources. [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html) notes other GPU engines, including copy and video engines, can access shared resources during profiling. |

## Answers to the design questions

**Do process-sharing mechanisms alter overlap? Yes.** Separate CUDA processes commonly use distinct contexts; MPS provides a shared server path that can permit kernel/memcpy overlap and reduce context-switching. Same-process batching is a third condition: it changes the workload itself through larger batches and shared model/runtime state. Therefore compare these modes explicitly; a process-count sweep alone cannot identify the mechanism. Treat MIG/SM partitioning as a later contrast only if the target hardware and intended deployment support it. CUDA context and MPS behavior is documented in NVIDIA’s [Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html?highlight=local+memory) and [MPS documentation](https://docs.nvidia.com/deploy/mps/latest/index.html). Actual overlap is not guaranteed by the API or by nominally separate streams/contexts; inspect the timeline on the target stack.

**Can low measured memory bandwidth still mean memory is the bottleneck? Yes.** Low aggregate DRAM bandwidth does not rule out long dependent-load latency, cache/TLB misses, cache-set or L2 contention, insufficient memory-level parallelism, or queue/translation pressure. A task can wait on a few serial cache misses without generating enough concurrent traffic to saturate DRAM. Use time/throughput plus cache hit/miss, memory-stall/long-scoreboard, outstanding-request/bytes-in-flight, and L2/DRAM metrics where available. NVIDIA’s [Compute Triage Guide](https://docs.nvidia.com/nsight-compute/ComputeTriage/) explicitly explains that bandwidth below peak can reflect too few in-flight requests, while the [Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html?highlight=cu+da+ProfilerStart) distinguishes cache and memory levels. Counters and interpretations vary by architecture; validate with targeted access-pattern or co-runner perturbations.

**How to separate demand from sensitivity?** Define demand as a solo-run profile (phase-level execution time, SM/compute, cache/DRAM traffic, capacity, CPU and transfer activity). Define sensitivity as the change in that task’s latency/throughput under a stated co-runner or resource perturbation. Define impact as the slowdown it causes to the co-runner. Measure both directions from A-alone, B-alone and the same A+B concurrent run. If launch order matters, test A-first versus B-first as a separate controlled condition. Then use a small targeted stressor (e.g. compute-heavy or memory-latency/traffic-heavy) to see whether the suspected resource tracks the slowdown. Solo counters alone do not reveal either sensitivity or impact; symmetric “interference score” loses useful asymmetry. This follows the distinction made in interference characterization such as Orion and the SoCC’25 study.

**Can profiling perturb the result? Yes, especially detailed kernel-counter profiling.** Nsight Compute may replay kernels multiple times, save/restore memory, patch instructions for some metrics, flush caches, and incur significant overhead; Nsight Systems traces can also alter or expose concurrency/timing differences. First collect primary latency/throughput from unprofiled runs. Use lightweight system/timeline counters for the full run, then profile a small number of representative kernels/instances and compare profiled versus unprofiled duration. Keep a profiler-off paired baseline and do not use profiler wall-clock timing as application latency. [Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html?highlight=cu+da+ProfilerStart).

## What to avoid in the first study

- Avoid broad Cartesian sweeps over many models, batch sizes, process counts, tools, and backends. First establish the few contrasts above; expand only when results change a decision.
- Avoid inferring a bottleneck from GPU utilization, memory capacity, or DRAM bandwidth as a single scalar. Low DRAM throughput can coexist with memory-latency/cache stalls; high SM-busy can coexist with low useful compute throughput.
- Avoid mixing cold-start costs into steady-state contention results, and avoid treating container/model cache state as GPU execution demand.
- Avoid calling a co-run slowdown “memory contention” without a solo baseline and targeted perturbation. Report resource demand, sensitivity, and impact separately.
- Avoid combining encode and decode or assuming their engine paths from task labels. Confirm engine/backend and detect CPU fallback.
- Avoid extrapolating a profile to another GPU, driver, backend, model/input shape, or memory architecture without a held-out check. Existing sharing papers establish methods and workload-specific findings, not universal timeslice predictions.
- Avoid collecting every hardware counter on every run. Counter replay and profiling overhead can dominate short tasks; instrument narrowly after measuring unprofiled behavior.

## Smallest useful first sequence

1. Choose one repeatable GPU task and one CPU-heavy speech/video task. Establish solo warm baselines and record distinct task phases and actual backend/engine.
2. For one GPU model, compare batched single-process against separate processes, then repeat separate processes with MPS if available.
3. Run one same-device co-run pair with the GPU task and a deliberate compute-heavy or memory-stressing partner; keep both solo baselines and measure slowdown in both directions.
4. Repeat only the most decision-relevant contrast under cold launch/model state and one changed input/batch size. This checks state/input dependence without exploding the matrix.
5. Profile representative phases/kernels narrowly; check that the profiled result agrees in direction with the profiler-off timing. Record uncertainty and unsupported/missing counters.

This sequence should determine whether a future system needs separate features for process/sharing mode, phase/input shape, cold/warm readiness, CPU activity, and engine/backend, before anyone builds a generalized predictor. It does not establish that the predictor will generalize; that later claim needs held-out processes and hardware.
