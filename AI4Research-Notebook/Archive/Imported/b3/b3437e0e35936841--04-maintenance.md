# 4. Maintenance

**Keep shared names and meanings consistent.** Architecture connects requirements to component detail, so documentation belongs with design changes.

## Writing and naming

| Maintain | Rule |
|---|---|
| Writing | Plain English. Action first. Bullets, tables and breathing room. |
| New document paths | Lowercase kebab-case. Keep established `README.md`. |
| Existing identifiers | Exact canonical spelling, including `Research_Brief.json`. |
| Links | Check case against Git. Windows may hide Linux/WSL failures. |
| Diagrams | Mermaid source, clear boundaries, inputs/outputs and responsibilities. Render and register. |

## Documentation and glossary

- **Glossary:** one [canonical term](../glossary.md). Update prose, diagrams and agent instructions together. Prose edits do not rename contracts.
- **Immediate reading:** [README](../README.md), [M1 design](../m1-design.md), [principles](../principles.md). Retain the 3,400-word target.
- **Deeper context:** affected components, contracts and examples. Review affected meanings.
- **English/Chinese:** integrated agents make future parallel documents easier to maintain. Update required counterparts together. People review consequential meaning.
- **History:** preserve immutable sources. Git-tracked context supports role rotation.

## Integrity review

Check coverage, compatibility, feasibility, permissions, exits and failure paths. Record missing prerequisites, scientific negatives and stale evidence.

Resolved shared behavior supports specification. Integration evidence supports connection. Phase exits support M1 completion. Human review and AI/document checks remain distinct.
