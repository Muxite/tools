# 2606.02060 · Where Do Deep-Research Agents Go Wrong? Span-Level Error Localization (TELBench / DRIFT)

NJU-LINK · arXiv v1 June 2026 · 28 pp (9 body)
Read: body p1-p9, appendix analyses p12-p22. Data: HF NJU-LINK/TELBench;
code github.com/NJU-LINK/DRIFT.

## Summary
Moves claim checking from the report to the **trajectory**. 2,790 real deep-research agent
runs are segmented into semantic spans and annotated for harmful error spans; TELBench is a
1,000-instance localization benchmark; DRIFT is a claim-centric auditor that keeps a claim
ledger, checks support in trajectory evidence, and backtraces which spans depend on
unsupported claims.

## How it works (p2, p6)
- Four modules: **Claim Keeper** (ledger: when a claim is introduced, when it becomes
  consequential, which later spans depend on it) → **Support Seeker** (directly supported /
  weakly supported / missing support / contradicted) → **Specialist Auditors** (skill-routed
  checks for entity, constraint, evidence, retrieval, compute, process claims) →
  **Dependency Tracer** (backtrace to separate errors from benign exploration)
- ⭐ The error definition is commitment-based, not correctness-based: a span is an error
  only if it "introduces, relies on, amplifies, or finalizes" an unsupported or premature
  judgment **that affects the answer path** (p3). Failed searches, tentative hypotheses,
  recovered mistakes and tool noise are explicitly *not* errors
- Corpus: 3 backbones (GPT-5.4, Gemini-2.5-Pro, Claude-Sonnet-4.5) × 2 frameworks
  (MiroFlow, OAgent) × 3 benchmarks (p3). Seven expert annotators, **>300 hours each** (p3)

## Results
- 1,890 of 2,790 trajectories (**67.7%**) contain at least one span-level error (p4);
  1,000 verified instances form TELBench
- ⭐ **Among *successful* trajectories, 36.9% still contain at least one error span** (p13)
  — correct answers routinely rest on unsupported intermediate commitments
- DRIFT overall macro-F1 vs bare full-context prompting (p7 Table 2):
  Claude-Sonnet-4.6 21.89 → **54.91** (+33.0), DeepSeek-V3.2 22.46 → 50.51 (+28.1),
  GPT-5.4 33.93 → 52.48 (+18.6), Gemini-2.5-Pro 31.01 → 48.41 (+17.4)
- ⭐ **First-error accuracy stays low**: best overall FEA is 24.10% (Claude + DRIFT); on the
  hard split FEA is 7.25-12.00% even with DRIFT (p7). "Identifying some erroneous regions
  and identifying where the error first appears are distinct diagnostic abilities" (p7)
- Generic agentic wrappers do not help and can hurt: Codex on DeepSeek-V3.2 drops F1 from
  22.46 to 12.05 (p7)
- ⭐ **Scale does not help**: across Qwen variants, larger models do not consistently
  achieve better macro-F1 or FEA (p7)
- Module ablation (p8 Fig 5c): bare 22.46 → +Claim Keeper 43.08 → +Support Seeker 46.15 →
  full DRIFT 50.51. The single largest jump is the **claim ledger**
- DRIFT's biggest recall gains are precisely on evidence- and constraint-related errors —
  source verification, unsupported commitments, omitted constraint checks — the categories
  bare prompting handles worst (p8)

## Limitations
⚠ Annotation is "LLM-assisted expert review": an LLM proposes error spans, experts verify
and adjudicate (p3). The gold labels are therefore partly shaped by a model, and the
auditors being evaluated are LLMs of the same families.
⚠ Absolute performance is low in every condition — best overall F1 54.91, best FEA 24.10 —
so "+30 pp" is an improvement from very bad to bad.
⚠ Only three backbones and two frameworks; benchmark tasks are browse/search-style
(BrowseComp-like), not report writing, so transfer to long-form report claims is untested.

## Relevance
- ⭐ **The 36.9% figure is the sharpest thing in this slice for AI4Research's argument**:
  final-answer correctness certifies nothing about the chain that produced it. It is the
  trajectory analogue of "the sentence occurs in the cited section" — right output,
  unverified provenance
- The claim ledger with a consequential/dependency structure is close to what AI4Research's
  verdict table does statically; DRIFT shows the ledger is where most of the gain lives
  (ablation p8), not the judging
- Evidence against "scale will fix checking": bigger backbones do not localize errors better
- Its error taxonomy (p15-p16: Unsupported Commitment, Source Verification Error, Source
  Misuse Error, Overanchoring) is a ready vocabulary for AI4Research's failure categories
