docs/architecture/design-package\method\decisions.md:182:`Standard`. **The API router is a separate process.** The API router runs as a separate process inside the app container. A person can kill it. `RouterPort` reaches it only over local IPC (a Unix domain socket in the container) and returns the router's model choice and nothing else. The router calls no provider, holds no provider credential and writes no route record. The model bridge dispatches to the provider and writes the route record and the call record. `RouterPort` enforces the 30 s deadline with its own timer. A crash, a hang, an invalid reply or an unreachable process gives the Codex fallback with the matching `router_failure` (`error`, `timeout`, `invalid_decision` or `missing`). A router failure never fails a run. A failure of a model the router chose halts the node like any other model failure, because the model is fixed once the call starts. The router is on only under an approved evaluation profile. Verifier subnode calls always use the Codex route, whatever the router says; only the Phase 3 alternate-verifier evaluation profile may override that. This amends [owner ruling routing row 2](../side-systems/owner-rulings.md#routing-v21) (in-process module) and the execution-adapter wording of the owner design. The hot path now imports no router code at all ([import boundary](../reference/import-boundary.md)). Reason: a router that shares the process of the runtime can take the runtime down with it. A separate process can be killed, and the non-blocking test can prove that a killed router leaves a run unharmed.
