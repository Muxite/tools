# 2608.01050 · Don't Offer What Can't Be Done: Deterministic Executability Gating for LLM Skill Selection at Scale

Ortal Ashkenazi, Vitalii Kloz, Mykhailo Ulianchenko · Wix (Israel, Ukraine) · preprint under review at KDD 2027 Applied Data Science · arXiv v1 2 Aug 2026 · 7 pp (6 body)
Read: p1-7 in full this session (body p1-6, refs p7; Figures 1-3 on p4 and p6 rendered from the PDF, which agree with the text)

## Summary
A skill can match the user's topic and still be impossible to run in the current
account state. The paper describes a **deployed three-stage selection pipeline** in
**Helpmate, Wix's customer-care assistant**, evaluated on one topic family of **ten
domain skills** (p1, p2). Stage 1 is a state-blind semantic matcher. Stage 2 is a
deterministic **executability gate** that removes skills whose own exit conditions hold.
Stage 3 is the LLM, which decides whether to activate, answer from the KB, or clarify
(p3). Over one month of production traffic, the gate removed **59.4%** of post-semantic
skill–message pairs (p5). With all ten skills exposed in a 1,000-conversation
**risk-enriched** replay, the model chose a skill production would have blocked in
**7.8%** of conversations (p5). The paper measures selection only, not execution or
customer outcomes.

## How it works (p2-3)
- **Stage 1 (semantic)**: recall-oriented and state-blind. If a message is about the
  domain family, **all ten** skills become candidates; otherwise none (C(m) = S or ∅,
  p3). ⚠ It does not rank or shortlist individual skills
- **Stage 2 (gate)**: **exit-condition inversion**. Each skill's internal abort branches
  (e.g. domain already connected, missing premium entitlement, requester not owner) are
  reused as gate predicates on authoritative state. Visible set V(m) = {s ∈ C(m) :
  ¬E_s(x)} (p2-3)
- **Contract-relative soundness** (p3): *provided* predicate parity holds and both
  checks see fresh authoritative state, a blocked skill would exit if invoked. It is
  **one-sided**: passing the gate does not mean the skill is wanted or will succeed.
  No labeled executability data is needed
- Why deterministic: prompting the model to remember business constraints makes them
  compete with intent and history in a stochastic context (p3)
- **Predicate lifecycle** (p5): change the exit condition → update the predicate →
  parity regression tests (boundary, missing-state, stale-state) → serve with
  versioning and rollback. Three monitored failure modes: predicate drift, state
  staleness, backend-contract drift. Fail-open vs fail-closed on unavailable state is
  "not determined by the gating architecture" (p5)
- The gate is not an authorization boundary: backend least-privilege and transaction
  validation remain at execution time (p2)

## Results
- **Dataset** (p3): 9 Jun-10 Jul 2026, **756,641 messages / 267,612 conversations**.
  The semantic stage matched **174,927 messages (23.1%)** → × 10 = **1,749,270
  skill–message pairs**
- ⭐ **Gate after semantic matching (p5)**: removed **1,039,462 pairs (59.4%)** and
  228,799,446 description tokens (**59.1%** of 387.3M), leaving 709,808 pairs. That is
  5.94 skills and 1,308 tokens removed per matched message
- **Combined**: semantic matching + gate cut skill-description tokens by **90.5%** vs
  exposing all ten skills to every message (1,675.2M → 158.5M; Fig. 2, p4-5)
- **Offline all-message diagnostic** (not a production stage): 3,075,236 of 7,566,410
  pairs (40.6%) non-executable (p5)
- **Per-skill heterogeneity** (p5): block rate 28.1%-94.1%, median 48.2%. Savings 8.9M-
  42.3M tokens per skill; top 3 skills = 46.3% of savings. Descriptions 152-344 tokens,
  2,214 in total (p4)
- ⭐ **Counterfactual replay** (p5): the first 1,000 conversations (chronologically) in
  which a matched skill failed a precondition and was not activated, each replayed
  **once** with all ten skills exposed → the model selected a production-blocked skill
  in **78 (7.8%)**. The paper warns this is conditional on a risk-enriched cohort and
  must not be extrapolated. Selected skills were not executed (p5)
- ⚠ **Not measured**: end-task success, resolution rate, customer satisfaction,
  latency or billed cost, false-block rate, or any empirical check that gate decisions
  match actual skill exits. The paper lists "discrepancies between gate decisions and
  subsequent skill exit behavior" as a signal to monitor, but reports none (p5)
- ⚠ No model name is given for the Stage-3 LLM or the replay

## Limitations (stated, p6)
- One topic family (ten skills), one observation window. It may not generalize to other
  families or traffic periods
- The 7.8% is conditional on a risk-enriched cohort, from a single replay per
  conversation, and measures selection rather than execution, severity or variance
- Soundness depends on predicate parity and state freshness
- Only preconditions expressible as deterministic state checks are handled. Ambiguous
  intent and incomplete requests stay with the agent
- Tokens ≠ billed cost, latency or avoided retries. Period aggregates allow no daily
  uncertainty estimates or causal attribution

## Relevance
- **Directly supports** the design: in production, a deterministic filter from exit
  predicates to authoritative state runs **after** relevance matching and **before** the
  LLM chooses, and it removes most candidates (59.4%) that semantic relevance lets
  through (p3, p5)
- Supports that the filter changes model behaviour, not only context size: ungated, the
  model picks a known-blocked skill in 7.8% of risk-enriched conversations (p5)
- Supplies the correctness argument and its conditions: soundness only relative to
  predicate parity and fresh state, enforced by parity regression tests and monitoring
  (p3, p5). It is a one-sided guarantee, and the filter is not an authorization layer
  (p2)
- Does **not** show better task outcomes, safety incidents avoided, or cost savings.
  It does not show false-block rates or that parity held in practice. Its scale is ten
  skills in one family, not a large library
