# Shared GPU, same node

What happens when AI task nodes (small LLMs, model training, speech-to-text, video encoding) share one GPU, what it costs to start them, and what the GPU is doing inside each one. Every number is measured, per process, on one workstation.

Short version 1 · A + B 2 · Copies vs batching 3 · Who loses 4 · What each uses 5 · Starting 6 · wonhee What to do Limits & ARM Open questions Appendix 

## The short version

- Two tasks on one GPU take turns; they do not add up.  Run together, the GPU looks like a blend of the two, weighted by who got more time, minus 2–22% lost to switching between them.

- Copies of the same model as separate processes is the worst arrangement.  Four copies produce less in total than one. Batching the same four requests in one process gives 2.4× the output in less than a third of the memory.

- Who loses depends on the shape of the work.  A small LLM loses about half its speed next to model training; training barely notices. Tasks that use other hardware (the video encoder, the CPU) hardly interfere.

- Starting is cheap; starting cold is not.  A container adds about 0.15 s. A fresh LLM container that has to compile its GPU code adds about 59 s, and loading a model from disk instead of keeping it in GPU memory costs about 120×.

- Everything comes with per-node execution traces : every GPU kernel each node ran, alone and shared, ready to check a simulator against.

One workstation: RTX 5070 Ti 16 GB (Blackwell) on PCIe Gen4 x16 · Ryzen 7 3700X, 16 threads · 46 GiB RAM · Docker 29.8 · llama.cpp CUDA · Nsight Systems 2026.3. Details in the appendix.

We recorded the whole GPU's activity counters 10,000 times a second through one fixed sequence: idle, task A alone, idle, task B alone, idle, both together. Each task also recorded its own GPU work, which shows how the GPU split its time between them.

Shaded bands are the measured windows. In the A+B window the lines sit between A's and B's levels instead of adding up.

Sum : both run at once and their activity adds. Time-split : the GPU alternates, so A + B is each task's solo activity weighted by its share of GPU time. Time-split is close; the measured value falls below it by the time lost to switching.

84% / 16% GPU time to training vs the LLM when they share

What it means:  to estimate a shared GPU, weight each task's solo profile by its share of GPU time and subtract a switching cost. Never add them.

## Who loses depends on the shape of the work

Four task types shared the GPU in every pairing, each compared with its own runs alone.

Row task's slowdown with the column task on the same GPU. The LLM loses about half its speed beside training; training slows only 16%.

Finding 4

## Each task leans on a different part of the GPU

Fig. 8 · memory bandwidth vs tensor-core use, each task alone

Hover a dot for details. Generating text (decode) is limited by memory bandwidth and uses no tensor cores. Reading the prompt (prefill) and training use tensor cores. Speech-to-text and video encoding barely use either.

What it means:  generating text re-reads the whole model for every token, so on this card a 7B model reaches about 95% of the measured memory ceiling. Faster generation needs more memory bandwidth, not more compute. Appendix table B.3 has the numbers per model size.

## What to do with this

- One model, one batching server.  Route all agents' requests for a model to one process that batches them (Finding 2).

- Pair by hardware, not by convenience.  Put an LLM next to video encoding or CPU work, not next to training (Findings 1, 3, 4).

- Budget memory per copy.  Every separate process holds its own weights (Fig. 5).

- Keep short tasks warm.  Reuse running containers; skip networking where it is not needed (Finding 5).

- Avoid the cold paths.  Share the GPU-code cache across containers and keep hot models loaded (Finding 5).

- Model shared GPUs as time-sharing.  A simulator should blend solo profiles by time share and subtract a switching cost (Finding 1).

## Limits, and would it hold on a unified-memory ARM system?

One machine and one GPU model. 2–12 repeats per point (repeat agreement is listed in the appendix). The shapes should carry over to other NVIDIA GPUs; the absolute numbers belong to this card. Profiled runs carry a small profiler cost, which is equal across every compared pair.

Everything here used x86-64 with a separate GPU joined over PCIe. Unified-memory aarch64 systems (NVIDIA Grace-based machines, Jetson, Apple silicon) share one memory pool between CPU and GPU. These are expectations, not measurements:

### Likely to carry over

- Text generation is memory-bandwidth-bound ; speed follows that system's bandwidth, often lower on unified LPDDR designs.

- Batching beats separate processes : a property of the workload.

- Separate processes take turns  and lose time switching; the size needs remeasuring.

- Container start is a fixed cost ; milliseconds depend on the CPU.

### Needs remeasuring

- Model loading : no PCIe copy, so "in RAM" vs "in GPU memory" may converge.

- Running part of a model on the CPU : the PCIe cliff goes away; the trade-off changes.

- CPU tasks vs GPU tasks : they share one memory bandwidth, so new interference is likely.

- Memory accounting : one pool, so per-process numbers and limits need re-validating.

- Counters, power, software : availability varies by chip; images need arm64 builds.

## Open questions

- What is the switching cost made of?  Context-switch time, cache refills or launch queuing. NVIDIA MPS, which removes context switches, would separate them.

- Can a node's own profile predict its time share?  Kernel length and Fig. 8's position might predict who wins the GPU; the per-node traces are the test set.

- Where does batching stop paying off?  Larger batches, longer contexts and larger models would find the limit.

- Real agent traffic.  Bursty calls with gaps, model swaps and cold starts are not measured here.

- Other hardware.  Rerun on a datacenter GPU and on a unified-memory ARM system to see which shapes carry over.

## Appendix

Written to be used without the rest of this conversation: on another machine, next to other documents, or as input to someone building a simulator. A.x explains the method; B.x holds the numbers behind every figure.

### A.1 Glossary

**Node / task**: One unit of work in an agent pipeline (generate text, transcribe a clip, train for N steps), run as one container.

**Prefill / decode**: The two phases of LLM inference: reading the whole prompt at once (large matrix multiplies, compute-bound) and generating tokens one at a time (matrix × vector, memory-bandwidth-bound).

**Kernel**: One function launched on the GPU. A decode step is hundreds of them; each has a start time, a duration and a launch shape (grid, block).

**SM**: Streaming multiprocessor: the GPU's compute units (the "CUDA cores" live inside them). "SMs active" is the share of them doing work.

**Tensor cores**: Matrix-multiply units inside the SMs, used by prefill and training.

**DRAM bandwidth**: How fast the GPU reads and writes its own memory, as a share of the maximum. The limit for text generation.

**Time-slicing**: How the GPU shares itself between separate processes by default: it switches between their contexts instead of running them at once.

**Switching cost**: The gap between measured A+B activity and the time-split blend: work lost to context switches and refills.

**Batching**: One process serving several requests with each weight read once for all of them.

**Page cache**: Linux keeps recently read files in RAM; a model "in RAM" loads without touching the disk.

**cgroup**: The Linux mechanism that gives each container its own CPU, memory and IO counters.

**NVML / CUPTI / Nsight Systems**: NVIDIA's management library (memory, power, utilization), profiling interface (kernel traces) and profiler (traces plus hardware counters).

### A.3 How gauge measures a task

- Declare.  A task is a workload (container image + command + parameters). `gauge run`, `sweep` (a grid from YAML), `corun` (deliberate pairs) and `sequence` (idle → A → B → A+B) launch them.

- Predict, then freeze.  Before launch, gauge writes predictions it may never change (the database rejects edits). Kept for later prediction work; not used in this report.

- Launch.  Each task is one container under a small shell wrapper. The wrapper runs the task, prints its exit code, then waits on stdin, so the container stays alive until the host has read its final counters. Without that, Docker deletes the counters the moment the task exits.

- Measure, on the host:  every 100 ms, the container's cgroup counters (CPU time, memory, IO, pressure) and NVML (GPU memory per process ID, mapped to the container; utilization, power, clocks, video engines). At the end: the kernel's exact peak-memory mark, out-of-memory events and the GPU energy counter.

- Trace, inside:  optionally Nsight Systems inside the container records every GPU kernel and memory copy of the task's own processes ("trace"), plus the whole GPU's hardware counters at 10 kHz ("metrics"; one task at a time).

- Classify and store.  Outcome (success, out of memory on CPU or GPU, timeout, error), a summary of about 70 fields, and the raw samples go to a SQLite ledger. Out-of-memory runs are kept but marked censored.

| Scope | Measures | Isolated to one task? |
| --- | --- | --- |
| container | CPU time, RAM peak, IO, out-of-memory events (cgroup v2) | Yes, exactly, even when sharing |
| process | GPU memory per process; every kernel and copy (CUPTI) | Yes. Under sharing a kernel's duration also includes time the GPU spent on others |
| device | GPU utilization, power, clocks, SM / tensor / DRAM / PCIe counters | No: whole GPU. Equals the task only when it ran alone (each run records this) |

The GPU lock: a machine-wide advisory lock (`gpu-lock`) is held for every measured run, so other agents' GPU work does not land inside a measurement.

### A.5 Metrics and formulas

**Slowdown**: Run time with a partner ÷ median run time of the identical task alone, in the same profiling mode. For LLM decode we use tokens/s alone ÷ tokens/s shared.

**Time share**: From each task's own kernel trace inside the A+B window: busy time ÷ window length. When two shares sum past 1 (a kernel's span includes time it was switched out), both are scaled to sum to 1.

**Time-split model**: A+B ≈ floor + (A − floor) × shareA ÷ busyA,solo + (B − floor) × shareB ÷ busyB,solo, where floor is the idle reading.

**Sum model**: A+B ≈ A + B − floor, capped at 100%.

**Switching cost**: (time-split − measured) ÷ time-split, per counter. DRAM read: 9% (LLM + training), 2% (LLM + NVENC), 22% (LLM + LLM).

**Decode bandwidth**: Model file bytes × tokens/s. Decode reads every weight once per token, so this approximates the memory traffic.

**Energy per token**: Mean GPU power while busy ÷ tokens/s. Valid for decode; prefill bursts are shorter than NVML's ~1 s power averaging.

**Overhead**: Median request-to-result time minus the native median for the same work.

### A.7 Setting this up on another machine

- Linux with cgroup v2, Docker, and the NVIDIA container toolkit (`docker run --gpus all` works).

- Copy the gauge repo; `uv sync --extra dev`; `uv run gauge doctor` checks cgroup v2, Docker, the GPU runtime, NVML capabilities and the GPU lock.

- Nsight Systems: download the `nsight-systems` .deb for your OS and architecture from NVIDIA's CUDA repository and extract it (`dpkg-deb -x`); point `NSYS_DIR` in `gauge/nsight.py` at it. No system install is needed.

- GPU counters: if the driver restricts profiling to admins (`RmProfilingAdminOnly: 1` in `/proc/driver/nvidia/params`), gauge already adds SYS_ADMIN to counter-reading containers.

- Images: `uv run gauge build` (stress, torch, wonhee, startbench); pull `ghcr.io/ggml-org/llama.cpp:full-cuda`, `ollama/ollama:0.35.0` and `linuxserver/ffmpeg:7.1.1`. On aarch64, use arm64 builds of each.

- Models: pull qwen2.5 into an Ollama volume (`ollama pull qwen2.5:3b`, etc.) and set `MODEL_VOLUME` in `gauge/workloads/llm.py` to that volume.

- Media: `uv run gauge prepare` makes the video source. The wonhee clips came from a third-party reel and are not included; use any clip with speech.

- Run the experiments in A.4, then `gauge dataset` and `gauge trace-export`.

### A.8 Pitfalls we hit

- Ollama kills its model process , so its traces lose buffered records. For per-process traces we ran llama.cpp directly (the same engine).

- CUDA code compiles on first use  in every fresh Ollama container on this GPU (about 59 s) unless `/root/.nv` is shared between containers.

- File memory is charged to the first container that reads a file.  A model's first run looks like it needs 9 GB of RAM; later runs, 0.6 GB.

- The profiler raises the idle floor  (≈27 W vs 17 W unobserved). Only compare profiled runs with profiled runs.

- Only one session can read the GPU counters at a time.  X7 uses one observer and gives the tasks kernel traces only.

- Lock tokens can start with "-" : pass `--token=…`, or the release fails silently and the GPU lock leaks.

- Concurrent jobs need separate database connections ; one shared SQLite connection crashed under parallel writes.

- stress-ng reads fractional timeouts as 0 , which means forever.
