### C14. `packages/ptc-runtime/` implements PTC mode: model writes TypeScript or Python against host-provided async bindings, executed in a fresh process under the same sandbox policy as Bash, returning a lossless-JSON value, ordered per-channel logs, or a structured error
**Verdict:** PARTLY
**Evidence:**
- The abstract seam and result contract are exactly as described: `packages/ptc-runtime/ptc-runtime/README.md` — "Use `dsh-ptc-runtime` to run one model-written program against host-provided asynchronous functions through a configured backend. A request returns a lossless-JSON value, ordered per-channel logs, or a structured error…" The type is `PtcRunResult` at `packages/ptc-runtime/ptc-runtime/src/types.ts:144-160`: `value?: PtcJsonValue`, `logs: string[]` (comment: "Each source channel preserves emission order"), `error?: PtcRunFailure` (a closed `kind` union: `exception | timeout | abort | worker-exit | invalid-output | output-limit | protocol | sandbox-unavailable`).
- The TypeScript backend under `packages/ptc-runtime/` matches "same sandbox policy as Bash" verbatim: `packages/ptc-runtime/ptc-runtime-node/README.md` — "Execute model-written TypeScript under the same platform sandbox policy as Bash… Each call starts a fresh Node process and returns captured logs, an exact JSON value, or a structured failure."
- **The Python backend does not live under `packages/ptc-runtime/`.** It is at `packages/experimental/ptc-runtime-python/`, a sibling of the `ptc-runtime/` group, not inside it. The group's own README acknowledges this split: `packages/ptc-runtime/README.md` — "Choose the TypeScript backend for execution in a fresh Node process under the configured sandbox policy, or the experimental Python backend when a CPython process is required," listing only two packages as belonging to the group (`ptc-runtime/`, `ptc-runtime-node/`) in its packages table.
- **The Python backend does not run under the same sandbox policy as Bash — it explicitly has no sandbox at all.** `packages/experimental/ptc-runtime-python/README.md` — "Resource budgets and process-group teardown contain runaway work, but the subprocess is not a security boundary: direct Python operations have no filesystem sandbox, no state persists across runs, and no shipped profile enables this runtime." (It is also not mounted in any shipped bundle/preset.)

**Note:** the claim is true for the TypeScript path (package location, fresh-process execution, sandbox parity with Bash, and the result shape) but false for the Python path on two counts: the implementing package is outside `packages/ptc-runtime/` (it's under `packages/experimental/`), and it explicitly does *not* run under the same sandbox policy as Bash — the README states it has no filesystem sandbox and ships in no default profile.

## What else I noticed

- **Row-order caveat is load-bearing for reading the bundle file in general**, not just for `agent-loop` (C3): `packages/bundle/base/cordis.patch.yml:12-13` disclaims load semantics for every row, so anyone inferring priority or dependency order from position anywhere in that file would be wrong.
- **C13's negative claims are reinforced by an explicit repo-level naming choice**: `packages/host/plugin-inventory/` and `packages/llm/plugin-package-inventory-deepseek/` are the only packages that look like a "capability registry" by name, and both go out of their way to disclaim history/versioning in their first paragraph. That's stronger evidence than a mere absence of matches — the absence was apparently a deliberate design choice that someone thought worth documenting.
- **The C12 invariant is package-scoped and request-scoped, not global**: `packages/core/agent-loop/src/invariant.ts` only fires for `isAgentLoopRequest(options)` — i.e., loop-built requests. One-shot / hand-built `GenerateOptions` calls (mentioned in `packages/llm/llm/src/types.ts:462-464` as a legitimate path — "a hand-built one-shot passes any list") are explicitly exempted from this check by design, so "Model-visible means logged" as a *runtime-enforced* rule applies to the main agent loop but is a documentation-level expectation elsewhere (e.g. `packages/session/session-title-llm/src/index.ts:26` treats a one-shot title-dispatch request as needing its own separate log record by convention, not by this invariant).
- **PTC's sandbox story is uneven across languages** (surfaced while checking C14): TypeScript/Node PTC execution shares Bash's sandbox policy and can fail closed with `SANDBOX_UNAVAILABLE`-style reporting (`sandbox?: PtcRunSandbox` field with `enforcement?: SandboxEnforcement`), but the Python backend is unsandboxed by its own README's admission and unmounted by default — someone designing on top of PTC mode should not assume both languages get equivalent confinement.
- Root package name is `@deepseek-ai/dsh-root` (`package.json:2`), for anyone cross-referencing package scoping conventions (`@deepseek-ai/dsh-*`) mentioned throughout the READMEs quoted above.
