## Common issues — check every batch (continued)

**5. A capsule that needs both a model call and a nested call to a pinned helper must be `kind: tool`, never `skill`.** Only `tool` code can make a `nested` call at all (the working choice: "a capsule that calls an operator is a `tool`. Its code makes the operator call as a `nested` call, and its model call through M05"). `screening_capsule` (pinning `rank_opportunities`) and the first draft of M20 (pinning `compare_to_thresholds`) both got this wrong, drafted as `skill`. **Check this whenever a capsule design pins a deterministic helper — it's `tool`, and the model call (if any) happens inside its own code via M05, the same way M05 itself works.**

## Process mistakes and lessons

**Quote the exact source text before making a claim about what a page says — paraphrasing from memory of having read it earlier produces wrong citations.** Happened twice in one day on the same page (`permissions.md`): first, misattributing "jiuwenbox is a later step" to its Gaps section (it doesn't say that); second, claiming an `effect_class: irreversible` declaration would be "unenforced" on the Codex runtime, when the actual text puts enforcement "by the runner" and the policy mapping makes it DENY on an unattended run — the opposite of what was claimed. **When citing what a specific page says, re-read and quote it in the same turn, don't rely on an earlier read from several turns back.**

**A design review scoped to one module can miss an error that only shows up when the whole chain is checked together — budget for both, not just the narrow one.** The claim-vs-falsification-threshold collapse in `hypothesis` (2026-09-30) is the clearest case: a review of M08 alone (which consumes `hypothesis`) didn't catch it, because the collapsed field still had the right *type* for what M08 reads. It only surfaced when a reviewer was asked to trace the *whole* data chain end to end and noticed the PRD's own worked examples give the claim and the threshold as two different numbers. **For a chain of dependent modules, at least one review pass needs to trace the full chain together, not just adjacent pairs.**

**Reading the PRD stage a module maps to is not enough — also read the stage immediately upstream, before designing the module's inputs.** M08 (2026-09-30) was redesigned by reading PRD 3.7 carefully, and got the baseline mechanism backwards: it assumed M08 independently sources and runs a baseline, when PRD 3.6.3 says the harness M07d builds runs both baseline and treatment internally, and M08 just executes that one script. This is the third consecutive load-bearing redesign in one day found substantively wrong by a dedicated adversarial review (after the RSI build-order note and M20) — but it's the clearest case of a specific, nameable mistake, not just "wasn't careful enough." **A module's In list is only as correct as the adjacent upstream module's actual PRD-specified Out — check that PRD sub-feature directly, every time, not just the module being redesigned's own stage.**

**A module that reverses an earlier decision needs two review rounds before it's called done, not one.** M20 (PRD 3.8, 2026-09-30) is the second time this happened today, after the RSI passage. First review pass checked the fix's reasoning was PRD-grounded and found the core mechanism sound. A *second*, dedicated adversarial pass — explicitly asked to be skeptical of a load-bearing reversal, not just fact-check it — found the fix wasn't actually finished: real missing inputs (M08/M07c payloads), an unenforced safety guarantee, a separate unfixed risk one stage earlier (G6), and a kind conflict. **Lesson: when content reverses or supersedes an earlier explicit decision, budget for a second review round by default, specifically instructed to look for "is this actually finished" rather than "is this accurate" — those catch different things, same as the two-pass lesson below for schema edits.**

**RSI's sandbox/admission mechanics took three review rounds to get right (2026-09-30).** First pass: overstated the blockers (claimed one blocker when there were several) and wrongly framed "an admitted `screening_capsule`" as the dependency. Second pass, after review: still wrong — said `screening_capsule` itself was `evolution.rsi: none` (it's `propose`; `none` belongs to the nested pure helper `rank_opportunities`, which is target 1's actual mutation target). Third pass, verified directly against `rsi-3y-full.md`'s own text line by line, held up. **Lesson: for subtle mechanics (what's admitted vs. sandboxed, which rule applies when), read the primary source document directly and quote it — don't restate from a summary, an earlier draft, or your own inference, even when the inference sounds reasonable.**

**Introduced a real bug while fixing the Research Brief schema (2026-09-30).** Added a `requirements_and_metrics_present` rule requiring "at least one metric" always — directly contradicting the page's own pre-existing rule that a request with no measurable metric still returns a valid Brief with an `INPUT_INCOMPLETE` issue. Caught by a *second*, dedicated review pass that checked internal self-consistency only (Declaration vs. its own rendered `make_capsule.md` mirror, schema table vs. worked example) — separate from the first pass, which only checked PRD-grounding. **Lesson: a multi-field schema edit needs two review passes, not one — "is this grounded in the right source" and "does this still agree with the rest of the same document" catch different classes of error.**

**The original incident: deleted `m1-architecture.md` without checking inbound references.** A subagent (see [[HANDOFF]], 09-30 morning) deleted it as "stale" without checking that `capsule/guards.md` cited its anchors ten times. Recovered from a dangling git blob — survived by luck. **Lesson: before deleting or retiring any page, grep the whole vault for references to it first.**

**"19 modules" was wrong for most of the day.** `m1-architecture.md` has 27 distinct module IDs (M00a-c, M01-M19, M07a-e, M10a); I'd been reading "M01 to M19" as the total and dropping the lettered ones. Caught by the top-bottom connection review. **Lesson: count directly (grep, don't eyeball) before stating a total anywhere it'll get repeated.**
