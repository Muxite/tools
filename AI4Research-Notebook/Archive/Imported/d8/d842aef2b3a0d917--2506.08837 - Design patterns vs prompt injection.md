# 2506.08837 · Design Patterns for Securing LLM Agents against Prompt Injections

Beurer-Kellner, Buesser, Creţu, Debenedetti, Dobos, Fabian, Fischer, Froelicher, Grosse, Naeff, Ozoani, Paverd, Tramèr, Volhejn · Invariant Labs, IBM, EPFL, ETH Zurich, Swisscom, Google, Microsoft, … · v3 27 Jun 2025 · 32 pp (27 body)
Read: p1-7 (framing, defence taxonomy, patterns 1-4); patterns 5-6 and case studies from structure

## Summary
Argues that general-purpose agents are unlikely to be made safe against prompt injection
with today's models, and asks a better question: **what agents can be built now that are
useful and resistant?** Answer: agents **deliberately constrained** so that once untrusted
data is ingested it cannot trigger consequential actions. Proposes 6 design patterns and
applies them to 10 case studies.

## The principle (p4)
"once an LLM agent has ingested untrusted input, it must be constrained so that it is
impossible for that input to trigger any consequential actions."

## The 6 patterns (p4-7)
1. **Action-Selector**: the LLM maps a request to one of a fixed list of actions (an
   "LLM-modulated switch"); no feedback from actions
2. ⭐ **Plan-Then-Execute**: the agent fixes a plan (a list of tool calls) **before** any
   untrusted data is processed; tool outputs can affect arguments but "cannot inject
   instructions that make the agent deviate from its plan" (p5). A form of **control-flow
   integrity**; it does not stop injection in the user prompt or manipulation of
   arguments (e.g. the email body)
3. **LLM Map-Reduce**: one isolated sub-agent per untrusted document (map), outputs
   constrained (e.g. a Boolean or regex-checked value), then a reduce step that is either
   non-LLM or only sees constrained outputs
4. **Dual LLM**: privileged planner with tools, quarantined reader without tools
5. **Code-Then-Execute**: the plan is a program (as in CaMeL, 2503.18813)
6. **Context-Minimization**: remove the user prompt from context once used

Also a defence taxonomy (p3): LLM-level (prompting, adversarial training: no guarantees),
user-level (confirmation: fatigue risk), system-level (detectors: heuristic; isolation:
the promising path).

## Relevance
- REPORT.md §3.2: the canonical statement of **plan-then-execute**, which is AI4Research's
  freeze seen from the security side: fix the plan from trusted input, then execute
- Its explicit trade, "constrain the agent to explicitly prevent it from solving
  arbitrary tasks", is the same trade AI4Research makes, and the right way to present
  AI4Research's reduced flexibility: as a deliberate security and verifiability choice
- Map-Reduce with constrained map outputs parallels AI4Research's verbatim, hash-bound
  claim spans passed between stages (cf. 2608.24306's "pass raw snippets" intervention)
