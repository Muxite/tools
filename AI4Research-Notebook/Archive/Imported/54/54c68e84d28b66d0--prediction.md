# Research memo: GPU resource pressure and performance prediction

The literature supports two distinct prediction stages. Before execution, model or code structure plus input shapes can predict coarse utilization, occupancy, or latency. After a short run, hardware counters can classify the observed bottleneck more directly. These are different claims: counter-based prediction must not be presented as pre-execution prediction.

## Relevant primary papers

- **“Towards GPU Utilization Prediction for Cloud Deep Learning” (HotCloud 2020).** Yeung et al. predict GPU utilization from features extracted from a DNN computation graph, including FLOPs, input size, and graph structure. Their goal is proactive prediction for scheduling, without isolated online profiling. The paper reports an RMSLE of 0.154 and evaluates scheduler benefits; it does not predict pressure on specific execution units or establish broad transfer to arbitrary GPU tasks. [Authors’ USENIX proceedings PDF](https://www.usenix.org/system/files/hotcloud20_paper_yeung.pdf) · [Lancaster repository record](https://eprints.lancs.ac.uk/id/eprint/144290/).

- **“Horus: Interference-Aware and Prediction-Based Scheduling in Deep Learning Systems” (IEEE TPDS 2022; published online 2021).** Horus extends graph-feature prediction to GPU and memory utilization and uses those estimates to select co-locations. It characterizes hundreds of co-location combinations across heterogeneous GPUs and evaluates a Kubernetes-integrated system plus trace-driven simulation. Its GPU-utilization target is the fraction of a sample interval with a kernel active, explicitly not SM-core or memory-bandwidth utilization. This is a useful precedent for task matching and workload history, but its target is scheduler-level use and interference, not component-level chip pressure. [Primary paper PDF](https://yangrenyu.github.io/paper/tpds2021-horus.pdf) · [IEEE paper record](https://doi.org/10.1109/TPDS.2021.3079202).

- **“GPU Occupancy Prediction of Deep Learning Models Using Graph Neural Network” (IEEE CLUSTER 2023).** Mei et al.’s DNN-occu encodes computation-graph node and edge semantics with a GNN to predict occupancy, including for unseen models. The paper reports overall error of 9.271% and tests trace-driven scheduling simulations. It is closer to predicting SM residency pressure than coarse GPU utilization, but occupancy is still not equivalent to achieved throughput or a precise bottleneck; its inputs and evaluation are DNN-focused. [Primary paper and author-version link](https://www.microsoft.com/en-us/research/publication/gpu-occupancy-prediction-of-deep-learning-models-using-graph-neural-network/?lang=fr_ca).

- **“Forecasting GPU Performance for Deep Learning Training and Inference” (ASPLOS 2025; preprint 2024).** NeuSight predicts performance on unseen GPUs without executing the target model there. It breaks kernels into tiles, predicts tile-level behavior, then aggregates estimates into end-to-end latency, combining hardware descriptions with learned behavior. The authors report a GPT-3/H100 case where their latency percentage error is 2.3%; the public repository includes code, model/device configuration examples, training data and labels. This is the strongest precedent here for cross-hardware forecasting, though its scope is DL model latency and tile behavior rather than general task capsules or component-level pressure. [Primary paper](https://doi.org/10.1145/3669940.3707265) · [author repository](https://github.com/scai-tech/NeuSight).

- **“Utilizing GPU Performance Counters to Characterize GPU Kernels via Machine Learning” (2020).** This work trains classifiers on counters collected while generated kernels execute, to characterize compute and memory behavior and identify possible low-performance causes. It demonstrates a useful post-start profiling path, but the counters are runtime observations: using them as input to a claimed pre-run predictor would leak the target execution. Evaluation focuses on stencil and sparse-matrix kernels; adding classes requires adding them to the training data. [Primary open-access paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC7302272/).

- **“A Unified, Hardware-Fitted, Cross-GPU Performance Model” (2016).** Stevens and Klöckner automatically extract symbolic operation and memory-access counts from kernel representations, fit machine parameters per device from measurement kernels, and predict runtime across GPU vendors and generations. It demonstrates interpretable static features and hardware-specific calibration. The paper explicitly leaves occupancy, latency hiding, overlap, and some resource-granularity effects outside its model, making those useful dimensions for a richer learned predictor. [Primary paper](https://arxiv.org/abs/1604.04997).

## Existing results versus proposal boundary

**Already established:** workload/model graphs can support pre-execution estimates of coarse GPU utilization and occupancy; tile-level decomposition can help with cross-GPU latency forecasting; and runtime counters can classify observed kernel behavior. A proposal should not claim these ideas as novel by themselves, nor treat coarse “GPU utilization” as a direct measure of SM, tensor, cache, memory, or interconnect pressure.

**A credible gap to measure:** whether historical task/capsule feature vectors can predict a *component-wise resource-demand profile* for heterogeneous research workloads, with an explicit distinction between static/declared features available before launch and counters available only after a bounded profiling prefix. Evaluate nearest-neighbor retrieval against a learned predictor and simple analytical baselines; report uncertainty and abstain for out-of-distribution tasks. Hold out entire task families and hardware targets, not random executions of the same workload. Measure calibration and transfer for compute pipelines, memory hierarchy/bandwidth, occupancy/register/shared-memory limits, launch/synchronization overhead, and power where available. Then test whether predicted profiles improve resource-use simulation for proposed chip designs. The cited papers do not establish that a representation learned on DNN graphs or kernel counters will transfer to general AI4Research task/capsule processes, or that predicted pressure alone yields reliable chip-design conclusions.
