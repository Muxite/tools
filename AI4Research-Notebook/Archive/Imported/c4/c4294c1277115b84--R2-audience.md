## Verdict

**VARIANT-1 — Conditional yes.** It reads as an actual ten-minute piece, leads
with a worked example as AUDIENCE.md demands, and is honest about maturity. It
fails on two of AUDIENCE.md's own stated techniques: it never delivers the
"freeze = lockfile" and "logical/physical = interface/implementation"
analogies it promises (they live only in GLOSSARY.md, which V1 tells the
reader to treat as optional). A 1-day colleague reading V1 alone, as intended,
will hit several terms used before they are usable (see jargon table) and one
outright unexplained mechanism ("code re-derives those itself" — how?).

**VARIANT-3 — No, not yet, for its stated job.** Its stated job (AUDIENCE.md
§3) is to be the presenters' *study aid* and *defense document* against a
hostile expert. It is excellent as an engineering audit — precise, honestly
hedged, self-correcting. It is not yet safe to present from, because: (1) it
has no table of contents or anchor index across 39 sections / 1170 lines, so a
presenter under live questioning cannot find the answer fast; (2) several
load-bearing terms are used well before their formal definition (capsule,
physical/logical operator, trust class), which is fatal in a document whose
job is to *teach* two people who onboarded five days ago; (3) the
anticipated-Q&A section dodges the single most exploitable discrepancy in the
report (trust-class enforcement, §17) by not asking it directly; (4) five
imperative, second-person sentences ("Report the token layer as...", "Do not
cite it...", "Cite the code.") are leaked internal drafting notes, not
reader-facing prose — a presenter reading these aloud will look unprepared.

Neither document contains untranslated Chinese; a full-text grep for CJK
characters returned zero hits in both files. That constraint is satisfied.

## Unexplained leaps

1. **V1 line 55** — "code re-derives those itself." No mechanism given anywhere in V1 for *how* citation spans are re-derived from quotes. V3 §4 explains it (deterministic re-binding of `source_quotes` → `source_spans`), but V1 readers are told never to need V3 for the ten-minute version.
2. **V1 §5** — the logical→physical operator diagram jumps from "an abstract role" to "a concrete executor" with a routing table example, but never says *what decides* which physical operator is chosen at runtime beyond "conditions." A colleague will ask "who evaluates `if quota allows`, and when?" — unanswered in V1.
3. **V3 §17 → §22** — the trust-class rank-vs-exact-match discrepancy is stated as unresolved, then the report moves on to Verification (Part III) without ever circling back to say what this means for a working system *today*. A presenter needs a one-line practical answer ("in practice this only matters for X, because Y") and none is supplied.
4. **V3 §11.3** — "This is the concrete answer to 'how does it avoid stuffing everything into a prompt'" for `context_projection.py`'s 8,000-token budget — but the mechanism ("retain high-value events, summarise low-value ones") never says who or what scores an event as high/low value. A colleague will ask "scored by what — a heuristic, a second model call, a rule?" and the report has no answer at that point.
5. **V3 §18** — admission reads normalised field names not present in the raw manifest, flagged `[inferred]` — good honesty, but the report never resolves *where* that normalisation happens, leaving a presenter unable to answer "show me the normalising code" if asked.
6. **V1 §8 / V3 §32** — both versions explain the deadlock's *cause* precisely, but neither explains why the completion-confirmation code had filename-inference logic in the first place — was it a leftover from an earlier design, a defensive heuristic added under time pressure, or an accidental import? Without that, "the bug that explains the whole system" reads as a morality tale without an origin story, which a supervisor will probe ("who wrote that code and why did it exist at all if the freeze thesis was already the stated design?").

## Tone problems

### Sycophancy / advocacy language
- V1: "**The most telling statistic**..." — conclusion baked into the label before the reader sees the number.
- V3 §15: "**This is a governance boundary you can point at** — a concrete artifact, not a policy document." — defensive, rhetorical, reads as persuasion rather than assessment.
- V1 & V3 both close their best bug narrative with near-identical triumphant lines: "**That is the whole thesis, defended against its own implementation**" (V1) / "**This is the freeze thesis defended against its own implementation**" (V3). Repeating the same rhetorical beat in both documents makes it read as a rehearsed talking point rather than an observation — exactly what a skeptical supervisor is primed to discount.
- V3 §29(f): reframing six recurrences of the same bug as "design pressure, not carelessness" is advocacy, not assessment (see table above).
- V3 §14: "**Correction to project documentation**" is fine and appropriately blunt — contrast this with the softer language elsewhere; the report is not consistently rigorous in how hard it pushes on its own findings.

### Harshness / register problems (opposite failure)
- Five imperative, second-person sentences read as internal QA notes left in the final draft rather than harsh-toward-the-project content: "Report the token layer as designed but not wired" (line 368), "Do not present HIVE as working distributed execution" (line 525), "Do not cite it as an enforced contract" (line 344), "Cite the code" (line 224), "Report the token layer..." This isn't harsh toward the project so much as harsh/brusque toward the *reader* — it tells the presenter what to do instead of stating the fact. In a document meant to be read aloud or quoted under questioning, this is a real defect: fix all five to third person.
- No instance found of the report being unfairly harsh toward the project's actual engineering; if anything the balance tips toward advocacy (above), not excessive criticism.

## Missing content the audience needs

1. **Cost and latency.** Neither document states how long the 2026-09-03 15-node run took, or its token/dollar cost. A supervising engineer evaluating whether this is viable will ask this in the first two minutes; it is absent from both documents.
2. **Runtime enforcement of declared effects.** Capsules *declare* read/write/execute/network/cost/risk (V1 §4, V3 §16), but neither document explains what actually stops a capsule from violating its own declaration at runtime. `capability_token.check_path_access()` — the component that looks like it would answer this — is explicitly reported as having no production callers (V3 §9, ledger #6). The real enforcement is described only as "operatord's allowed-output-roots and staged-publish mechanism," with no explanation of what that mechanism actually is (a path-prefix check? a sandboxed process? a container?). This is a security question a careful reviewer will not let go, and both documents leave it unanswered.
3. **Trust-class practical resolution.** §17's open discrepancy (rank vs. exact-match enforcement) is flagged but never resolved into "here is what happens for a real plan today." The anticipated-Q&A section does not ask this question directly, despite it being the report's own most-cited unresolved item (ledger #9). This is the single most exploitable gap for a hostile questioner and the document does not pre-arm its presenters for it.
4. **Who wrote this, and how.** Neither document states team size, whether the codebase itself was agent-authored (relevant given the domain), or the development timeline. A supervisor sizing up "is this a two-week prototype or a year of work" gets no anchor.
5. **What a refusal or failure actually looks like to a user.** V1 states refusal is a "designed outcome, not an error" but never shows what the user receives — an error message, a partial IR, nothing? Same gap in V3.
6. **A worked example of §17's discrepancy** or of the `desktop_bridge` missing dispatch branch (ledger #8) — both are stated as facts but never illustrated with what actually happens when a plan hits them (silent no-op? crash? explicit error?). Presenters cannot defend "it fails how" if asked, because the report doesn't say.

## Presenter-defensibility analysis — the 5 hardest claims

For each: can a presenter with 5 days of context defend this live? What's missing to make that possible?

1. **"Verification recomputes every stage rather than trusting stored verdicts" (V3 §7).**
   Defensible only if the presenter can say, without hesitation, that recomputation replays deterministic compiler stages and never re-invokes an LLM. The report never states this distinction explicitly. **Missing:** one explicit sentence distinguishing "recomputed" (deterministic re-serialization + hash compare) from "re-decided" (would require a fresh, possibly different, LLM output). Without it, the first hard follow-up ("so if I re-ran verification, could I get a different hash because the model behaves differently?") has no scripted answer.

2. **Trust-class enforcement: rank vs. exact match (V3 §17, ledger #9).**
   Not defensible as written — the report itself states this is unresolved. **Missing:** a rehearsed, honest one-liner for presenters, e.g., "We found two enforcement mechanisms and could not determine from static reading alone which one binds at plan-compile time; our working hypothesis is X; we would need to instrument a real run to confirm." Currently a presenter has only "it's an open question," which invites the follow-up "then how do you know the system behaves correctly here?" — for which there is no prepared answer anywhere in the document.

3. **52 of 102 executors are vendor-neutral, presented as a structural/architectural virtue (V1 §5, V3 §10).**
   Only half-defensible. The presenter can state the registered count confidently, but the report itself elsewhere states 63/102 enabled and 93/102 "available" (V3 §10) without reconciling the three numbers. **Missing:** a single explicit sentence stating how many of the *enabled* operators are vendor-neutral, so the presenter isn't caught doing arithmetic live when asked "so in practice, in the one run that succeeded, how much of it was vendor-neutral?"

4. **"There is no formal-verification formalism in this system" despite the vocabulary in the design docs (V3 §20).**
   Defensible in substance (well-evidenced by the zero-occurrence grep results), but the presenter needs to be ready with a concrete example of what "verification" *does* mean here beyond the label, e.g. reciting one real capsule invariant as a string-expression precondition. The report gives the example material (§16's worked invariants) but doesn't connect it explicitly to §20's claim — a presenter would need to make that link themselves live, under pressure. **Missing:** an explicit forward/back cross-reference so the presenter has the example ready without hunting through 1170 lines.

5. **The deadlock bug as proof of the freeze thesis (V3 §32, V1 §8).**
   Mostly defensible — this is the best-supported, most concretely narrated claim in either document, with direct quotes from the maintainers' own diagnosis. The remaining risk: if asked "was this the *only* instance of runtime semantic re-inference you found, or did you audit for others?", there is no answer in the report. **Missing:** either a statement that a systematic search for similar patterns was or wasn't performed, so the presenter isn't left improvising an answer to "how do you know this was a one-off?"
