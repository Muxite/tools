# 03 — Capability seams and the shipped tool surface

This is dsh's most portable idea. If you take one thing from the repo, take this.

---

## 1. The seam definition (from `docs/glossary.md`, verbatim-faithful)

A **capability seam** is a *swappable capability* with **three roles**:

| Role | What it is | Constraint |
|---|---|---|
| **Service Definition** | the Cordis `Service` owning its `ctx.<key>` and vocabulary types | an **abstract class** (e.g. `ShellExecutor`) or a **concrete registry** (e.g. `WebRuntime`) — **never a TypeScript `interface`** |
| **Service Provider** | one or more implementations | |
| **Consumer** | one or more packages injecting the service, commonly a model-facing tool | |

**The seam is the complete capability, never one role.** The glossary explicitly
reserves the word: name a constituent by its role, class, service, contract, or
extension point — don't call a provider "a seam."

**Canonical example — `packages/shell/`:**

```
dsh-shell                     Service Definition   (ctx.shell)
dsh-bash-local / dsh-bash-sandbox   Providers
dsh-tool-bash                 Consumer             (the model-facing `bash` tool)
```

**Splitting rule:** roles occupy separate packages *when they evolve
independently*. One package may own several roles when they're one concern —
`dsh-user-approval` owns the approval Service Definition and its concrete
implementation together. `AGENTS.md` states the reverse obligation too: **adding
a capability means designing all three roles**, and a seam is "complete, never
one role."

**Dependency rule:** extension plugins depend on **Service Definitions, never
concrete providers**. `dsh-agent-loop` is swappable; UI, hook, and tool plugins
depend on `dsh-agent`.

## 2. Why the seam pays off

The stated payoff, and it's a real one:

> Filesystem and subprocess providers share **one execution world**, so pointing
> them at a remote sandbox moves **Bash, PTY, and LSP** with them — **with no
> provider forks**.

That is the whole argument for the abstraction in one sentence. Swap the `ctx.fs`
and `ctx.subprocess` providers to an E2B remote sandbox (`packages/e2b/` is
exactly this POC) and every capability layered on them relocates, because none of
them reached past the seam.

The same shape holds for `ctx.subagents`: providers "vary just as widely behind
one interface, from a fresh child agent to a delegated turn in another product."

## 4. The shipped tool surface

From the generated `docs/tool-catalog.md`, which **boots each plugin** rather
than reading source. Grouped by what they do:

**Filesystem / search**
- `read`, `write`, `edit`, `read_image` (`dsh-tool-fs`) — read-before-write policy
  is a *separate* plugin (`dsh-fs-observation-policy`), an `fs/*` event gate with
  **no schema change**. `read_image` refuses unless the exact routed model
  declares image input.
- `str_replace_editor` (standalone view/create/unique-replace/insert)
- `glob`, `grep` — spawn the **packaged** `@vscode/ripgrep` binary through
  `ctx.subprocess`, never a host `rg`, never a shell layer. Capped results spill
  the full list to `ctx.spillStore`.

**Execution**
- `bash` (`dsh-tool-bash`) and `pwsh` (`dsh-tool-pwsh`) — same seam, different
  dialect; `pwsh` mirrors `bash` call-for-call minus sandbox controls.
- `bash` / `pwsh` **persistent** variants over `ctx.terminals` (PTY, owner-isolated).
- `terminal_open/read/send/close/list/signal` — six opt-in PTY tools.
- `run_code` (`dsh-tools`, **PTC mode**) — see §5.
- `lsp` — returns structured `LSP_UNAVAILABLE` when no provider is registered,
  rather than changing its schema.

**Delegation and background work**
- `subagent` (+ alias `subagent_fork`), `list_subagent_models`
- `send_message`, `interrupt_agent`, `list_agents` (continuable background children)
- `job_list`, `job_output`, `job_kill` — **kind-agnostic**: background bash runs,
  PTY sends, and subagents are all controlled through the same three tools.
- `workflow`, `ralph`

**Session state and planning**
- `todo_write`, `exit_plan_mode`, `create_goal` / `get_goal` / `update_goal`,
  `schedule_create` / `schedule_list` / `schedule_delete`
- `session_search`, `session_trace`, `session_event_read/search/trace` (read-only,
  every result authorized from the immutable calling agent session)

**Other**
- `web_search`, `web_fetch` · `skill` · `present` (deliverables) ·
  `ask_user_question` (pauses the tool call until a UI provider returns a human answer)
- `spawn_teammate`, `team_task_*`, `wait_agent` — experimental Agent Teams,
  **disabled in the shipped `dsh-base` bundle**
- `cordis_define/run/stop/undefine/inspect_*` — self-modification, **not in any
  shipped tree**

### Details worth stealing

- **Tool *names* can be load-time config.** `dsh-tool-subagent`'s `toolName`
  defaults to `subagent`; a deployment may expose the package under a different
  or additional name. The catalog records shipped aliases explicitly.
- **Config choices change the *description*, not just behavior.** `todo_write`'s
  `allowParallelInProgress` is REQUIRED with no default; `true` yields a
  description inviting several `in_progress` items, `false` yields one asking for
  exactly one active task. The catalog records which branch it documented.
- **Every tool row declares `Requires` and `Writes / affects`** — the `ctx.*`
  services it injects and the session events it emits. That table is a
  machine-maintained capability manifest for the model surface.

## 5. PTC mode — the unusual one

`run_code` under `mode: ptc` / `mode: both` is a **reserved transport owned by the
tool registry**, outside the filterable capability layers. Under `ptc` it is the
registry's **only** wire contribution: the other visible capabilities are emitted
as a **generated SDK section in the loaded runtime's language**, and the model
writes a program that calls them as bindings.

Those bindings are scheduled under a stated native concurrency contract —
submission-ordered starts, concurrency-safe bodies overlapping up to
`maxParallelSubCalls` — and each **re-enters the complete guarded tool pipeline**,
linking every nested execution to the outer result via
`tool/ptc-dispatch-start` + `tool/ptc-dispatch` pairs.

So: instead of N tool schemas, the model gets one code tool plus an SDK, and
nested calls remain fully governed and fully logged. This is a meaningfully
different answer to tool-count/context bloat than "prune the tool list," and it
preserves the model-visible ⟺ logged invariant.

## 6. Sandboxing and policy

- `ctx.sandbox` backends: **bwrap** (Linux), **Landlock** (Linux LSM),
  **Seatbelt** (macOS), **Windows ACL**.
- Consumers **wrap argv before spawning** — confinement is applied at the call
  site by the consumer, using a backend, rather than being trusted to the tool.
- `sandbox-policy` is a separate package from the backends, so policy and
  mechanism are independently swappable.
- `guard/` adds loop hygiene: advisory repeat-call reminders plus a
  `tools/execute` **deadline enforcer**.
- `interaction/` owns the approval and permission seams; `dsh-user-approval` owns
  both definition and implementation.

## 7. Honest limits

- **MCP support is tools-only.** One package (`mcp-client`), tools bridged under
  server-qualified names; **MCP resources and prompts are not supported**.
  Nothing ships enabled.
- **`experimental/`, `e2b/` are explicitly POC/unreleased**; `test-support/`,
  `runtime-diagnostics/`, `util/` are declared support-tier with lower
  compatibility expectations.
- **Self-modification (`extensions/`) is deliberately unmounted** in every shipped
  tree — the Agent Note reasoning is that dynamic package code reaches the real
  runtime. Worth reading before anyone proposes an equivalent elsewhere.

  built or run. Schemas in `docs/tool-catalog.md` were produced by *their* CI,
  not reproduced here.
