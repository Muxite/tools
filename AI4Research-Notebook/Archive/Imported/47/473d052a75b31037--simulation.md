# GPU workflow and architecture simulation literature

## Practical split

Use two representations for different questions. A workflow trace captures operators, dependencies, timing, and communication across a training/inference run; a device-level kernel trace captures the executed GPU instruction stream. Workflow traces are portable inputs for system/network simulation, while kernel traces support detailed microarchitecture what-if analysis. Neither substitutes for the other. Reusing a trace holds its workload/software behavior fixed; changing model structure, algorithm, compiler lowering, precision, or kernel implementation requires recollection or a justified regenerated trace. Hardware-only changes can be explored by replaying the same trace if its instruction semantics remain supported.

## Recommendation

First profile the real AI workflow and preserve its dependency graph plus per-operation timing/resource data (Chakra is a candidate interchange format). Identify the GPU kernels responsible for the stress/bottleneck, then collect device-specific traces and counters for those kernels. Use Accel-Sim for detailed NVIDIA kernel-level architectural changes, PPT-GPU where faster broad sweeps are more valuable, and Timeloop/Accelergy only for a separately specified tensor accelerator. Keep claims bounded by the validated target generation and model: rerun physical measurements when the software workload, compiler-generated ISA, or unsupported hardware feature changes.
