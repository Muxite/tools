Read: §1 (p4-6), §2 opening (p7-8), §5.2-5.3 and §6.1-6.3 (p69-73), related work p82 this session. Not re-read: the calculus and metatheory (§3-4). Earlier close read in `notes/20-cordis-spatiotemporal-composability.md`

## Summary
A formal and practical account of **dynamic composition**: loading, unloading and
reconfiguring components at runtime without restarting the process. It is the formal
substrate of the **DeepSeek Harness** (dsh), whose plugins are Cordis components. Two
properties are defined and proved:
- **Temporal composability**: removing a component completely reverts its side effects
- **Spatial composability**: components declare dependencies, and the runtime activates
  and deactivates them as those dependencies appear, change or disappear

## How it works
- ⭐ **Revertible effects** (§3.1): every context transformation carries an inverse that
  the runtime holds; inverses compose in LIFO order, so unloading restores the context
  without a hand-written uninstall path
- **Reactive coeffects** (§3.2): a component declares what it requires; every context
  change is classified as activating, deactivating or neutral for that component
- **Context paradigm** (§3.3): effects and coeffects are mediated through one context
  type, giving an observational equivalence under which components interleave without
  disturbing each other
- A calculus of components and fibers with preservation, temporal and spatial
  composability, progress and confluence results (§4)
- Implementation (§5): TypeScript core library plus a declarative loader with config
  reconciliation and **transactional hot module replacement**; a failed reload restores
  every stale entry from backup (Alg. 10, p69)

## Evidence
- Motivation: 87 of the top 100 VSCode extensions contain code and need a host restart
  to remove; only 7 declare dependencies on non-built-in extensions (p5)
- **Case study, Koishi** (p69-70): a chatbot framework on Cordis v3 with over 4,000
  community plugins; plugins are disabled and hot-reloaded in place
- Stated threats to validity (p70): 1 ecosystem, 1 language, observational; "an
  existence-and-adoption result rather than a quantitative one". No overhead or
  productivity measurement

## Points that matter for the reports
- **System boundary** (§6.1): only effects on locations the system exclusively controls
  can be reverted. Emissions that leave the boundary (bytes written to a shared file, a
  network send) cannot; recovery then needs withholding (output commit) or
  **compensation**, and the proofs do not carry over automatically
- **Access control** (§6.3): a component can reach only dependencies it declared, so the
  full set of proxy-mediated capabilities is **known before it runs** and can be
  approved at load time; interception adds per-call policy such as read-only paths
- ⚠ **Untrusted code needs an external sandbox**: "language-level access control is
  insufficient" against a malicious component (p73)
- §1.2.2 names **self-evolving agent harnesses** as a motivating case: "a faulty
  self-modification can disable the very process needed to recover" (p5)

## Relevance
- **General report**: the foundation for §5.1 (what dsh is). Explains why a dsh
  registration is an effect, why unloading a plugin is clean, and where that guarantee
  stops (the system boundary). Declared dependencies known before load are the hook a
  contract check would use
- **Capsule report**: gives capsule retirement a formal meaning (revert the component's
  effects) and marks its limit: a capsule that wrote outside the boundary needs
  compensation, not reversal. Pairs with the DGM case, where the agent removed its own
  logging
