## What each thing is for

### sciencediscovery

> "ScienceDiscovery is a one‑stop AI research workspace built specifically for scientific research... literature review, hypothesis formulation, code development, experimental trial‑and‑error, and parameter tuning in a single unified environment."

But its own architecture doc narrows this considerably: **"ScienceDiscovery is a local, single-user scientific agent for Linux."** Not multi-tenant, not a hosted service: "The product is intended for trusted local or workstation use, not hosted multi-tenant use." This is the repo closest in purpose to a capsule-based research-agent system, and the one the brief asked to be read most carefully.

Both README and README_zh carry an identical disclaimer (word-for-word equivalent in each language): **"This product serves solely as a workflow orchestration tool and does not embed any AI model capabilities. When users integrate AI models for specific business scenarios, they shall bear full responsibility for compliance obligations under the EU AI Act..."** (ZH: "本产品仅作为流程编排工具，不包含 AI 模型能力...") — this exact disclaimer, near-verbatim, recurs in `deepsearch`, `jiuwenswarm`, and `jiuwensymbiosis` too; it is evidently an org-wide legal boilerplate, not a repo-specific design statement, but it is a consistent, explicit non-goal across all four products: none of them claim to *be* an AI model.

### deepsearch

> "openJiuwen Search is a collection of search capabilities within the openJiuwen open-source project, providing comprehensive intelligent search solutions from deep research to code search... aiming to deliver enterprise-grade Agentic AI search capabilities to enterprises and developers."

Three subprojects, each with its own stated purpose:
- **DeepSearch**: "a knowledge-augmented, high-performance, high-precision deep retrieval and research engine... structured knowledge and large language models with various tools to deliver enterprise-grade Agentic AI search and research capabilities." Advertised capabilities include Deep Research ("多步骤、多源验证、逻辑严谨的结构化研究报告生成" — multi-step, multi-source-verified, logically rigorous structured research report generation), Deep Search (state-space search Q&A), and "Segment-level provenance: Outputs with validated citations, supporting segment-level traceability and confidence assessment."
- **CodeSearch**: "an intelligent retrieval engine for code repositories," built explicitly "on openJiuwen agent-core," that outputs "which files and which lines to look at to resolve" a query — it never executes retrieved code.
- **openjiuwen-search-base**: a shared foundation library with a stated dependency-direction rule (ZH): "依赖方向：base 不依赖任何产品包，产品依赖 base" (base depends on no product package; products depend on base), and "核心导入路径不触碰 openjiuwen / pymilvus / aiohttp" (core import paths never touch openjiuwen/pymilvus/aiohttp — those are optional extras).

### jiuwenswarm

> "JiuwenSwarm is an Agent system that makes multi-agent collaboration truly work... drive multi-agent collaboration, Skill self-evolution, and tool invocation through natural language."

The Chinese README states a differentiation claim the English one does not carry: **"与同类项目相比，JiuwenSwarm 的核心差异在于：Skill 自演进让能力越用越强、蜂群协作让多 Agent 专业分工..."** (gloss: compared to peer projects, JiuwenSwarm's core differentiator is: Skill self-evolution makes capability strengthen with use, swarm collaboration gives multi-agent specialized division of labor). `AgentTeam.md` frames the product's own positioning as a shift from "Harness Engineering" (single-agent capability) to "Coordination Engineering" (orchestration) — i.e. jiuwenswarm frames itself as one level up the stack from single-agent harnesses like sciencediscovery.

### jiuwensymbiosis

> "JiuwenSymbiosis is an embodied-agent framework built on openjiuwen for adapting one safe, auditable Agent workflow to different robot bodies." (ZH: "让一套安全、可审计的 Agent 工作流适配不同机器人本体。")

This is the outlier of the four: not a research-workspace or retrieval/orchestration product but a framework for embodied robotics, whose two headline claims — "configuration-agnostic capability reuse" and "safety control" — map to concrete, well-documented mechanisms (detailed below). README and architecture.md EN/ZH were found in lockstep with no material divergence, notably because both were touched by the same HEAD commit ("docs: update architecture.md").

## Goals and direction

**sciencediscovery** distinguishes current-phase implementation from roadmap explicitly in several places:
- The write-time skill-admission pipeline (Chinese-only docs, see below) is staged MVP → M1 → M1.5 → M1.6 → **M2 (planned)** → **M3 (planned)**. M2 is "evaluation-assisted publish, baseline/candidate comparison"; M3 is "policy-gated auto-publish for low-risk additions only, still human confirmation for edits/deletes" — both explicitly future, not current.
- CAS (content-addressed storage) explicitly excludes, in this phase: "Fork, cross-instance recovery, GC, OCI export/import, Evaluation, or a version browser." There is no deletion/GC interface at all currently: "Garbage collection is outside the current implementation."
- Skill self-evolution's ZH-only doc lists explicit non-goals for the *current* phase that read like a deliberate scope fence rather than a permanent boundary: "不新增独立多 agent 编排系统" (no new independent multi-agent orchestration system — reuse subagent instead), "不让 Agent 静默 commit Skill Library" (the agent may never silently commit to the skill library), "不在第一阶段实现 frontier、自动发布策略" (no frontier or auto-publish policy in phase 1), "不修改基础模型权重" (never modifies base model weights).

**jiuwenswarm**'s skill self-evolution pipeline states a deliberate present-tense discipline rather than a roadmap item, worth reading as a design rationale: "The current main path does not create experience merely because an error keyword or a single user correction appears... the main Agent considers the evidence from the current task, decides whether the improvement is reusable, and only then decides whether to suggest Skill evolution." This is a stated intention about *how* evolution should work, not just what exists today.

**jiuwensymbiosis** states plainly, identically in EN and ZH architecture.md and AGENTS.md, that automatic skill authoring from execution history is *not* implemented: "Automatically saving successful sequences as new SKILL.md files is not implemented." Its Trace-Feedback-Loop design doc (Chinese only) goes further and frames this as a *permanent* design choice, not a temporary gap: "闭环刻意在 `SkillPatchProposal → SKILL.md` 之间设置人工门禁。Trace 只能说明"发生了什么"，无法证明某条工作流规则在所有机器人和场景下都安全，因此模块不自动写技能文件。" (gloss: the loop deliberately places a human gate between a generated SkillPatchProposal and the actual SKILL.md; a trace can only show what happened, not prove a workflow rule is safe across all robots and scenes, so the module never auto-writes skill files.) This reads as a stated, principled non-goal — evidence sufficiency is explicitly distinguished from safety proof, and the gap between them is closed by a human, permanently, by design.

**deepsearch** shows less roadmap language and more "this is the current architecture" description, but one candid engineering note stands out from its coverage-evidence-channel doc: a documented prompt-injection threat model added in response to a specific PR review ("PR !380 审核意见"), with two concrete code-enforced mitigations bound to a named test (`test_subsection_outline_prompt_untrusted_evidence_boundary`) — this is a "we found a problem in review and fixed it in code, not just in docs" trace, valuable as an example of the evidence discipline this whole survey is trying to practice.

## Findings relevant to the capsule

### Capability reuse (skills, tools, plugins, capability assets)

- **sciencediscovery**: skills are `SKILL.md` files with YAML frontmatter (`name` — stable kebab-case identity, ≤64 chars, "every revision or alternative version of one logical Skill must reuse exactly the same name"; `description` — the selection trigger; optional `metadata.version`) plus a structured body: Overview, Core Capabilities, an explicit "When To Use" / "Do NOT use this skill when" boundary, an Input Template (typed), a **Handoff Contract** ("the exact output shape a downstream consumer can rely on without reading intermediate messages"), Methodology/Workflow, Output Template, and an Error Handling table. This is a real per-skill contract with declared inputs, outputs, and non-goals — but it is **not machine-validated** beyond frontmatter parsing at write time. At *read* time, selected skills are staged read-only and hash-verified before a run starts: "Freeze selected revision, package hash, instructions, and resources at run start, so later reads cannot observe a disk edit," recorded in a manifest that ends up in the Prompt Manifest so "an execution can be replayed against an exact package."
- **sciencediscovery** also composes whole pipelines, not just functions: subagent orchestration dispatches up to 10 child tasks per turn (50/request), each an independent agent run with its own workspace/budget and an optional JSON-Schema-validated **Brief v1** contract (`goal`, 1–20 constraints, 1–20 output requirements, 1–12 collaboration rules), server-versioned and immutable once running. The `science-research-team` skill is a fixed-topology pipeline (intent parsing → literature/evidence domain → code/evaluation iteration loop with a hard cap → report writer) that explicitly forbids the agent from improvising: "Do NOT plan independently, re-design the topology, or skip steps."
- **jiuwenswarm** has two tiers of capability packaging: an **Agent Skill** (single `SKILL.md`, same frontmatter shape as sciencediscovery's) and a **Swarm Skill** — a 5-file directory (SKILL.md + roles/ + workflow.md + bind.md + dependencies.yaml). `bind.md` declares real resource/behavior contracts: `max_parallel_teammates`, `total_wall_clock_budget`, `total_token_budget`, Behavioral Constraints, and named Failure Handling strategies. `dependencies.yaml` distinguishes a declared-empty list (`[]`, meaning "checked, confirmed no dependency") from omission (a spec violation) — a genuine declared-absent-vs-undeclared precondition distinction, worth noting for capsule contract design. Skills exist exactly once on disk; distribution to teams/members is via `allow`/`deny` visibility JSON rather than copies, with an explicit precedence rule: "deny always wins over allow."
- **jiuwenswarm**'s **AutoHarness** hot-loads Tools/Skills/Rails as a "Harness Package" with no restart, multiple packages stacking, and Activate/Deactivate/Export/Import — the closest analogue in this repo to a versioned, composable capability *unit* (at the harness level, not the skill level).
- **jiuwensymbiosis**'s mechanism is the most precise and load-bearing finding across all four repos for "capability reuse," detailed in its own subsection below.
- **deepsearch** registers tools as openJiuwen `LocalFunction`s with a documented input contract (`query` + `search_engine_name`) and output contract (`search_engine`, `search_results`, optional `error`); Runtime-API (user-configured HTTP tool) responses are explicitly size- and depth-bounded ("响应大小限制为 2 MiB，JSON 深度限制为 20，单个对象或数组最多 1000 项"). But there is **no capability/skill marketplace or runtime admission gate for tools** in deepsearch — registration is developer/config-time wiring, not a runtime-discoverable, versioned capability asset the way sciencediscovery's or jiuwenswarm's skills are.

### Configuration-agnostic capability reuse — the jiuwensymbiosis mechanism (read closely, as the brief asked)

The marketing phrase decomposes into a concrete design: a shared `ActionSpec` contract, capability gating, and per-body adapters, documented identically in `architecture.md` EN/ZH and `AGENTS.md`.

- An action's full contract — name, capability gate, parameters, result shape, preconditions, effects — is declared **once**, centrally, as an `ActionSpec` instance (`api/actions.py`, class in `api/decorators.py`). This is the single source of truth for what an action *means*.
- Each robot body ("adapter") supplies only an *implementation* of that same spec via `@implements(SPEC)`. Quoted: "So the same action name means the same thing on every robot, and a plan or SKILL.md written for one body is meaningful on the next." `@implements` attaches a `ToolMeta` that *holds* (not copies) the spec, so "the contract fields exist in one place and a planner cannot read a different answer from the vocabulary."
- Where an action is generic across bodies, the adapter one-line-forwards to a shared function in `api/defaults.py`; where hardware geometry differs, the adapter overrides only the method body, and "the contract comes from the spec, the implementation only says how" (`adapter-reference.md` §5).
- **Capability gating is the admission mechanism**: an `Env` (hardware) declares a `frozenset` of capability strings from a closed vocabulary (`KNOWN_CAPABILITIES`, 19 total, e.g. `motion.cartesian`, `grasp.parallel`, `vision.eye_to_hand`); an `Api` *derives* its own capability set from which `ActionSpec`s it has bound. `build_robot_tools(api, env=env)` exposes tools only for `api.capabilities ∩ env.effective_capabilities` — an action whose capability the hardware lacks never becomes an LLM-visible tool at all. Mismatches are caught at session start, not at plan time.
- Drivers implement capability-sliced Protocols (structural typing, not base classes) — a `RobotDriver` requires only `close()`; each capability adds a sibling protocol (`CartesianDriver`, `JointDriver`, `BaseDriver`, `CameraDriver`, ...). Quoted rationale: "A mobile dual-arm body has no flange pose; a bench arm has no wheels; a single god-protocol would force one of them into `NotImplementedError` stubs."
- A **planning-contract layer** sits above mere callability: each `ActionSpec` (and the compound-action `SkillSpec`, which shares the same fields) carries `requires`/`provides`/`invalidates` (robot self-state, closed vocabulary) and `produces_location`/`consumes_location`/`invalidates_locations` (location freshness). The contract "never encodes an order; it states pre-conditions and effects so a planner can derive one" — `parse_sequence` accepts any permutation whose preconditions hold. **This is the closest analogue in jiuwensymbiosis to an admission gate, and it is called sequence validation, not "admission" or "precondition gate"** — the sub-agent noted this consistent with the brief's own warning about keyword-miss.
- Caveat stated in the docs themselves: "A capability name alone does not guarantee that a task can run: the task also needs corresponding actions, satisfied preconditions, and the necessary sensor and model data." Capability gating is necessary but not sufficient.
- New hardware integration is templated to exactly 7 files (`templates/xxx_adapter/`); "changes are concentrated in the adapter" (architecture.md §14) — task/planning logic is untouched when porting to new hardware. A static structural checker (`scripts/validate_adapter.py`) enforces this with numbered diagnostic codes (e.g. "E-04 unknown capability," "A-08 Api capability missing from Env," "D-14 Driver missing required members").

In short: "configuration-agnostic" means the planner and skill layer only ever see the shared `ActionSpec` vocabulary, filtered to the capability-intersection this body supports — never robot-specific method names or geometry. "Capability reuse" means the contract is written once and every body either reuses the default implementation verbatim or supplies a body-specific implementation behind the identical name and contract.

### Safety control — the jiuwensymbiosis mechanism

Not one mechanism but five independently-gated "Rails" (Agent-lifecycle hooks), from `architecture.md` §8:
- **SafetyRail** (`before_tool_call`): pre-motion boundary checks whose watch set is *derived from declared capabilities* (`motion.cartesian` → Z-floor + XY bounds; `motion.joint` → joint soft limits; `motion.base` → per-command translation/turn caps; etc.). Every envelope property defaults to `None` = no check: "declaring a capability never invents a limit the hardware never stated." Rejects with `ValueError`.
- **RecoveryRail** (`on_tool_exception`): auto-home + release end-effector on failure, checking `env.holding_payload` first so a payload isn't dropped blindly — explicitly "best effort and cannot guarantee that the device ends in a safe state."
- **VisualFeedbackRail**: post-action camera frame injected before the next model call — no effect in `fastagent` mode, so no automatic step-by-step visual verification there.
- **DiagnosisRail** (requires tracing enabled): online failure diagnosis injected before the next LLM turn.
- **TraceRail**: parallel, non-blocking evidence collector (see Evidence/provenance below).

The documents are unusually candid about the limits of all this, quoted verbatim (both EN/ZH): "Software boundary checks do not replace device emergency stops or hardware protection." / "SafetyRail is a software precheck; Driver and controller hard limits remain required." / "Software `emergency_stop()` does not replace a physical E-stop, guarding, or operating procedure." `parallel_tool_calls` is rejected outright when the Env declares cartesian/joint/suction/parallel-grasp capability, together with a self-critical disclaimer: "This check does not yet cover every motion and grasp capability, so its acceptance does not establish that other capabilities are safe to run concurrently."

So "safety control" is concretely: a bundle of software rails whose scope is derived from the same capability declarations used for tool exposure, with an explicit and repeated refusal to claim this substitutes for hardware-level safety.

### Contracts (declared inputs, outputs, preconditions, effects, permissions, cost)

- **sciencediscovery**: SKILL.md Handoff Contracts (above); Brief v1 subagent contracts (goal/constraints/output requirements/collaboration rules, JSON-Schema-validated, immutable once running); Prompt Manifest per model turn (model/endpoint, CAS refs, skill id/hash/version/revision, cost, `redactionStatus`).
- **jiuwenswarm**: SKILL.md frontmatter + Swarm Skill `bind.md` (resource/behavior contract: parallelism cap, wall-clock budget, token budget, behavioral constraints, failure-handling strategy) + `dependencies.yaml` (declared-absent vs. undeclared distinction).
- **jiuwensymbiosis**: `ActionSpec` (name, description, capability gate, parameter schema, result shape as JSON Schema, `requires`/`provides`/`invalidates`, location-freshness fields, access-effect fields `opens_access`/`closes_access` — though "current built-in actions do not declare these effects" — and a planner-visibility flag). `ToolMeta` = spec + body-specific call schema; a mismatched signature raises `ContractViolation` **at import time** — a static, code-enforced admission check, not just documentation.
- **deepsearch**: tool contracts as above; a cross-cutting structured error contract (`error-and-common-contracts.md`): 6-digit `StatusCode` (20 = common, 21 = module) shared across algorithm/framework/utils/server layers.

Cross-cutting observation: **jiuwensymbiosis has the only contract in the four repos that is enforced by the type system / import-time check** (`ContractViolation`). sciencediscovery's and jiuwenswarm's skill contracts are structured but validated only at parse/frontmatter level, not against a schema of the contract's semantic fields.

### Admission and validation (deciding whether a capability is good enough to keep or publish)

This is the area where the brief's specific warning ("grepping for 'admission'/'precondition' missed a 2,734-line subsystem under different vocabulary") mattered most, and all four sub-agents were specifically directed to read whole documents rather than grep. Findings:

- **sciencediscovery — the single most capsule-relevant subsystem found in the entire survey**, and it exists **only in Chinese-language internal design docs** (`skill-self-evolution.md`, `skill-library-management-m1.md`, no English counterpart at all): a `SkillLibrary` has versioned states with a `head` pointer; a run pins `head` to a concrete `versionId + contentHash` at creation ("避免评估被演进中的 head 污染" — avoid evaluation being contaminated by an evolving head). An agent/subagent calls `propose_skill_library_update`, which runs a **dry-run only** and returns diff/diagnostics/conflicts plus a pending `proposalId` — **"不更新 head；不发布新版本"** (does not update head; does not publish a new version). Publishing (`publish_skill_library_update`) requires the existing permission-confirmation flow: **"Agent 可以 propose；publish 必须经过用户确认权限"** (the agent may propose; publishing must go through user permission confirmation). Built-in libraries are read-only to self-evolution. Same-priority name conflicts with differing hashes **block the run** rather than silently resolve. A stated safety principle: **"ground truth、参考答案和 benchmark hidden data 只能用于分析失败，不能写入 Skill 正文"** (ground truth/reference answers/hidden benchmark data may only be used to analyze failure, never written into skill body text). This is a working propose → dry-run → diagnose → human-gated publish → versioned/rollback-capable pipeline for a capability artifact — functionally very close to what a capsule's admission gate needs to do — and it is undocumented in English.
- **sciencediscovery** also has a separate, lighter-weight **Reviewer Specialist**: disabled by default, runs as an independent checkpoint whose findings are read-only ("do not mutate an Artifact or force another run") and "does not determine main-run success." Quick tier checks citations and computation provenance specifically.
- **jiuwenswarm**'s Symphony subsystem was specifically checked against the brief's warning (structural grep of the 8,142-line `symphony/` source plus full reads of both language docs) and found to be genuinely **not** an admission gate: its own FAQ states "Does it install new skills automatically? No." / "Does it replace Team/Cluster Mode dispatch? No." It is retrieval (a tree for browsing installed skills) plus orchestration (`symphony_compose_graph`, an executable chain built from a `can_feed` graph gated by `min_edge_confidence`/`max_depth`). The real admission-gate-like mechanisms in jiuwenswarm live elsewhere, under different names: the **swarmskill-creator's structural validator** (5-file completeness, required frontmatter, role count, mermaid presence, bind.md sections, dependency completeness — "Exit code 0 = compliant"); the skill-evolution pipeline's approval gate (`evolution_reviewer` subagent with read-only tools → structured proposal → `auto_save` flag, always true for Teammates → `EvolutionStore`); and AutoHarness's "Extension verified → Preview component manifest → Dynamically injected" flow. Note the sub-agent's caveat: this conclusion rests on two full doc reads plus a structural (not line-by-line) source grep, not an exhaustive code audit — so absence of a hidden gate elsewhere in the 8,142 lines cannot be fully ruled out.
- **jiuwensymbiosis**: three concrete gates — (a) `ContractViolation` at import time (static, see Contracts above); (b) `parse_sequence` validating every planned step's requires/params/result-references/location-validity before execution; (c) `scripts/validate_adapter.py`, a static structural checker. A calibration subsystem has the clearest fail-closed publication gate in this repo: **"Publication is fail-closed: only ACCEPT plus a reload smoke test through the adapter's own runtime loader publishes a formal schema-2 artifact. Anything else lands in a `.candidate.json` REVIEW report that the runtime loader will not load. Never hand-promote a candidate."** — though this is calibration-specific (sensor/geometry calibration), not a general-purpose capability admission mechanism.
- **deepsearch**: no capability/skill admission gate found for tools or search capabilities themselves. What *is* validated with genuine rigor is generated-content evidence: citation checking re-validates every LLM-asserted citation against the original text span ("标记片段不能回查原文...就视为本次 LLM 校验失败" — if the marked span cannot be traced back to the original text, this LLM validation attempt is considered failed), with failed batches bisected and retried up to 3×; ordinary citations that finally fail are dropped, but chart citations fall back to an existing source at minimum score 0.85 instead — a documented, deliberate exception to the "drop on failure" rule.

### Versioning, lineage, deprecation

- **sciencediscovery**: `SkillLibrary` head-pointer versioning with pinned runs (above); CAS agent-state versioning produces an **AgentManifest** (behavior + content-derived harness build descriptor) and an **AgentRevision** (lineage) per `createAgentRun`; `RefStore` keeps append-only history roots with compare-and-swap commits ("A crash exposes the old or new complete head, never a partially committed head"); record schemas are strict RFC 8785 JCS and **"Unknown record schema versions are rejected; there is no implicit in-place upgrade."**
- **jiuwenswarm**: skill evolution has explicit lifecycle commands — `/evolve_list`, `/evolve_simplify`, `/evolve_rebuild` (archives Skill+log, merges into SKILL.md), `/evolve_rollback [version|latest]` — and rollback is itself reversible ("current state auto-archived before restore"). Harness Packages support Activate/Deactivate/Export/Import.
- **jiuwensymbiosis**: **no skill/action versioning or deprecation mechanism found** beyond the calibration artifact's "schema-2" label, which is calibration-specific. This is stated as an explicit gap by the docs themselves (the "automatically saving successful sequences... is not implemented" line under Goals and direction above).
- **deepsearch**: versioning found only at the data-storage layer — Milvus collections are named `{prefix}{name}__{schema_version}`, with an explicit rule: **"schema 变更必须递增 `schema_version`，禁止静默复用旧结构"** (schema changes must increment schema_version; silently reusing old structure is forbidden). This is index/storage lineage, not capability/skill lineage — deepsearch has no capability-versioning concept analogous to the other three.

### Evidence and provenance (traces, audit trails, claim-to-evidence links, reproducibility)

- **sciencediscovery** has the richest documented model here. `review-provenance.md` (EN+ZH, ZH substantially more detailed) describes: an `ExecutionRun` per sandbox run (tool/language, CAS refs, exit code, environment revision, kernel mode, permission epoch, network policy, sandbox engine, changed files); an `ArtifactDerivation` per generated file, with the caveat that "this audit does not automatically make every diff a visible Artifact" (visibility requires explicit `declare_artifact`, upload, MCP download, or collected job output); a **Prompt Manifest** per model turn (model/endpoint, CAS refs for system/input/response, skill id/hash/version/revision, cost, `redactionStatus: "not-applied" | "not-required"` — explicitly: **"There is no automatic secret redaction."**); and a genuine **Claim → EvidenceLink → EvidenceItem** model, where `EvidenceLink` is typed (`supports`/`context`/`contradicts`), `EvidenceItem.origin` distinguishes `mcp-record`/`paper`/`execution`/`artifact`/`remote-job`/`user-input`, and `contentScope` distinguishes `curated-record`/`abstract`/`metadata` from full text — with `fullTextRetrieved` only set true "after a successful `paper_extract_pdf` call," i.e. "the condition for claiming the full text was read." This is a designed, sentence-level claim-to-evidence provenance chain, not just a log.
- **sciencediscovery**'s `/evolve` search discipline is worth carrying into capsule design directly: data is split into `rollout`/`gate`/`test` shards, and the `test` shard is never seen by the search — **"Nothing that steers the search ever touches the test shard, so the figure you are shown at the end cannot have been inflated by the search process itself."** The scorer is frozen against candidate edits: "without it the shortest path to a high score is to weaken the thing measuring it."
- **jiuwensymbiosis**'s `TraceRail` (opt-in, off by default) produces a structured `ExecutionTrace` per `agent.invoke()` with per-step `TraceEntry` (tool, params, output summary, success/error, duration, observation snapshot, optional frame path, rail events, log events), persisted once per invoke to `<workspace>/traces/{run_token}.json` with an immutable `run_token`. It is explicitly bounded (`max_entries`, `max_frames`, no raw RGB/depth, tool output truncated to 2000 chars) and explicitly evidence-only: the replay tool "replays execution evidence and does not command the robot to execute the actions again." An offline Trace Feedback Loop clusters failures into a `SkillPatchProposal` but always terminates at the human gate described above; its confidence score is explicitly disclaimed: **"只由样本数决定，不等价于真机安全置信度"** (determined purely by sample count, not equivalent to real-hardware safety confidence). Both jiuwensymbiosis design docs state a shared failure-safety invariant: a logging/tracing/diagnosis failure must never change task success/failure ("日志故障不得改变机器人任务结果").
- **deepsearch** has the most developed *citation*-provenance pipeline of the four, distinct from run/session provenance: global source tracing runs after report generation (strip existing references → convert citations to internal markers → identify sentences needing citation → match candidate sources → validate → append reference list), and only validated citations survive ("只保留校验通过的文本引用"). Its coverage-evidence channel adds a documented, code-enforced prompt-injection boundary (above) — a real trust boundary on evidence text, not just a claim. However, the sub-agent found **no run-level immutable snapshot/lineage record** analogous to sciencediscovery's frozen Prompt Manifest / CAS agent-state versioning — deepsearch's `report_bundle/` is a packaging/export format (with path-traversal-safe resource-ID validation), not a provenance manifest.
- **jiuwenswarm**: no dedicated provenance document was surfaced by the sub-agent's reading list; the closest analogue is the skill-evolution proposal's structured fields (`target`/`section`/`reason`/`content`) and the `EvolutionStore`'s `evolutions.json`, plus AutoHarness's package manifests. This is thinner than sciencediscovery's or jiuwensymbiosis's provenance model and may simply reflect the sub-agent's necessarily incomplete coverage rather than a real absence — flagged in "What I could not determine."

### Composition (do capabilities compose into systems, not just functions?)

All four products compose beyond single tool calls, in different registers:
- **sciencediscovery**: subagent orchestration (Brief v1 contracts) + the `science-research-team` fixed-topology pipeline skill + `/evolve`'s whole evaluation system (candidate generation → sandboxed scoring → tree/archive search).
- **jiuwenswarm**: Swarm Skills are literally 5-file compound-capability packages with roles, workflow, bindings, and dependencies — a system-level unit, not a function-level one. Symphony composes orchestration graphs from a `can_feed` relation between skills.
- **jiuwensymbiosis**: `SkillSpec` (compound action) shares the same contract fields as a primitive `ActionSpec`, and `parse_sequence` derives valid orderings from preconditions/effects rather than requiring one to be hand-specified — genuine precondition-driven composition, though scoped to sequencing actions on one robot body, not multi-agent system composition.
- **deepsearch**: composition here is pipeline-internal (retrieval → report generation → source tracing → bundling) rather than a general-purpose capability-composition mechanism exposed to users; deepsearch does not appear to let users compose arbitrary capabilities into new systems the way jiuwenswarm's Swarm Skills or sciencediscovery's subagent Briefs do.

### Research-agent workflows (literature, hypotheses, experiments, reports)

sciencediscovery is the only one of the four with dedicated research-workflow skills (`literature-searcher`, `evidence-extractor`, `code-engineer`, `result-evaluator`, `report-writer`, chained by `science-research-team`) and an evolution/search engine (`/evolve`) for hypothesis/parameter search with the held-out-test-shard discipline above. deepsearch supports the "Deep Research" report-generation half of this (multi-step, multi-source, cited reports) but has no hypothesis/experiment-loop equivalent to sciencediscovery's `/evolve`. jiuwenswarm and jiuwensymbiosis are not research-workflow products in this sense — jiuwenswarm is a general multi-agent coordination product, jiuwensymbiosis a robotics framework.

### Relationship to agent-core

This is one of the sharpest findings across the four repos, and it runs in the **opposite direction** in different products:

- **sciencediscovery** — narrower and more specific than "removed agent-core" as originally framed. There is **zero literal occurrence** of the string "agent-core" anywhere in the current tree (checked across `.md`/`.json`/`.ts`/`.py`). It appears exactly once in git history, in a merge-commit body (`3a267cfeb790daab094e13de00b627954054820a`, PR description, not a shipped doc): **"Runtime Core 仍只依赖稳定的 `ContextAssembler` 端口；不引入 openJiuwen agent-core、DeerFlow Python 进程或新的跨进程协议。"** (gloss: Runtime Core still depends only on the stable `ContextAssembler` port; it does not introduce openJiuwen agent-core, the DeerFlow Python process, or a new cross-process protocol.) So the documented fact is a **standing refusal to adopt agent-core** stated once as a design constraint on a specific PR, not a repo-wide announced removal of a prior dependency. What *is* extensively documented as removed is a related but distinct thing: the Python gateway process running LangChain's `create_agent`, and the `deer-flow` Python framework dependency (submodule, first-launch download, and packaging pin all explicitly listed as gone in `agent-backend.md` §11's "Retired" table). Separately, `runtime-core.md` notes an internal package literally named `agent-runtime` (not `agent-core`) was split apart: "The former private `packages/agent-runtime` aggregate has been removed after all repository imports were migrated to their owning capability package." **What replaced all of this**: a self-built TypeScript native agent loop (`packages/runtime-core` / `services/api/src/native-agent/`) — "the stable, domain-neutral execution kernel" — depending only on four typed ports (`ContextAssembler`, `ModelClient`, `ToolDispatcher`, `RunEventSink`), with **"no product package dependencies"** and explicitly **"no LangChain or LangGraph."** Dependency direction is enforced by a `pnpm architecture:check` script. The sub-agent flags its own synthesis here as interpretation: whether an earlier historical version of sciencediscovery (outside this repo's current git history) ever depended on `agent-core` proper could not be determined from the docs.
- **deepsearch** goes the opposite way: it is built **on top of** agent-core throughout, and says so repeatedly. Root README: "DeepSearch is built mainly on openJiuwen agent-core and can connect to different LLMs and tools." (ZH: "DeepSearch 主要基于 openJiuwen agent-core 构建"). CodeSearch README: "Built on openJiuwen agent-core, a retrieval agent autonomously inspects the repository map..." `deepsearch/AGENTS.md` names `openjiuwen_deepsearch/framework/openjiuwen/` as an "orchestration layer built on openJiuwen agent-core concepts." Only `openjiuwen-search-base` is deliberately kept independent of agent-core (an optional extra, not a core import).
- **jiuwenswarm** also builds directly on agent-core: `AutoHarness.md`'s first line states **"Auto Harness is an agent self-optimization solution built on openJiuwen Agent Core."** The tiered tool-permission engine and `builtin_rules.yaml` are sourced directly from agent-core ("agent-core `openjiuwen/harness/resources/builtin_rules.yaml`"), not reimplemented. An unresolved ambiguity: `SkillSelfEvolution.md` separately cites "the openJiuwen evolution framework," and the sub-agent could not determine from docs alone whether this names the same substrate as "Agent Core" or a distinct framework.
- **jiuwensymbiosis** has the tightest, most explicit coupling of all four: a **pinned** dependency in `pyproject.toml`, `"openjiuwen>=0.1.13,<=0.1.17"`, confirmed against `agent-core/pyproject.toml`'s `name = "openjiuwen"` — i.e. agent-core ships under the package name `openjiuwen`, and jiuwensymbiosis's README states it is "built on openjiuwen" (= agent-core). It directly reuses agent-core's `SkillUseRail`, re-exported via `agent/abstractions.py`, with its own Rails purely additive on top. The upper version-bound pin suggests deliberate, cautious coupling rather than loose integration.

**Net finding**: of the four DeepAgent products, three (deepsearch, jiuwenswarm, jiuwensymbiosis) build directly and explicitly on agent-core (the `openjiuwen` package); sciencediscovery is the outlier, having built a self-contained native TypeScript execution kernel and stating, once, in a PR description, a deliberate choice not to introduce agent-core into it. This is worth treating as a real architectural divergence inside openJiuwen, not a uniform "the org moved away from agent-core."
