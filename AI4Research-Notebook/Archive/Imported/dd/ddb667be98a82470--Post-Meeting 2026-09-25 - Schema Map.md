**Post-meeting, 2026-09-25: the most immediate goal is to find every major schema that connects the major
components of the design, investigate each one, and then work out its inputs.**

## Goals, in order

1. **Find all the major schemas** that connect major components. We find them by tracing the big-picture (M4)
   Mermaid map (`capsule-openjiuwen/merged/figures/big-picture/big-picture.mmd`, generated by `big_picture.py`).
2. **Investigate each one:**
   - what exists today, and where;
   - what our design needs from it;
   - what is missing or wrong.
3. **Find the inputs to each schema**, from our design needs and the system's objectives: who writes each field,
   from what, and why.

**How importance is read:** by how many edges touch a schema and how many components it reaches. The Capability
Capsule schema is obviously central for exactly this reason: more edges touch it than anything else except the
observability record.

## How the list was made

The expanded M4 map (251 edges) was parsed. For each schema node, the edges touching it were counted, and each
edge's far end was mapped to its component block. Edges that cross between blocks show the data handed across
each seam. The counts are from the map as republished on 2026-09-25 (v9).

## Outcome, same evening: 15 schemas drafted for sign-off

The 16 were reviewed for necessity and became 13 specs, then 15 when Muk asked for node outputs (**Artifact**) and
for what goes to and comes back from verification (**Verification**, request and result; gate results left the
Observation). The specs are in `huawei/ai4research-design/schemas/`:

- **merged:** the policy and `needs.when` into the Declaration; Binding `invocations[]`, the pre-freeze stage record
  and `gate_verdicts[]` into one **Observation** record, so the run contract is truly immutable;
- **not ours:** Symphony's descriptor and plan graph (mapped from the Declaration and Plan pages instead);
- **Standing from M1:** M1's "latest version" pointer is a one-state Standing, so there is one moving pointer;
- **added:** a **port type vocabulary**, which the map had no owner for;
- **out of scope:** the workflow version (meta-RSI).

14 naming conflicts are resolved in `schemas/schemas.md`, e.g. every schema id is `cc.<name>.v1` (the Declaration's
`schema_version` 2.10 becomes `cc.declaration.v1`), `contract_hash` → `interface_hash`, `sprint_id` → `run_id`,
`check` → `check_id`, "Verdict" only for admission. Each spec is v1 when Muk, Xiaoyang, Ramika and Saurav sign.

**Opus review, same evening:** 5 blockers, 16 should-fix and 13 nits, all verified in source and applied. The main
changes: freeze copies into each Binding everything dispatch needs, so dispatch still reads only the run contract;
the Plan gets `bind[]` and `yields[]` to wire the contract's `given` and `want` to step ports; the issue template's
capsule block is a literal `cc.declaration.v1`, and modules get a separate work order; Verification is a request and
a result with one writer each; Artifact separates content (by hash) from the per-run record; AI4Research's
`discovery` block is kept in the contract; the gates keep the Directive's names (`decide_acceptance`). Known gap
before M3: the research port types (`report`, `source`, `claim`) have no fields yet.

**What/how/reuse split, same evening (Muk: "split what is done vs how it should be done, plus what we can reuse").**
Three Opus agents classified every field; each reuse claim was checked in source. Outcome:

- Records hold only *what*. Every threshold, default, bound and rule moved to a new **`cc.policy.v1`**: one
  versioned document per epoch, pinned by hash (`policy_ref`), with one owner per section. This reverses "policy merged
  into the Declaration". openJiuwen already splits this way (agent-core Card vs Config; Symphony
  `CapabilityDescriptor` vs `OrchestrationConfig`), and so did AI4Research.
- New foundation page **`cc.common.v1`**: one envelope, `Ref`, `EvidenceRef`, and extension rules: `ext` per owner,
  registries for open lists, promotion to the core only when a second reader appears. A schema template for anything
  new.
- Judge calibration is a Finding kind `verifier_audit`, and Verdict invalidation is a Finding kind `invalidation`. Both
  kept records that never change from being edited. There is no new record for either.
- Main reuse: the Observation is stored in agent-core's KV store (`exclusive_set`) and stamped on its spans, not a
  parallel log. Spans alone are sampled and expire after 7 days. Plans use Symphony statuses and ports through an
  adapter (Symphony keys by capability, not step). E2A shapes are used for intake and delivery.
- Naming conflict 15: our `step_id` goes on spans as `cc.step_id`, never as `openjiuwen.step.id` (the ReAct step).
- Questions per person to settle CC: `ai4research-design/process/questions.md`.

**Proposal pass, same evening (Muk: "propose our schemas as best as we can... describe each field").**

- Every field on all 17 schema pages has a type from a fixed grammar, Req, From, a per-field State
  (`proposed`/`changed`/`agreed`) and a description with an example.
- New `design/principles.md` (14 principles) and `schemas/invariants.md`:
  - INV-1 to INV-18, the type grammar and the finalization lifecycle;
  - a "where to edit what" table, so each fact has one home.
- `tools/sync.py` generates every derived section and lints fields, types, links and diagrams:
  - who reads, writes and stores a record, edited only in the component pages' properties;
  - clickable Obsidian diagrams (`class ... internal-link`);
  - the index tables.
- The policy page has a proposed `m1` value for every section, and holds every registry's values.
- `process/questions.md` gives a proposed answer to all 37 questions.
- Research port types are proposed from AI4Research's evidence schemas.
