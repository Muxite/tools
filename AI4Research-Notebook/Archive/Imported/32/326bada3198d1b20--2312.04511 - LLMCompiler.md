# 2312.04511 · An LLM Compiler for Parallel Function Calling (LLMCompiler)

Kim, Moon, Tabrizi, Lee, Mahoney, Keutzer, Gholami · UC Berkeley, ICSI, LBNL · ICML 2024 · 22 pp (9 body)
Read: body p1-5 (motivation, architecture, dynamic replanning), results from abstract/contributions

## Summary
Borrows from classical compilers to replace ReAct's one-call-at-a-time loop: an LLM
**planner compiles the request into a DAG of function calls** with placeholder variables,
a deterministic **Task Fetching Unit** dispatches every task whose dependencies are met,
and an **Executor** runs them in parallel. Faster, cheaper, and sometimes more accurate,
because intermediate outputs no longer interrupt the model's reasoning.

## How it works (p3-5)
- **Function Calling Planner** (LLM): decomposes the query into tasks with dependencies,
  e.g. `$1 = search(Microsoft)`, `$2 = search(Apple)`, `$3 = math($1 / $2)`; guided by a
  fixed prompt, tool definitions and optional in-context examples; can **stream** tasks
  as they are planned
- **Task Fetching Unit**: greedy fetching of ready tasks; substitutes placeholders with
  real outputs; "can be implemented with a simple fetching and queuing mechanism **without
  a dedicated LLM**" (p4)
- **Executor**: runs independent tasks concurrently; each task has its own memory
- **Dynamic replanning**: when the graph depends on unknown intermediate results, the
  Executor feeds back to the Planner (like runtime branching)

## Results (p1-2)
- HotpotQA / Movie Recommendation: 1.80× / 3.74× speedup, 3.37× / 6.73× cost reduction
  vs ReAct
- ParallelQA (new): up to 2.27× speedup, 4.65× cheaper, +9% accuracy
- Game of 24: 2× faster than Tree-of-Thoughts via replanning; WebShop: up to 101.7×
  speedup, +25.7% success
- Failure modes of ReAct it avoids: repeated identical calls, early stopping on partial
  results

## Relevance
- REPORT.md §3.1 and §3.3: the canonical **"compile the request into a DAG, execute
  deterministically"** paper, with the model confined to planning and the dispatcher
  model-free. Same split as AI4Research's planner → scheduler
- Differences: the goal is latency and cost, not checking; the plan is not typed, hashed
  or frozen, and replanning is allowed at run time
- Its accuracy gain from keeping tool outputs out of the reasoning loop parallels the
  deep-research finding that orchestrators are where errors enter (2608.24306)
