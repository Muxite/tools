Reviewer: adversarial agent, read-and-measure only. Nothing in the design, deck or asks was edited.

Scope: `DESIGN.md` (1,072 lines), `deck/deck-draft.md` slides 1–15, `asks/*.md`, the six agent summaries
with *Claims checked* tables, close-read notes 20–38, the supervisor's slides (note 45) and answers (note 46),
and openJiuwen source at `agent-core` `e23806c10732`, `sciencediscovery` `cee1974`, `skillhub` `236f56c`.
The source findings in *Buildability* are from a parallel read of agent-core, cited file:line.

**Verdict in two sentences.** Requirements (a), (b) and (e) are answered, (d) is still one-sided and (c) and
(f) are weak on the slides that exist. Two of the design's headline claims to beat the alternatives do not
survive: "the one check no prior system performs" and "none binds a hash to a verification result". What
survives is narrower. Nothing else read here combines a persistent, per-version, hash-bound admission
record, a pre-registered no-regression suite against a named predecessor, and a deterministic precondition
filter under one contract. That is a defensible *integration* claim, not a novelty claim for any one
mechanism. On the chosen platform, agent-core, the declared-versus-observed check can only be built at
tool-call granularity. The effect-level version the design promises needs a sandbox that does not exist in
agent-core.

## 2. Contradictions (each with both locations)

**C1. The content hash covers the certificate that names it. MUST fix.** §2.3 table (line 334):
`content_hash` "is the hash of the manifest itself, so it covers every component hash below". The same
table (line 344) makes `admission_record`, the certificate "bound to one `content_hash`", a *manifest
field*. A manifest cannot contain a record naming its own hash, and adding the certificate after admission
would change the hash and so the identity. §2.3.1 lines 362–365 and 373–379 treat the certificate as a
separate record ("a certificate names this `content_hash`"), which is the workable design. The same applies
to `lineage` if "supersedes" is written after the fact. **Fix:** hash the manifest *excluding*
`admission_record`, or move the certificate out of the manifest into the store. Say which.

**C2. A certificate inside an append-only manifest cannot be "withdrawn".** §2.2 lines 322–326:
"Revocation is a certificate being withdrawn (§2.3.1)". §2.1 invariant 2 says versions are never edited.
If the certificate lives in the manifest (C1), revocation edits an immutable object. It needs a separate
revocation record or exposure log. The exposure table (§2.2 line 285) has "revoked" as a state, which
implies an exposure store that §2.3, §7.2 M1 and slide 8 never name.

**C3. A local edit does not land in row 2 of §2.3.1.** §2.3.1 lines 381–383: "A person who edits a
capsule on purpose has made a new capsule with a new hash, so the edit lands in row two, where it can be
accepted". Row 3 (line 379) says components that do not match the manifest are "refused, and not
overridable". Editing a body file without regenerating the manifest's `components` is exactly a component
mismatch, so it falls in row 3. Row 2 is only reachable if some tool re-manifests the edit. That tool is
unspecified, and whoever runs it can also launder a damaged install into row 2.

**C4. The prediction in §7.4 contradicts the premise in §1.3.** §1.3 lines 72–77: Alita-G's library,
kept on outcome only (by this design's standard a library with "the gate off"), raises GAIA 75.15 → 83.03,
and "the question is not whether a self-built library helps". §7.4 line 1059 predicts "arm two [library,
gate off] should be at or below arm one [no library]". 2608.05810's own summary adds that on InterCode
**ungated was still +8.0 pp net positive** (summary, Results/Transfer). Slide 14's IF ASKED also predicts
"the gate barely moves task scores". Pick one prediction.

**C5. Who writes the admission suite?** §2.2 lines 257–260: RSI owns "writing the manifest, the suite and
the implementation". Invariant 5 (§2.1 line 220) requires the suite author not to see the implementation.
§2.2 line 272 says a "different author", checked "from provenance". The verification ask (`asks/verification-ramika.md`,
*What I send you*) says **this model** sends "the admission suite … by an author who never saw it", and §4.2
line 794 has the capsule model giving "a held-out suite". §2.3.1 line 393 and invariant 5 say admission
"never writes the suite itself". So the suite comes from RSI, the builder's side. Invariant 4's
independence then rests on RSI separating two of its own agents, and "different author" is undefined for
LLM agents: a second session, a second model, or a second family? Supervisor question 5 already notes that
some arguments need a different model family. **Undefined author identity makes invariant 5
uncheckable.**

**C6. The asks contradict the 2026-09-21 RSI split and the supervisor.** `asks/rsi-saurav.md`, *The short
version*: "Our two models are the same loop seen from two ends". The supervisor said "the function of CC
and RSI are totally different". The same ask says *My design has a build loop … That loop is arguably RSI*,
"Proposals enter the build loop as candidates", "enough for the build-decision agent to write one", and
"RSI may change capsule bodies" (which breaks invariant 2, since bodies are never changed and a change is a
new version). §2.2 and §4.2 now give the build loop to RSI. `asks/QUESTIONS-teammates.md` Saurav Q3 still
asks "Is the build loop yours or mine? My draft has one". The RSI ask also has no *If the answer is no*
section, although §4.3 line 822 says every ask has one. **MUST** be rewritten before the teammates read it.

**C7. The name "library loop" survives in five places after the loops were renamed.** §2.2 now has *Use*,

## 4. Buildability

All agent-core paths are under `openjiuwen/agent-core/openjiuwen/` at `e23806c10732`. jiuwenswarm is at

**Headline.** Phase 0 is buildable on agent-core, but the store must be built, since agent-core has no

### 4.4 Phase 0 / M1 (manifest schema, content-addressed append-only store, lineage, binding, pinning).**
Buildable, with low risk, and largely precedented inside openJiuwen, which cuts both ways:

- **Store.** ScienceDiscovery already ships a SHA-256 CAS in OCI layout with atomic, non-replacing
  hard-link publication and hash verification on every read (`sciencediscovery/docs/en/explanation/cas.md:9-27`).
  It is TypeScript and sits outside agent-core (ScienceDiscovery removed its agent-core dependency, `notes/11` §4),
  so it is a pattern to copy, not a module to import. The design never mentions it.
- **Pinning per run.** ScienceDiscovery stages each selected skill's frozen revision per execution and
  verifies it against the package hash before the sandbox starts (`skill-progressive-disclosure.md:36,56`).
  That is invariant 3 plus §2.3.1's bind-time check, already implemented in openJiuwen. §5.4 must list it,
  and §6.3 cannot claim reproducibility as a difference.
- **Manifest + lineage.** ScienceDiscovery's `AgentManifest` + `AgentRevision (lineage)` and per-turn
  before/after state (`cas.md:59`) is the nearest precedent for a reconstructable log (H4).
- **The C1/C2 defect** (hash covers the certificate; the certificate cannot be withdrawn) must be fixed in
  the schema before M1, or the store's identity scheme is wrong on day one.

- **Binding by version** needs the pinned snapshot to reach Symphony as the provider `SourceSnapshot`,
  whose `snapshot_id` must equal the `source_revision` of every graph mutation (§4.2 above). Design the
  library revision id to be that value.

**Admission (M3).** The executed parts are buildable: the held-out suite, no-regression, provenance checks,
and a threshold over verification's verdicts. program_opt's seam is a usable execution path, but its
`local_execution` is not isolation. Declared-versus-observed is buildable only at tool-call granularity on
agent-core (§4.1 above). At effect granularity it needs a new observing sandbox.
