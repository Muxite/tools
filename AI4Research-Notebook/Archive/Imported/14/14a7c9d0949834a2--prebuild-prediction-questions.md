# Pre-build questions for a future GPU workload predictor

AI4Research is not built yet. This note recommends what to measure now with standalone workloads so a later historical-vector predictor can be evaluated credibly. These are preparation recommendations, not claims that the future system exists or that the proposed dataset/model has been validated.

## Questions and provisional answers

**What can be known before launch, at low cost?**

Use workload-side descriptors that are available without running the target on the target GPU: operation/algorithm family; source or IR-derived operation counts and data types; input and output shapes/bytes; estimated arithmetic intensity and memory traffic; parallelism/grid size; dependency/branch structure; and, when applicable, framework graph/operator type and execution settings such as batch size. Kerr et al. show that pre-execution CUDA metrics can predict kernel behavior; Johnston et al. demonstrate architecture-independent workload features across multiple devices. In practice, static counts may require IR/source access or model graph metadata, so retain provenance and mark unavailable features rather than silently imputing them. [Kerr et al., “Modeling GPU-CPU Workloads and Systems” (2010)](https://llvm.org/pubs/2010-03-GPGPU-ModelingGPGPU.html) · [Johnston et al., “OpenCL Performance Prediction using Architecture-Independent Features” (2018)](https://arxiv.org/abs/1811.00156).

**What is gained by a short profiling prefix?**

Counters and runtime summaries reveal realized behavior that static estimates miss: achieved occupancy, SM/pipeline activity, DRAM/L2/shared-memory traffic, stalls, launch duration and variability. Keep the prefix explicitly separate as an “after-prefix” predictor, record its duration and sampling method, and predict only the remaining/full-run outcome. A model that uses full-run counters to predict full-run pressure is retrospective classification, not pre-launch prediction. Counter-based GPU kernel classification has been demonstrated, but it requires executing each target kernel and has narrower kernel-class coverage than a general task predictor. [“Utilizing GPU Performance Counters to Characterize GPU Kernels via Machine Learning” (2020)](https://pmc.ncbi.nlm.nih.gov/articles/PMC7302272/).

**What raw records and labels should be kept?**

Store immutable workload identity/version, task family, source or graph hash, input-shape/configuration, compiler/runtime/library versions, launch metadata, and feature extraction version. For every measured run, record exact GPU model and architecture, clocks/power mode, memory capacity/bandwidth metadata, driver/tool versions, warm-up and repetition policy, timestamps, and raw per-kernel/per-phase elapsed time. Keep raw counter values and units, collection scope, and tool configuration alongside derived ratios; save host-to-device transfers, synchronization, and whole-task wall time separately from kernel time. Labels should be measured values (including repeated-run spread), not only categories: per-kernel and per-phase latency; memory traffic/bandwidth; compute/pipeline activity; occupancy; power/energy if available; and an explicitly defined bottleneck label derived from documented thresholds or expert review. Do not collapse “GPU utilization” (kernel active during a sample interval) into compute-unit utilization or bandwidth pressure; Horus explicitly distinguishes these. [Horus, “Interference-Aware and Prediction-Based Scheduling in Deep Learning Systems” (TPDS 2022)](https://doi.org/10.1109/TPDS.2021.3079202).

**Should the first predictor be nearest-neighbor, analytic, or learned?**

Use all three as measured baselines, in increasing complexity: (1) a nearest-neighbor/profile lookup on normalized workload descriptors with distance and neighbor agreement reported; (2) a simple analytical roofline/resource-count estimate; and (3) regularized regression or a small tree ensemble. Nearest-neighbor is valuable because it tests whether workload reuse and “similar task” retrieval has value at all, but it can fail on sparse coverage and misleading feature distances. The analytical estimate gives a legible floor/ceiling check, while regression tests whether patterns generalize beyond near duplicates. NeuSight illustrates decomposing latency prediction around tiles and hardware behavior; it does not establish that one model wins for general task vectors. [Stevens and Klöckner, “A Unified, Hardware-Fitted, Cross-GPU Performance Model” (2016)](https://arxiv.org/abs/1604.04997) · [Lee et al., “Forecasting GPU Performance for Deep Learning Training and Inference” (ASPLOS 2025)](https://doi.org/10.1145/3669940.3707265).

**How should evaluation separate interpolation from transfer?**

Report at least two separate tests: a workload-family holdout (entire algorithms/models/tasks withheld) and an input-size/configuration holdout within known families. Add a hardware-family holdout only if there are enough genuinely distinct devices; otherwise report per-device and cross-device results as exploratory. Random row splits can put near-identical inputs or repeat runs on both sides and overstate reuse generalization. Pre-register grouping by task family and source/graph lineage. For each test, report error and calibration by family and resource label, plus nearest-neighbor distance so out-of-coverage cases are visible. Architecture-independent feature work used leave-one-kernel-out checks; GPU benchmark characterization work shows why suite diversity and redundancy should be assessed rather than assumed. [Johnston et al. (2018)](https://arxiv.org/abs/1811.00156) · [“An Automated Framework for Characterizing and Subsetting GPGPU Workloads” (ISPASS 2016)](https://vtechworks.lib.vt.edu/bitstream/handle/10919/64331/ispass16-gpuworkload.pdf).

**How can hardware-dependent target leakage be prevented?**

Keep workload descriptors, target hardware descriptors, and measured labels in distinct fields. For a prospective design query, provide only declared workload descriptors plus an explicit candidate hardware configuration/specification; never feed target-run counters, achieved occupancy, measured bandwidth, or telemetry into the pre-launch model. Treat counters from the target GPU as labels or as prefix-only inputs in a separately evaluated model. Split and normalize carefully: fit scaling/transforms on training data only, and group all runs from one workload lineage together. Report intrinsic demand estimates separately from hardware-normalized utilization: an absolute byte or operation demand is not the same as percent-of-device capacity. This separation is a design recommendation inferred from the distinct inputs/targets in static-feature, counter-based, and cross-GPU prediction papers.

**Which small workload set gives useful diversity before collecting a large history?**

Start with a compact, feature-stratified set rather than many arbitrary tasks: dense GEMM/tensor compute; streaming bandwidth; stencil/locality; irregular sparse gather/scatter; graph traversal; reduction/scan/atomics; FFT or other structured transforms; and launch/synchronization-heavy small kernels. Include at least two sizes per family to expose scaling and cache transitions, and retain repeated runs for measurement noise. Choose candidates by feature-space coverage and add workloads that fill gaps. The 2016 characterization study finds suite redundancy and diversity differ; Parboil had stronger coverage than Rodinia/SHOC in its analysis. ALTIS motivates modern workloads beyond older suites, including DNNs and graph analytics. These suites are seeds for coverage, not evidence that they represent AI4Research capsules. [ISPASS 2016 characterization paper](https://vtechworks.lib.vt.edu/bitstream/handle/10919/64331/ispass16-gpuworkload.pdf) · [ALTIS: “Modernizing GPGPU Benchmarking” (2019)](https://arxiv.org/abs/1906.10347).

## Minimal pre-build experiment plan

1. Select roughly one small representative workload per resource/behavior family above, with a second size/configuration for each. Freeze workload identity, input and launch metadata.
2. On one available GPU, run isolated workloads with a fixed warm-up and repeat protocol. Save per-kernel timing, whole-task timing, phase boundaries, raw counters where available, and device/software metadata. Run only enough profiling to establish that the proposed labels are collectable and repeatable; this is dataset preparation, not model integration.
3. Build the three baseline input sets: static/declared only; static plus short-prefix summaries; and, as an explicitly retrospective diagnostic, full-run counters. Do not use the third as evidence of pre-launch prediction.
4. Compare nearest-neighbor lookup, a transparent analytical estimate, and a simple regression/tree model on family-held-out and configuration-held-out splits. Add another GPU only when available and treat it as a separately grouped transfer test.
5. Use results to decide which features and workload families are missing before expanding collection. Do not optimize a model or claim chip-design validity from this pilot.

## Existing tests to refine or stop

- **Generic batching tests:** keep only as a throughput/aggregation sanity check. They do not establish resource-pressure prediction unless batch size, shape, overlap, and per-kernel ground truth are recorded. Add a fixed-workload comparison across sizes and batch settings to separate scaling from concurrency.
- **Solo/pair tests:** retain solo runs as calibration and pair runs as an interference test, but choose pairs to span complementary and competing resource profiles. Record both jobs’ individual-alone baselines and concurrent slowdowns/counters. Arbitrary pairs or a single “good/bad pair” do not validate nearest-neighbor task prediction or component attribution.
- **Operational cold-start tests:** preserve launch, JIT, loading and first-result measurements separately from steady state. Control cache/residency explicitly. The separate problem of an unfamiliar task with no historical neighbor requires its own family-held-out test and abstention baseline; do not conflate it with operational startup.
- **Stop treating** a high-level GPU-active percentage as the target for component pressure, full-run counters as pre-run features, or random repeat splits as transfer evidence. Avoid expanding a large benchmark set until the compact set demonstrates feature/label quality and family coverage.
