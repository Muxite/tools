Your pool metaphor translates well into concrete responsibilities:
Pool model	M2 responsibility
Swimmer	JiuwenSwarm’s agent reasons, chooses actions, delegates, and adapts
Floating capsules	Discoverable packages containing tools, skills, MCP integrations, specialist agents, or data
Pool quality	Admission tests, input checks, execution controls, output checks, and independent verification
Swimming history	Durable records linking actions, versions, inputs, results, and scientific claims


The key change is when we commit. Keep the objective, constraints, and evidence obligations explicit. Bind exact versions, inputs, permissions, and checks when an action is dispatched. Let future actions change as discoveries arrive.

This gives us the fluidity you described without losing reproducibility. An experiment retains its preregistered protocol; an unexpected result can lead the agent to design another experiment. New software can enter the pool after qualification and become available for subsequent actions.

The proposed action cycle is:
1. Assess the current goal, observations, unresolved questions, and budget.
2. Discover eligible capabilities.
3. Inspect the relevant declarations and select an operation.
4. Execute through the capsule’s enforced checks.
5. Record the outcome and decide what to do next.
This uses the agent’s ordinary decision loop. It does not require a separate planning call before every action.

Your declaration idea is particularly valuable. Use structured filtering first—modality, input compatibility, permissions, resources, admission status—then semantic search within eligible candidates. Load detailed contracts only for the shortlist. A text-only operation never competes for direct video processing, though an explicit conversion operation could make it useful afterward.

The JiuwenSwarm reconciliation is concrete: its existing provider assembly, skill discovery, MCP configuration, session facilities, and optional Symphony planning offer integration points. AI4R’s contribution should concentrate on:
- Capsule declarations, qualification, installation, updates, and revocation.
- Discovery that combines compatibility filters with semantic relevance.
- Guarded invocation that runs the required checks automatically.
- Research state and evidence linking results to claims.
- Structured failures that support repair, alternatives, or an honest stop.
The portable capsule runtime is a useful starting point, but it still has gaps: process-local admission, incomplete portability of pipeline checks, timeout limitations, and semantic review that excludes original inputs. Those need explicit M2 work.

I would retain node chains as optional recipes for bounded procedures. They should be capabilities the agent can select, rather than the mandatory structure governing every research task. Intent compilation likewise fits at the user boundary: clarify the request and produce an editable brief, then allow further clarification as research develops.

There is external support for this direction: Anthropic describes research as dynamic and dependent on intermediate discoveries, and openJiuwen’s own harness paper emphasizes capability composition and runtime adaptation.

One correction to the earlier report matters: reactive agents also accumulate errors. M2’s expected advantage comes from adaptation plus enforced detection and recovery, not simply removing the graph. The proposal therefore includes a matched evaluation against native JiuwenSwarm and M1plus, measuring independently correct completion, recovery, false rejection, and cost per correct completed task.
