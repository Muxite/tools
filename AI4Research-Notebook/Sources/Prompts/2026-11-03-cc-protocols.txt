# CC Protocols — a unified declaration and invocation standard

Create a self-contained `CC Protocols/` folder under **Designs → CC and Strata delivery**. Use the November 3 single-CC declaration as the starting point, the M2a call and receipt contracts for runtime behavior, and the reviewed Strata/Muse Spark presentation for the Factory and Lab workflows.

**A Capability Capsule (CC) is a versioned, installable package that exposes one or more related operations.** Before calling an operation, a person or Lab agent should be able to tell what it does, what it needs, what it can change, what it returns, and what its result establishes. That is the usability test for the standard.

## Keep the declaration small and unambiguous

- Retain the existing vocabulary: `takes` for inputs, `gives` for outputs, `needs` for execution prerequisites, `changes` for permitted effects, and `guarantees` for checkable commitments. Define the boundary of each term with examples. For a profiler, the target process is an input, permission to inspect it is a prerequisite, attaching instrumentation is a possible effect, and a sampled trace is an output. A complete trace can satisfy a guarantee even when it reveals poor performance.
- Give each fact **one authoritative location**. Define a port or check once and reference it by ID wherever it is shared. Derive package summaries and discovery views from operations. Keep granted permissions on the bound call, observed effects on the receipt, and scientific verdicts on the evaluation. Authors should never have to keep duplicate lists in sync.
- Specify a compact YAML form for one operation and a named-operation form for bundles. Both expand to the same JSON model. Publish an exhaustive field table covering meaning, type, scope, requiredness, default, and validation. Define identifier scope, versioning, digest subjects, and the differences between omitted, empty, and unresolved values.
- Keep domain details in typed inputs, outputs, or versioned profiles. A CPU tool should need no GPU fields. A profiler must still be able to declare attachment privileges, supported targets, sampling limits, possible perturbation, and partial-trace behavior. Unknown mandatory semantics must be rejected explicitly.

## Test against different kinds of CCs

| Case | What the protocol must demonstrate |
|---|---|
| Small CPU transformation | A short declaration is sufficient. A caller can distinguish invalid input, execution failure, and a valid empty result. |
| Profiler operated by a Lab agent | The agent can decide whether it may attach to a particular target, identify what sampling may disturb, start a bounded capture, and interpret a complete, partial, or unavailable trace. The receipt identifies the target and attempt. |
| Multi-operation diagnostic package | An inspector and a benchmark can share a carrier and port definitions while keeping different prerequisites, effects, and guarantees. Selecting the inspector does not grant benchmark permissions. |
| Factory-built Strata tool | A pinned source recipe resolves to a specific executable release. A mutable reference, incompatible ABI, or missing implementation produces a specific diagnostic. |
| Strata/Muse Spark measurement | A Lab agent binds an eligible operation to the candidate, model, workload, and qualified GB10 environment. A result identifies exactly which revision ran, including local adjustments. A valid measurement can show that the candidate missed its target. |
| Cross-domain and legacy CCs | Replay representative existing CC fixtures, including a non-Strata tool and an older declaration. Preserve their input, output, failure, effect, and provenance meanings or identify the exact incompatibility. |

## Acceptance criteria

1. Parse the embedded examples, expand the compact declarations, and validate the normalized records against existing schemas wherever compatibility is claimed. Include rejecting fixtures for duplicate IDs, conflicting definitions, undeclared effects, unresolved references, and unsupported required profiles.
2. Apply a **caller comprehension check** to every example. Using only the published CC description, a reviewer must be able to choose the operation, supply valid inputs, predict its observable effects, find the outputs, and distinguish success, partial evidence, and failure.
3. Apply a **field ownership check** across the corpus. Every required author field must serve a demonstrated use. No example should require the same fact to be authored twice. Record any necessary compatibility duplication as compiler-generated output.
4. Verify the README diagram against the worked Factory and Lab flows, check the folder’s internal links, and distinguish schema validation, fixture replay, and actual hardware execution in the reported results.
